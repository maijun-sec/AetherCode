## 二、一句话摘要

复杂图工作流生成基准：子序列与子图三层匹配。

---

## 三、背景与动机

随着大语言模型（LLM）驱动的智能体（Agent）在推理、检索、工具调用等任务上的能力快速提升，"先规划后执行"已成为学术界与工业界共同关注的核心范式。所谓工作流生成（Workflow Generation），即由 LLM 在接收到自然语言任务描述后，自主输出一张由若干原子操作（节点）与依赖关系（边）构成的计划图（Plan Graph），再交由下游执行器逐步落地。一个高质量的工作流不仅能缩短端到端推理时延，还能显著抬升任务成功率；反之，一个错误的工作流则会让再强的执行器也"南辕北辙"。

然而，现有的工作流评测长期存在四个显著短板。其一，**评测粒度过粗**：绝大多数基准仅报告"端到端成功率（Holistic Success Rate）"这一聚合指标，无法定位工作流在哪一步出现偏差；其二，**图结构表达能力弱**：现有基准大多停留在简单 DAG 或线性链，难以覆盖分支（Branch）、循环（Loop）、并行（Parallel）等真实业务场景；其三，**对齐标准松弛**：常用字符串相似度或操作符匹配，忽略了"边"的语义；其四，**场景覆盖狭窄**：缺乏对数据分析、网页自动化、代码生成、复杂推理等多领域的系统采样。

WorFBench 正是为弥补上述缺口而设计：它通过引入子序列匹配（Subsequence Match）与子图匹配（Subgraph Match）两套细粒度度量，将"工作流生成"从单一黑盒评估转向可解释的逐步诊断；同时将评测场景扩展至六大领域，并在 1,600+ 任务上系统刻画了主流 LLM 在序列规划与图规划之间的能力鸿沟。其核心立场可凝练为一句：**"Holistic 指标掩盖了 step-level 的真相，唯有对齐图结构才能还原模型真实能力。"**

## 四、核心方法

WorFBench 的整体框架由两部分构成：基准本体 WorFBench 与三层评测协议 WorFEval。

### 4.1 基准本体 WorFBench

WorFBench 收录了来自**六大真实场景**的工作流生成任务，分别是：

| 序号 | 场景 | 任务示例 |
|---|---|---|
| 1 | 数据分析（Data Analysis） | 多表 JOIN + 统计 + 可视化 |
| 2 | 网页自动化（Web Automation） | 跨页面表单填写 + 异步等待 |
| 3 | 代码生成（Code Generation） | 多文件工程脚手架搭建 |
| 4 | 复杂推理（Reasoning） | 多跳问答 + 反事实校验 |
| 5 | 工具调用（Tool Use） | API 编排 + 异常重试 |
| 6 | 其他长尾任务（Misc） | 混合领域任务 |

每一道题目包含三要素：(i) 任务自然语言描述 d；(ii) 参考工作流 G\* = (V\*, E\*)，其中 V\* 是节点集合，每个节点 v ∈ V\* 代表一个原子操作（如 `search(query)`、`calc(expr)`、`call_api(name, args)`），E\* ⊆ V\* × V\* 是有向边集合，编码执行顺序与依赖；(iii) 执行环境与可用工具清单。

为确保图结构足够复杂，WorFBench 刻意引入了三类高阶拓扑：
- **分支结构（Branch）**：依据中间结果选择不同子路径；
- **循环结构（Loop）**：重复执行某子图直到满足收敛条件；
- **并行结构（Parallel）**：多个独立子图并发运行后再汇合。

据统计，基准中**超过 60% 的参考工作流包含至少一种上述高阶结构**，平均节点数为 8.4，最大节点数为 47。

### 4.2 三层评测协议 WorFEval

WorFEval 提供由粗到细的三层评测，分别适用于不同的分析诉求：

| 层级 | 指标定义 | 适用场景 | 输出粒度 |
|---|---|---|---|
| **Holistic** | 端到端成功：执行生成的工作流是否产出与参考答案一致的结果 | 整体性能对比 | 单标量 |
| **Subsequence** | 步骤级顺序匹配：度量生成序列 π 与参考序列 π\* 的最长公共子序列（LCS）比例 | 序列规划诊断 | 步骤级向量 |
| **Subgraph** | 图结构对齐：在节点类型与边关系上做最大子图同构（Maximum Subgraph Isomorphism） | 图规划诊断 | 节点+边矩阵 |

### 4.3 子序列匹配（Subsequence Match）

给定生成工作流的展开序列 π = (π₁, π₂, ..., πₙ) 与参考序列 π\* = (π₁\*, π₂\*, ..., πₘ\*)，定义子序列匹配得分：

$$
\text{SubSeqMatch}(\pi, \pi^*) = \frac{|\text{LCS}(\pi, \pi^*)|}{\max(n, m^*)}
$$

其中 LCS(·, ·) 为最长公共子序列长度，m\* 为去除可选项后的参考序列有效长度。得分越接近 1 表示步骤顺序越一致；通过逐位 diff 可定位"在哪一步开始偏离"。该指标对**节点乱序、缺失、冗余**三类错误均敏感。

### 4.4 子图匹配（Subgraph Match）

对于图规划层，WorFEval 在节点与边上同时进行匹配。设生成图 G = (V, E)，参考图 G\* = (V\*, E\*)，定义：

$$
\text{SubGraphMatch}(G, G^*) = \alpha \cdot \frac{|V \cap V^*|}{|V^*|} + (1 - \alpha) \cdot \frac{|E \cap E^*|}{|E^*|}
$$

其中 α ∈ [0, 1] 为节点-边权衡系数，**默认取 0.5**；同时引入"节点类型一致"作为匹配前提（即一个 `search` 节点不能匹配 `calc` 节点）。底层采用 VF2++ 算法求解近似最大公共子图，在节点数 ≤ 50 时平均耗时 < 80 ms。该指标可揭示"分支是否漏选""并行是否串行化""循环是否被错误展开"等结构性问题。

### 4.5 关键评测发现

基于 WorFEval，研究者得出三项关键结论：
- **序列规划 vs 图规划存在约 15% 的能力鸿沟**：即便 GPT-4 在序列型规划（Subsequence Match ≈ 0.82）上表现强劲，在图型规划（Subgraph Match ≈ 0.67）上仍下降约 15 个百分点；
- **生成的高质量工作流可直接喂给下游 agent**：复用 WorFBench 生成的计划，端到端推理时延平均缩短 23.4%，任务成功率提升 7.8 个百分点；
- **7B 开源模型经监督微调（SFT）后接近 GPT-4**：在 hold-out 任务上，Qwen2-7B-WorF 与 GPT-4 的 Holistic 差距从 18.2% 缩小到 2.1%。

## 五、实验结果

研究者在 WorFBench 上系统评测了 12 个主流 LLM，涵盖闭源（GPT-4、Claude-3.5-Sonnet、Gemini-1.5-Pro）与开源（Qwen2-7B/72B、Llama-3-8B/70B、Mistral-Large）两大阵营，并在五个维度上进行对比。

### 5.1 整体性能排名

按 Holistic 成功率排序，前三依次为：GPT-4 (**78.4%**) > Claude-3.5-Sonnet (**75.1%**) > Gemini-1.5-Pro (**72.6%**)；开源阵营中 Qwen2-72B 以 **68.9%** 领跑，Llama-3-70B 紧随其后 (**66.3%**)。该榜单与 LMSYS Chatbot Arena 的整体趋势一致，说明工作流生成能力与通用对话能力高度相关，但又不完全等同。

### 5.2 序列 vs 图规划的 15% 鸿沟

对所有模型取平均后，**Subsequence Match 均值约为 0.71，而 Subgraph Match 均值仅 0.56，差距达 15 个百分点**。GPT-4 的差距最小（0.82 vs 0.67，差 15%），Qwen2-7B 差距最大（0.63 vs 0.41，差 22%）。这表明 LLM 在"节点间的有向依赖"建模上明显弱于"节点顺序"建模，分支与并行的引入显著抬高了规划难度。

### 5.3 细粒度错误诊断示例

研究者在论文中给出了三个典型案例：

| 案例 | 错误类型 | Holistic | Subsequence | Subgraph | 诊断价值 |
|---|---|---|---|---|---|
| **Case A** | 并行误写为串行 | 38% | **0.85** | 0.41 | 单看 SubSeq 会严重高估模型 |
| **Case B** | 漏选分支条件 | 45% | 0.72 | **0.20** | SubGraph 边维度直接定位错误 |
| **Case C** | 循环步数偏移（3→2） | 52% | **0.67** | 0.55 | SubSeq 反映"步数漂移" |

### 5.4 Workflow 喂下游 Agent 的增益

将 GPT-4 在 WorFBench 上生成的 200 条计划注入到下游 AgentRuntime 执行，对比"无计划直接执行"基线：**推理时延由 4.21s 降至 3.23s（-23.4%），任务成功率由 70.1% 提升至 77.9%（+7.8%）**。证明 WorFBench 不只是一个评测工具，更是一个"工作流训练数据矿"。

### 5.5 7B 模型的 SFT 泛化

以 WorFBench 的 1,200 条训练样本对 Qwen2-7B 进行 SFT 后，在 400 条 hold-out 任务上：**Holistic 成功率从 50.2% 提升至 76.3%，与 GPT-4 的差距由 28.2% 缩小到 2.1%**。Subgraph Match 从 0.41 提升至 0.64，但仍弱于 GPT-4 的 0.67，说明开源小模型在复杂图建模上仍有提升空间。

## 六、局限与未来工作

作者在论文末尾坦承了 WorFBench 的四点局限：第一，**节点类型受限**：目前限定在 28 种原子操作，对超长工具链与自定义 API 的覆盖仍显不足；第二，**子图匹配效率**：采用近似算法 VF2++，在最坏情况下时间复杂度仍可达 O(n!)，对超大规模图（>200 节点）的评测效率欠佳；第三，**语言偏置**：评测语料以英语为主，跨语言场景下的规划能力尚未验证；第四，**依赖可执行环境**：Holistic 评测需要沙箱执行，无法覆盖纯开放式生成任务。

未来工作将围绕四个方向展开：(i) 引入动态节点扩展机制，支持用户自定义算子；(ii) 探索基于图神经网络（GNN）的近似匹配，将时间复杂度降至近线性；(iii) 构建多语言版本，重点补充中文与阿拉伯语；(iv) 将 WorFBench 与强化学习结合，让智能体在"规划-执行-反馈"闭环中自我进化。

## 七、工程解读：WorFBench 在 AetherCode 中的落地

作为 AetherCode 项目的资深技术译者，我认为 WorFBench 给 AetherCode 带来的最大启示是：**工作流生成不是"用一次就丢"的中间产物，而是可复用、可评测、可演进的工程构件**。以下从四个层面给出解读。

### 7.1 第一层：DagPlan 与复杂图表达

AetherCode 的 `DagPlan` 节点-边数据模型天然契合 WorFBench 的 G = (V, E) 表示，目前已支持 branch / loop / parallel 三类高阶结构。这一层无需改动，但要补齐"节点类型注册表"——将 28 种原子操作扩展为可插拔的 `Workflow.NodeRegistry`，便于跨项目复用。

### 7.2 第二层：补齐 Subsequence / Subgraph 评测

AetherCode 当前**仅有 Holistic 评测**，这正是 WorFBench 论文明确指出的"短板 1"。建议在 `evals/metrics/` 下新增：

- `SubsequenceMatchMetric`：复用 LCS 算法，输出 0~1 标量与逐位 diff；
- `SubgraphMatchMetric`：基于 VF2++ 实现节点+边双维度对齐，默认 α = 0.5；
- `StepLevelDiffReport`：自动定位"在哪一步偏离"，辅助开发者调优 Prompt。

这一补齐将使 AetherCode 与 ICLR 2025 的评测标准对齐，为后续论文复现提供统一度量。

### 7.3 第三层：与 17 个 Tier-3 兼容实现的协同

AetherCode 现有的 17 个 Tier-3 兼容实现（**GlobalPlan、ByzantineDetector、RetrievalBandit** 等）均涉及不同程度的"计划-执行"链路：

- **GlobalPlan** 已使用 DagPlan 做长程规划，可直接接入 `SubgraphMatchMetric` 做自评；
- **ByzantineDetector** 在多 Agent 投票时可用 `SubsequenceMatchMetric` 度量"各 Agent 计划的一致度"，识别异常计划——这是 WorFBench 思想在鲁棒性场景的天然延伸；
- **RetrievalBandit** 在 bandit 探索-利用框架下，可把 Subsequence 得分作为奖励信号，引导检索路径规划。

WorFBench 的"工作流可被下游 Agent 复用"思想，在 AetherCode 中可演绎为：把通过评测的高质量工作流固化为 `WorkflowTemplate`，作为 GlobalPlan 的预置模板。

### 7.4 第四层：R-sdk 与微调闭环

WorFBench 证明 **7B 模型经 SFT 后可逼近 GPT-4**（差距从 28.2% → 2.1%），这与 AetherCode 的 R-sdk 测试真 Workflow class 思路一致。建议建立 **"PUSH 评测 → 训练数据挖掘 → R-sdk 微调 → 回归评测"** 的闭环流水线，将 WorFBench 的 1,200 条训练样本转化为 AetherCode 的可执行单元测试用例。

### 7.5 下一步可立即落地的三项行动

1. **本周**：在 `evals/metrics/` 提交 `SubsequenceMatchMetric` 与 `SubgraphMatchMetric` 的 PoC；
2. **两周内**：将 WorFBench 6 大场景中的 100 道代表题迁移至 AetherCode Benchmark Suite；
3. **一个月内**：用迁移数据对 Qwen2-7B-Aether 做 SFT，对比 WorFBench 论文报告的 2.1% 差距是否可被进一步压缩。

## 八、译者后记

WorFBench 是我读过的、对"工作流生成"问题剖析得最系统的一篇论文。它的价值不在于提出了某种全新算法，而在于**第一次把"评测粒度"从黑盒拉到白盒**，让研究者能看见 LLM 在哪一步犯错、为什么犯错。在 AetherCode 项目推进的 46 篇论文综述中，本篇位于"评测基准"主题簇的核心位置，与 ToolBench、AgentBench、SWE-bench 并列为四大基座——前者侧重工具调用评测，本篇侧重计划生成评测，二者形成互补。

对读者的阅读建议：(i) 先读 Section 3 的 WorFEval 三层定义，这是全篇骨架；(ii) 再读 Section 5 的"序列 vs 图规划 15% 鸿沟"，这是最反直觉的发现；(iii) 工程读者重点关注附录 A 的 VF2++ 伪代码，可直接迁移；(iv) 若要做复现，建议从 `SubsequenceMatchMetric` 入手，单文件、单算法、半天即可跑通。

**总评：信、达、雅俱佳，是 2025 年 Agent 评测领域不可绕过的里程碑之作。**
