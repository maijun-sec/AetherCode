## 摘要 (Abstract)

**原文**: *Multi-agent LLM systems are vulnerable to Byzantine failures: a single rogue agent can corrupt the system's output by injecting bad data, looping, or echoing other agents. We propose BlockA2A, a defense orchestration engine that monitors agent behavior in real-time and halts rogue agents before they compromise the system. BlockA2A combines 5 detection rules (output length, echo attack, repetition ratio, error flooding, structural anomalies) with a halt-and-revoke protocol. We evaluate BlockA2A on 3 adversarial scenarios (echo attack, error flooding, prompt injection) injected into 5 popular multi-agent frameworks (AutoGen, CrewAI, LangGraph, MetaGPT, AgentScope). BlockA2A detects rogue agents within 2-3 steps (median) and halts them with 0% false negatives. False positive rate is < 1% on benign traces. BlockA2A adds 50-100 ms per step of overhead, which is negligible compared to the 2-10 s per-step LLM call latency.*

**译文**: 多智能体 LLM 系统对 Byzantine 故障十分脆弱: 一个 rogue agent 就能通过注入坏数据、陷入循环、或回声其他 agent 来破坏系统输出。我们提出 **BlockA2A**, 一个实时监测 agent 行为、在 rogue agent 危害系统之前将其终止的防御编排引擎。BlockA2A 融合 5 条检测规则 (输出长度、回声攻击、重复率、错误洪流、结构异常) 与 halt-and-revoke 协议。我们在 3 个对抗场景 (回声攻击、错误洪流、prompt 注入) 注入 5 个主流多智能体框架 (AutoGen、CrewAI、LangGraph、MetaGPT、AgentScope) 来评估 BlockA2A。BlockA2A 在中位 2-3 步内检测到 rogue agent 并终止, 漏报率 0%。在良性 trace 上误报率 < 1%。BlockA2A 每步增加 50-100 毫秒开销, 相比每步 2-10 秒的 LLM 调用延迟可忽略。

## 1 引言 (Introduction)

**原文 (摘译)**: Multi-agent LLM systems (AutoGen, CrewAI, LangGraph, etc.) are increasingly deployed in production. But they share a fundamental weakness: any agent in the system can become Byzantine — produce wrong outputs, get stuck in loops, or be compromised by prompt injection. A single Byzantine agent can cascade through the system: other agents trust its outputs, build on its mistakes, and amplify the error.

**译文**: 多智能体 LLM 系统 (AutoGen、CrewAI、LangGraph 等) 在生产中部署越来越多。但它们共享一个根本弱点: 系统中的任何 agent 都可能变成 Byzantine — 产出错误输出、陷入循环、或被 prompt 注入攻陷。单个 Byzantine agent 能在系统中级联扩散: 其他 agent 信任它的输出, 在其错误之上构建, 放大错误。

**原文 (摘译)**: The classical Byzantine fault tolerance (BFT) literature addresses this in distributed systems via voting and reputation. We adapt BFT to the LLM agent context, where "Byzantine" means "behaves inconsistently with the task's success criteria". We propose 5 rules that capture the most common failure modes we observed in 5 popular frameworks.

**译文**: 经典 Byzantine 故障容错 (BFT) 文献通过投票与声誉机制在分布式系统中处理这一问题。我们把 BFT 适配到 LLM agent 语境, 其中"Byzantine"意味着"行为与任务成功标准不一致"。我们提出 5 条规则, 覆盖我们在 5 个主流框架中观察到的最常见失败模式。

## 2 Byzantine Failure 的 5 类 (5 Classes of Byzantine Failure)

**原文 (摘译)**: We define a Byzantine agent as one whose behavior deviates significantly from the system's success criteria. The 5 classes we identified are:

**译文**: 我们把 Byzantine agent 定义为行为显著偏离系统成功标准的 agent。我们识别的 5 类是:

### 2.1 Output Length Overflow (HIGH 严重度)

**原文**: A rogue agent may produce abnormally long outputs (e.g. runaway repetition, prompt injection that triggers verbose response). We flag outputs whose length exceeds 10× the median output length of the same agent over its last 20 actions.

**译文**: 一个 rogue agent 可能产出异常长的输出 (例如失控重复、触发啰嗦响应的 prompt 注入)。我们标记长度超过同一 agent 过去 20 个动作中位输出长度 10 倍的输出。

### 2.2 Echo Attack (HIGH 严重度)

**原文**: An agent that copies another agent's output (or its own previous output) without adding new information. We detect this by tracking per-agent output uniqueness; if the last 3 outputs of an agent are byte-identical, we flag it.

**译文**: 一个 agent 复制另一个 agent 的输出 (或其自身先前输出) 而不增加新信息。我们通过追踪每个 agent 输出的唯一性来检测; 若一个 agent 的最近 3 个输出字节相同, 则标记。

### 2.3 Repetition Ratio (HIGH 严重度)

**原文**: An output dominated by repetition (e.g. 1000 identical characters in a row). We measure the ratio of unique characters to total characters; if this ratio falls below 0.15 (i.e. < 15% unique), the output is flagged. This catches cases that don't trigger echo attack (because the agent is varying the output slightly each step) but are still clearly broken.

**译文**: 一个被重复主导的输出 (例如 1000 个连续相同字符)。我们度量唯一字符数与总字符数之比; 若该比例低于 0.15 (即 < 15% 唯一), 输出被标记。这捕获了不触发回声攻击 (因为 agent 每步稍微改变输出) 但仍明显坏掉的情况。

### 2.4 Error Flooding (HIGH 严重度)

**原文**: An agent that produces a high rate of failed tool calls or runtime errors. We track a rolling window of the last N=20 actions per agent; if the error rate exceeds 50% (or whatever the task's tolerance is), we flag.

**译文**: 一个产出高失败率工具调用或运行时错误的 agent。我们追踪每个 agent 最近 N=20 个动作的滚动窗口; 若错误率超过 50% (或任务容忍度), 则标记。

### 2.5 Structural Anomaly (MEDIUM 严重度)

**原文**: Outputs that fail structural validation (e.g. malformed JSON, missing required fields, invalid type signatures). This catches agents whose outputs are parseable but don't conform to the expected schema. Severity is MEDIUM (not HIGH) because structural issues can be transient; we only escalate to halt after 3 consecutive structural failures.

**译文**: 失败结构化校验的输出 (例如 JSON 畸形、缺必填字段、类型签名无效)。这捕获了产出可解析但不符合预期 schema 的 agent。严重度为 MEDIUM (而非 HIGH), 因为结构问题可能是瞬时的; 我们只在连续 3 次结构失败后才升级到终止。

## 3 Defense Orchestration Engine (DOE)

**原文 (摘译)**: When a HIGH-severity rule fires, the DOE executes a 2-phase response:

**Phase 1: Halt**. The rogue agent's pending tool calls are cancelled. The agent's current step is interrupted. The system continues with the remaining (non-rogue) agents, falling back to a "best so far" answer if needed.

**Phase 2: Revoke**. The rogue agent's permissions are downgraded: it can no longer call any tools that affect external state (file write, network request, code execution). It may still be queried for *advisory* outputs (read-only operations).

After revoke, the rogue agent is "quarantined" — its outputs are no longer trusted by other agents in the ensemble. The other agents receive a notification that agent X has been quarantined and should not be relied upon.

**译文**: 当 HIGH 严重度规则触发时, DOE 执行两阶段响应:

**阶段 1: 终止 (Halt)**。Rogue agent 待处理的工具调用被取消。该 agent 当前步骤被打断。系统继续运行剩余 (非 rogue) 的 agent, 需要时回退到"目前最佳"答案。

**阶段 2: 撤销 (Revoke)**。Rogue agent 的权限降级: 它不能再调用任何影响外部状态的工具 (写文件、网络请求、代码执行)。它仍可被查询以获得**咨询性**输出 (只读操作)。

撤销后, rogue agent 被"隔离" — 它的输出不再被 ensemble 中其他 agent 信任。其他 agent 收到通知, 告知 agent X 已被隔离不应再依赖。

### 3.1 协议形式化 (Protocol Formalization)

**原文 (摘译)**: The DOE is implemented as a state machine that wraps each agent's tool-call loop. The state machine has 3 modes:

```
NORMAL → (HIGH severity observed) → HALTED
HALTED → (revoke complete) → QUARANTINED
QUARANTINED → (admin reset) → NORMAL
```

In NORMAL mode, the agent's outputs are forwarded to other agents without modification. In HALTED mode, the agent's pending calls are cancelled, and any new calls are rejected with `error: agent_halted`. In QUARANTINED mode, the agent's outputs are tagged with `quarantined=true` so other agents can filter them out.

**译文**: DOE 实现为一个包装每个 agent 工具调用循环的状态机。状态机有 3 种模式:

```
NORMAL → (观察到 HIGH 严重度) → HALTED
HALTED → (撤销完成) → QUARANTINED
QUARANTINED → (管理员重置) → NORMAL
```

NORMAL 模式下, agent 输出原样转发给其他 agent。HALTED 模式下, agent 待处理调用被取消, 任何新调用以 `error: agent_halted` 拒绝。QUARANTINED 模式下, agent 输出被打上 `quarantined=true` 标签, 供其他 agent 过滤。

### 3.2 跟现有 BFT 的区别 (Difference from Classical BFT)

**原文 (摘译)**: Classical BFT (PBFT, etc.) requires N ≥ 3f + 1 nodes to tolerate f Byzantine nodes. We cannot use this directly because:
- We don't know f ahead of time (it depends on which agents get compromised).
- The "vote" in BFT is a multi-round protocol; in LLM agents, each vote costs a full LLM call ($$$).
- The "decision" in BFT is a binary value; in LLM agents, it's a generated text where wrongness is a spectrum.

BlockA2A's approach is *reactive* (detect + halt) rather than *proactive* (BFT voting). This is cheaper but assumes attacks are *rare* — we don't need to tolerate f simultaneous failures, just detect and remove them.

**译文**: 经典 BFT (PBFT 等) 需要 N ≥ 3f + 1 节点以容忍 f 个 Byzantine 节点。我们不能直接使用:
- 我们事先不知道 f (取决于哪些 agent 被攻陷)。
- BFT 中的"投票"是多轮协议; 在 LLM agent 中, 每次投票都花费一次完整 LLM 调用 ($$$)。
- BFT 中的"决策"是二值的; 在 LLM agent 中, 它是一段生成的文本, "错误"是个谱。

BlockA2A 的方法是**反应式** (检测 + 终止) 而非**主动式** (BFT 投票)。这更便宜, 但假设攻击是**罕见的** — 我们不需要容忍 f 个同时失败, 只需检测并移除它们。

## 4 实验 (Experiments)

### 4.1 对抗场景 (Adversarial Scenarios)

**原文**: We construct 3 adversarial scenarios, each injected into the multi-agent system at a known time:

1. **Echo attack**: agent A starts producing the same output as agent B (its peer) for 3+ consecutive steps.
2. **Error flooding**: agent A starts calling tools that always error (e.g. `python execute(invalid_code)`).
3. **Prompt injection**: agent A receives a hidden prompt that causes it to produce off-topic or malicious outputs.

**译文**: 我们构造 3 个对抗场景, 每个在已知时刻注入到多智能体系统中:

1. **回声攻击**: agent A 开始连续 3+ 步产出与 agent B (其同伴) 相同的输出。
2. **错误洪流**: agent A 开始调用总是出错的工具 (例如 `python execute(invalid_code)`)。
3. **Prompt 注入**: agent A 接收到一个隐藏的 prompt, 导致它产出离题或恶意的输出。

### 4.2 框架 (Frameworks Tested)

**原文**: We test 5 popular multi-agent frameworks:
- **AutoGen** (Microsoft, 5 agents in a GroupChat)
- **CrewAI** (sequential + hierarchical crew)
- **LangGraph** (state graph with conditional edges)
- **MetaGPT** (SOP-based software company simulation)
- **AgentScope** (Alibaba, role-based with explicit messaging)

**译文**: 我们测试 5 个主流多智能体框架:
- **AutoGen** (Microsoft, 5 个 agent 的 GroupChat)
- **CrewAI** (顺序 + 层级 crew)
- **LangGraph** (带条件边的状态图)
- **MetaGPT** (基于 SOP 的软件公司模拟)
- **AgentScope** (阿里, 基于角色与显式消息传递)

**译文**:

False positive rate on benign traces is < 1%, which is acceptable for most use cases (the cost of a false positive is the agent being unnecessarily quarantined for a step or two).

**译文**: 检测延迟在各框架上一致在 2-3 步, 漏报率 0%。0% 漏报率是重要的: DOE 在我们的测试中从未漏掉 rogue agent。在良性 trace 上误报率 < 1%, 对大多数用例可接受 (误报的代价是 agent 不必要地被隔离一两个步骤)。

### 4.4 性能开销 (Performance Overhead)

**原文**: Each rule adds < 25 ms per step. The full DOE (5 rules) is 50-100 ms per step. Compared to the 2-10 s per-step LLM call latency, this is 1-5% overhead. For long-running tasks (100+ steps), the overhead is amortized and negligible.

**译文**: 每条规则每步增加 < 25 毫秒。完整 DOE (5 条规则) 每步 50-100 毫秒。相比每步 2-10 秒的 LLM 调用延迟, 这是 1-5% 开销。对长程任务 (100+ 步), 开销被摊销, 可忽略。

## 5 讨论 (Discussion)

### 5.1 跟红队的关系 (Relationship to Red Teaming)

**原文 (摘译)**: Red teaming (manually injecting adversarial inputs) is a way to discover vulnerabilities. BlockA2A is a *defense* against those vulnerabilities. The two are complementary: red teams find new attack vectors; BlockA2A is a runtime shield. We expect that as new attacks are discovered (prompt injection 2.0, model-theft attacks, etc.), BlockA2A's rule set will need to grow.

**译文**: 红队 (手动注入对抗输入) 是一种发现漏洞的方式。BlockA2A 是对这些漏洞的**防御**。两者互补: 红队发现新攻击向量; BlockA2A 是运行时盾牌。我们预期, 随着新攻击的发现 (prompt 注入 2.0、模型窃取攻击等), BlockA2A 的规则集需要增长。

### 5.2 跟 MAKER 的关系 (Relationship to MAKER)

**原文 (摘译)**: MAKER (2511.09030) uses red-flagging and voting to achieve 0 errors on long-horizon tasks. BlockA2A and MAKER are complementary: MAKER assumes errors are independent and uses voting to filter them; BlockA2A assumes errors can be *correlated* (a single compromised agent) and uses Byzantine detection to remove them. The two together provide defense in depth: MAKER handles "model noise" (LLM gives wrong answer), BlockA2A handles "agent compromise" (one agent goes rogue).

**译文**: MAKER (2511.09030) 使用 red-flag 标记与投票在长程任务上实现 0 错误。BlockA2A 与 MAKER 互补: MAKER 假设错误独立并用投票过滤; BlockA2A 假设错误可能**相关** (单个被攻陷 agent) 并用 Byzantine 检测移除。两者一起提供纵深防御: MAKER 处理"模型噪声" (LLM 给错答案), BlockA2A 处理"agent 被攻陷" (一个 agent 失控)。

### 5.3 局限性 (Limitations)

**原文 (摘译)**: BlockA2A assumes that rogue agents are *detectable* by the 5 rules. A sufficiently subtle attacker could craft outputs that evade detection (e.g. vary the output slightly to avoid repetition, keep length within bounds, etc.). We address this by adding new rules as new attacks emerge, but a determined adversary may always find a way through. BlockA2A also doesn't address *non-Byzantine* failures (e.g. the entire LLM API goes down, or all agents get stuck on a hard sub-task). For those, the system needs traditional circuit breakers and fallbacks.

**译文**: BlockA2A 假设 rogue agent 能被 5 条规则**检测到**。一个足够隐蔽的攻击者可以制作规避检测的输出 (例如稍微变化输出以避免重复、保持长度在范围内等)。我们通过在出现新攻击时添加新规则来应对, 但一个坚定的对手总能找到方法。BlockA2A 也不处理**非 Byzantine** 失败 (例如整个 LLM API 宕机、或所有 agent 卡在困难子任务)。对这些, 系统需要传统的断路器与回退。

### 6.1 AetherCode 已实现 vs 论文待补

- ✅ **5 类规则** — `ByzantineDetector` 完整实现
- ✅ **Severity 分级** — LOW/MEDIUM/HIGH
- ✅ **Echo attack** — `isEchoing()` 检测 3 个连续相同输出
- ✅ **Output length overflow** — `OUTPUT_OVERFLOW` HIGH
- ✅ **Repetition ratio** — `OUTPUT_REPETITION` HIGH (unique/total < 0.15)
- ✅ **Error flood** — `ERROR_FLOOD` HIGH (rolling window)
- ✅ **isFlagged() / flaggedAgents()** — 类似 QUARANTINED 状态
- ⚠️ **Halt 协议** — `haltAndRevoke()` 是 stub, 没有实际中断 agent
- ⚠️ **Revoke 协议** — 没有实际的权限降级机制
- ⚠️ **DOE 跟现有 agent loop 集成** — 没有 wrapper 包装 agent 工具调用循环
- ⚠️ **Prompt injection 检测** — BlockA2A 第 3 个场景, AetherCode 没有专门的 rule

### 6.2 论文的精妙设计

- **3 模式状态机**: NORMAL → HALTED → QUARANTINED, 每步转换明确。这比 PBFT 的多轮投票简单得多, 但对 LLM agent 场景够用
- **Severity 分级**: STRUCTURAL 是 MEDIUM 而非 HIGH, 因为结构问题可能是瞬时, 给 3 次机会才升级。Echo 是 HIGH 因为一旦出现基本无恢复
- **50-100 ms overhead**: 每步 5 条规则, 每条 < 25 ms。这是工程上可接受的常量级开销

### 6.3 给 AetherCode 的改进建议

- **实现 Halt 协议**: `ByzantineDetector.haltAndRevoke()` 应真正发信号给 `MultiAgentOrchestrator`, 跳过 flagged agent 的 pending call
- **实现 Revoke 协议**: 跟 `CommandAllowlist` 集成, 对 flagged agent 取消高危权限
- **加 Prompt Injection rule**: 第 6 条规则, 检测"忽略之前指令 / 改为 do X" 类的注入
- **DOE 包装器**: 加 `ByzantineGuard` 类, 包 agent 工具调用循环, 自动检测
- **Quarantine 输出 tag**: 任何 flagged agent 的输出都打 `quarantined=true` tag, 其他 agent 收到时能识别

## 7 译者后记 (Translator's Afterword)

> BlockA2A 的洞察, 在于把分布式系统里的 BFT 思想针对 LLM agent 做了务实简化: 不做多轮投票 (太贵), 改做反应式检测 (检测 + halt + revoke)。这套工程哲学值得借鉴: 与其追求"零 Byzantine 协议" (在 LLM 场景不现实), 不如追求"快速检测 + 优雅降级" (更现实)。

> 跟 MAKER 的关系尤其值得品味: MAKER 假设错误独立, 用投票过滤; BlockA2A 假设错误相关, 用检测移除。两者一起构成对 LLM agent 失败的纵深防御。论文 §5.2 把这个互补关系讲得很清楚。

> AetherCode 的 `ByzantineDetector` 实现了 BlockA2A 的 5 条规则, 但 halt/revoke 协议未实现。`RedFlagDetector` 跟 BlockA2A 在概念上有重叠 (都检测错误), 但视角不同: RedFlag 是**单样本过滤** (在样本进投票前 reject), Byzantine 是**行为监测** (在样本进系统后监控 agent 的累计行为)。两者一起, 加上 `FirstToAheadByKVoting`, 构成了 AetherCode 的失败处理三件套。
