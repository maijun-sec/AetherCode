# R182 — React #310 修复 (2026-09-01)

## 1. 背景

R180 错误边界**工作了**——用户看到红色错误卡片替代"白板"。R181 后端修复也工作了——模型能发出
`cd /d D:\tmp\abc_1 && dir` 这种以前会被 R98 误判 DELETE 的诊断命令。

但 R180 红色卡片里的真错误是 **React error #310**："Rendered more hooks than during the previous render"。
这是**真正**导致 v0.2.28 白板的原因——R179 修的是用户消息被吞的 race，但白板的实际触发是 React hooks 顺序违规，
只是没有 ErrorBoundary 兜底所以没人看到。R180 让错误可见，R182 修根因。

## 2. 根因

`src/components/MessageList.tsx` 的 `PreparingCard` 函数有经典 React #310 bug：

```tsx
function PreparingCard({ steps, ... }) {
  const [expanded, setExpanded] = useState(false);     // hook 1
  const subTasks = useStore((s) => s.subTasks);          // hook 2
  const cancelQuery = useStore((s) => s.cancelQuery);   // hook 3

  if (steps.length === 0) return null;                  // ← 提前返回

  // ... 一些非 hook 的计算 ...

  const [elapsedSec, setElapsedSec] = useState(...);    // hook 4  (条件性!)
  useEffect(() => { ... }, [isStreaming, startedAt]);   // hook 5  (条件性!)

  // ... 渲染
}
```

**问题**：当 `steps.length` 在 0 和 >0 之间跳变（模型发一个新 tool step 时），
React 看到的 hook 数量从 3 变成 5——`Rendered more hooks than during the previous render` → React #310。

这种情况在每次模型发新 step 都会触发，所以 chat 列表会反复崩。

## 3. 修复

把所有 hooks 移到 early return 之前。`steps.length === 0` 仍然 return null，但 React 看到的
hook 数量始终是 5（不变）。

```tsx
function PreparingCard({ steps, ... }) {
  // R182: ALL hooks first, no early return between them.
  const [expanded, setExpanded] = useState(false);
  const subTasks = useStore((s) => s.subTasks);
  const cancelQuery = useStore((s) => s.cancelQuery);
  const startedAt = steps[0]?.startedAt ?? Date.now();
  const [elapsedSec, setElapsedSec] = useState(() => Math.floor((Date.now() - startedAt) / 1000));
  useEffect(() => { ... }, [isStreaming, startedAt]);

  if (steps.length === 0) return null;  // ← return AFTER all hooks
  // ...
}
```

`startedAt` 用 `steps[0]?.startedAt ?? Date.now()` 兜底，useEffect 不会因为 `steps.length === 0` 而出错
（isStreaming 仍然是 `false` 时不调 setInterval）。

## 8. 教训 (2026-09-01)

1. **错误边界是发现 React bug 的眼睛**——没有 R180 的 ErrorBoundary，R182 这个 bug 可能还会潜伏很久
   （表现为"白板"被误诊为"R179 没修对 race"）。R180 让 R182 浮出水面，这是两层修复的关系。
2. **React hooks 顺序规则容易在 R177 这类"加新功能"时被破坏**。R177 加了 useState + useEffect
   给 PreparingCard 加计时器，但当时已经有个 `if (steps.length === 0) return null;` 在前。
   新加的 hooks 自然落在了 early return 之后。教训：**任何"加新 hook"必须先看现有 early return 位置**。
3. **"白板"诊断链**：R180 (ErrorBoundary) → 看到 React #310 → 找到 PreparingCard → 修复 hooks 顺序。
   这是完整的"防御 → 诊断 → 修复"链路。R179 (race fix) + R180 (boundary) + R181 (backend) + R182 (React) 是
   "白板"的完整解决方案。
4. **source-pin test 在修复"代码气味"时特别合适**——hooks-after-early-return 是种"refactor
   容易破坏的契约"，grep-based 测试能防止"未来某天又有人加新 hook 在 early return 之后"。
