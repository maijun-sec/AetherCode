# ERL：面向自改进 LLM Agent 的体验反思学习 (arXiv:2603.24639)

## 一、标题与作者

- **原文标题**：ERL: Experiential Reflective Learning for Self-Improving LLM Agents

## 二、一句话摘要

反思单次轨迹生成可迁移启发式,选择性检索驱动 LLM Agent 实现免训练环境适应。

## 三、背景与动机

近年来,以大语言模型(LLM)为大脑的智能体(Agent)在复杂推理与多步问题求解任务上取得了显著进展。从 ReAct 的"推理—行动"交替范式,到 Toolformer 的工具调用,再到 Reflexion 的反思增强,Agent 系统的能力边界被不断向外拓展。然而,一个长期被工程团队忽视的痛点是:**大多数 LLM Agent 难以适应专门环境,且不会从过去的交互中真正获益**——每一次新任务都像新入职的员工一样从零开始,既不记得上周踩过的坑,也不会主动复用上个月总结出的工作流。

这种"金鱼式"的工作模式带来了三个具体问题。其一,**部署成本居高不下**:同样的环境陷阱会在无数次执行中反复消耗 token;在企业级 codebase、API 文档、SQL schema 等专门场景下,Agent 往往因为反复触发同一个错误模式而累积惊人的算力开销。其二,**迁移能力薄弱**:擅长检索的 Agent 不会因为在某个 codebase 上失败过几次就自动学会调试,擅长调用工具的 Agent 也不会因为重复遇到同一个工具的 4xx 错误就形成避坑直觉。其三,**长尾任务几乎无法收敛**:稀有错误没有积累成可复用的经验,导致每次遇到都重新试探,系统在边缘案例上几乎不可能达到稳定 SLA。

针对上述痛点,已有工作大致沿着两条路径展开。**参数化方法**(如 fine-tuning、RLHF、PPO)将经验固化进模型权重,代价是高昂的算力开销与灾难性遗忘风险,且每次环境变化都要重训;**非参数化方法**(如 ExpeL、AutoGuide、AutoMem)在外部 memory 中保留 raw trajectory 或配对轨迹,代价是 prompt 膨胀、检索噪声、上下文窗口过载。**ERL 的切入点是第三条路——反思后抽象**(reflective abstraction):把 trajectory 压缩成可迁移的启发式规则(heuristics),并通过 LLM 评分实现 selective retrieval,既避免参数更新,又规避 prompt 爆炸。

这一动机与 Illuin Technology 作为工业级 Agent 服务商的定位高度一致:生产环境需要的是"开箱即用、随用随学"的轻量级自改进机制,而非依赖大规模重训的重资产方案。ERL 的出现正好回应了这一诉求。

## 四、核心方法

### 4.1 整体框架

ERL 的运行周期由两个阶段构成:**经验沉淀阶段**(offline,可在异步流水线中执行)与**经验调用阶段**(test time,同步生效)。

在经验沉淀阶段,Agent 完成一次任务后会得到一条完整轨迹:
$$\tau = (s_0, a_0, s_1, a_1, \ldots, s_n)$$
其中 $s_i$ 表示第 $i$ 步的环境状态(observation),$a_i$ 表示 Agent 产生的动作(action),$s_n$ 是终态。**ERL 不要求配对(paired)或多轮(rollouts)轨迹——单次 attempt 的轨迹即可作为反思素材**。反思器(reflector,通常由同一个 LLM 扮演)对 $\tau$ 与最终 outcome 进行自然语言总结,得到反思文本 $R$,并从中抽取若干条启发式规则:
$$h_j = \mathrm{extract}(R), \quad j = 1, \ldots, m$$
每条 $h_j$ 在存储时附带两个字段:`rule`(规则正文,例如"当工具返回 4xx 时,优先检查参数 schema 而非重试")与 `applicability`(适用条件,例如"适用:任意 REST API 调用场景")。最终落库到全局经验库:
$$\mathcal{H} = \{h_1, h_2, \ldots, h_N\}$$
$N$ 随时间单调增长,需要配套的去重与版本治理机制(见第六节)。

在经验调用阶段,给定新任务 $T$,**ERL 不直接拼接所有历史启发式**——这正是 ExpeL 暴露的可扩展性瓶颈。取而代之的是调用 LLM 作为评分器,对 $\mathcal{H}$ 中每条 $h_i$ 计算与 $T$ 的相关性分数:
$$s_i = f_{\mathrm{score}}(T, h_i)$$
随后依据分数选取 top-k 条:
$$\mathcal{H}_T = \mathrm{top}\text{-}k(\{s_i\}_{i=1}^{N})$$
将 $\mathcal{H}_T$ 注入 Agent context,引导其执行当前任务。整个过程**不更新任何模型参数**,属于纯 in-context learning,因此部署成本接近零,且对底层模型无侵入。

### 4.2 关键设计选择

**(a) 启发式而非原始轨迹(Heuristics > raw trajectories)**:与 AutoMem(arXiv:2607.01224)保留 granular trajectory 细节不同,ERL 选择向上抽象一层,产出可跨任务复用的规则文本。两者并非互斥而是互补:heuristics 提供 general guidance,trajectories 提供 specific 案例。在生产中可按需混合使用,例如先由 heuristics 给出宏观方向,再由少量 trajectory 作为示范。

**(b) 单次 attempt 即可(Single-attempt trajectories are enough)**:不同于 ExpeL / AutoGuide 要求 paired trajectories 或多次 rollouts,ERL 在工程上把"反思—抽取"的成本压到单次 trajectory 级别,适合 production 部署中"每条样本都贵"的现实约束。

**(c) 选择性检索至关重要(Selective retrieval is critical)**:通过 LLM 对 stored heuristics 逐条打分并选 top-k,从根本上解决了"全部塞进 prompt"导致的上下文爆炸与噪声放大问题。这一思想把检索从"被动相似度匹配"升级为"主动相关性判断",更接近人类在新任务前主动调用相关记忆的工作方式。

### 4.3 与 AetherCode 现有实现的映射

下表给出 ERL 核心观点与 AetherCode 现有 Tier-3 兼容实现的对应关系,可作为后续工程落地的 checklist:

| ERL 核心观点 | 现有 Tier-3 实现 | 状态 |
|---|---|---|
| Reflection → heuristics | `MemoryCriticAgent`(KEEP/PRUNE/REWRITE) | heuristic generation 缺失 |
| Selective retrieval(LLM-scored) | `ProceduralMemory`(R-paper-batch5) | scored retrieval 未实现 |
| Single-attempt trajectory 也能用 | — | 是约束,现有实现可能依赖 multi-rollout |
| +7.8% 提升 vs ReAct | — | AetherCode baseline 待测 |

### 4.4 待补 Tier-3 候选(本论文衍生)

基于 ERL 的设计,AetherCode 可考虑新增以下三个模块:

- **`HeuristicExtractor`**:从 trajectory 反思提取 heuristics,输出 `rule + applicability` 二元组,作为 `MemoryCriticAgent` 的下游。
- **`ScoredMemoryRetrieval`**:LLM 评分相关性的 top-k 检索,替代或叠加于 `ProceduralMemory` 的向量相似度召回。
- **`SingleAttemptReflection`**:单次 attempt → heuristic 流程封装,降低对 multi-rollout 的依赖,直接对接生产 trace。

## 五、实验结果

ERL 在 **Gaia2 benchmark** 的 Search 与 Execution 两个 split 上进行了系统评测。基线选择 ReAct——LLM Agent 领域事实上的标准对照,几乎所有后续工作都以其为锚点。

**主结果**:在 Gaia2 整体成功率指标上,ERL 相对 ReAct baseline 取得 **+7.8%** 的绝对提升。这一数字看似温和,但在 LLM Agent benchmark 边际收益持续衰减的当下,7.8% 已经属于显著增益——以同期 SOTA 工作通常在 +1% 到 +3% 区间徘徊为参照,ERL 的提升幅度足以重排排行榜前列。同时,论文强调该提升**大幅改善了任务完成可靠性**,即从"偶尔成功"向"稳定可复现"过渡,这一点对生产环境部署比绝对分数更关键——一个成功率从 60% 提升到 67.8% 的 Agent,在 1 万次调用级别上意味着从 4000 次失败降到 3220 次失败,运维意义远超统计显著性。

**横向对比**:ERL 在体验学习(experiential learning)子类内**超过了先前方法**。具体而言,与 ExpeL、AutoGuide、AutoMem 等相比,ERL 在相同或更少轨迹数据量下达到了更高的最终成功率,验证了"反思—抽象"路线的优越性。这一结果呼应了论文的核心主张:抽象层级(abstraction level)而非数据量,才是经验迁移的关键变量。

**消融实验**揭示了两个关键发现:

1. **选择性检索至关重要**(Selective retrieval is critical)。一旦关闭 top-k 过滤、把全部 heuristics 串入 prompt,成功率出现显著下滑。这从实证层面印证了 ExpeL 范式在长尾经验库上的不可扩展性,也提示任何沿 ERL 思路扩展的工作都必须保留 selective retrieval 模块。
2. **启发式比 few-shot trajectory prompting 更可迁移**。当把存储内容由抽象规则替换为原始轨迹并采用相同检索策略后,模型在分布外(out-of-distribution)任务上的泛化能力明显下降。这进一步说明:**抽象层级才是经验迁移的关键变量,而非数据本身**。

| 消融维度 | 配置 | 相对 ReAct 增益 |
|---|---|---|
| 完整 ERL | reflection + heuristics + selective retrieval | **+7.8%** |
| 无 selective retrieval | 所有 heuristics 串入 prompt | 增益显著回落(具体数值论文未单列) |
| 用 trajectory 替换 heuristics | few-shot trajectory prompting | 增益回落,分布外泛化更差 |

此外,论文还观察到 **heuristic 库的规模并非越大越好**:当 N 超过一定阈值后,即使有 selective retrieval,top-k 中也会混入大量低质量早期规则,提示需要配套的去重/版本治理机制。

## 六、局限与未来工作

尽管 ERL 在 Gaia2 上表现稳健,论文与我们的二次审视共同指向三方面局限。

其一,**启发式抽取质量高度依赖底层 LLM 的反思能力**。弱模型可能产出无意义或有害规则,例如"如果失败就放弃"这类恒真但无指导意义的规则;强模型也可能因幻觉产生看似合理但实际错误的 heuristic。在生产中需要引入二次质检机制。

其二,**评估者—执行者耦合风险**。当前 scoring 函数直接复用同一 LLM,该 LLM 既生成 heuristic 又评估 heuristic 相关性,存在系统性偏差。生产中可考虑使用异质 LLM 做交叉评分,或引入 Critic-in-the-loop。

其三,**heuristic 库随时间增长的去重与版本治理**问题未充分讨论。当 N 持续增长,规则之间会出现冲突(如"重试三次"与"遇到 4xx 立即放弃"),或出现大量同义改写,导致检索效率下降与 top-k 信噪比恶化。

未来工作可朝三个方向延伸:引入 Critic-in-the-loop 对 heuristics 做二次质检与冲突消解;支持 heuristic 之间的组合(composition)与优先级排序;以及把 selective retrieval 与 `RetrievalBandit` 等 AetherCode 现有模块联调,实现基于反馈信号的检索策略在线优化。

## 七、工程解读

把 ERL 的思想映射回 AetherCode 现有的 17 个 Tier-3 兼容实现,可以看到几条清晰的落地路径。

**已被借鉴的设计**:`MemoryCriticAgent` 已经在做 KEEP/PRUNE/REWRITE 三态裁决,这是 ERL "reflection → heuristic" 思想的雏形——区别只在于 ERL 的输出是新建规则,而当前 `MemoryCriticAgent` 是对已有 memory 做分类维护。两者完全可融合:让 `MemoryCriticAgent` 在 PRUNE 失败时触发 `HeuristicExtractor`,把失败模式沉淀为新 heuristic,实现"判废—生新"的端到端闭环。

**与 `ProceduralMemory` 的耦合**:R-paper-batch5 中的 `ProceduralMemory` 目前依赖向量相似度召回,与 ERL 的 LLM 评分方式形成互补。生产中可考虑 hybrid 方案:先用 embedding 做粗筛(取前 20%),再用 LLM 评分做精排(取 top-k),兼顾效率与相关性。这一两阶段流水线也避免了每条 heuristic 都触发一次 LLM 调用的成本焦虑。

**与 `GlobalPlan` 的协同**:`GlobalPlan` 解决的是"长程任务怎么拆",ERL 解决的是"踩过的坑下次怎么避"。两者结合可形成完整的闭环:`GlobalPlan` 负责前瞻式规划,ERL 的 heuristics 负责回溯式避坑。在 AetherCode 的任务执行器中,可在 `GlobalPlan` 节点展开后、`ByzantineDetector` 节点裁决前注入 `HeuristicExtractor` 与 `ScoredMemoryRetrieval`。

**与 `ByzantineDetector` 的可能联动**:heuristic 库可能引入噪声规则(等价于 Byzantine fault),`ByzantineDetector` 的统计异常检测能力天然适合对 heuristics 做信誉评分,标记那些在多次调用中效果不佳的规则并降权。这一组合可同时解决 ERL 的局限性二(评估者偏差)与局限性三(库规模治理)。

**与 `RetrievalBandit` 的闭环**:`RetrievalBandit` 的 bandit 信号天然适合作为 `ScoredMemoryRetrieval` 的在线反馈:每条被检索出的 heuristic 在执行后获得的 success/fail 信号回流到 bandit,bandit 据此调整未来的检索权重,实现"检索—执行—反馈—调权"的完整在线学习闭环。

**可立即做的下一步**:

1. 在 `MemoryCriticAgent` 中接入 `HeuristicExtractor` 子流程,产出 `rule + applicability` 二元组。
2. 把 `ScoredMemoryRetrieval` 作为新模块独立实现,先用 GPT-4 级模型做 scoring,后续蒸馏到小模型以降低成本。
3. 在 AetherCode 现有 ReAct baseline 上跑 Gaia2 Search + Execution split,获得可比的 +7.8% 增益基线,完成论文结果的可复现验证。
4. 用 `SingleAttemptReflection` 替代现有 `MultiRolloutReflection`,降低 50% 以上的轨迹成本。
5. 把 `RetrievalBandit` 的 bandit 信号反馈给 `ScoredMemoryRetrieval`,实现 heuristic 检索的在线学习。

需要警惕的是,ERL 的成功部分归功于 Gaia2 这一相对友好的环境分布;在 adversarial 或分布剧变的场景下,heuristic 库可能反而成为负担。建议在引入 ERL 类机制时,同时保留 fallback 到 `MemoryCriticAgent` REWRITE 状态的兜底路径,并对 heuristic 库设置最大容量上限(例如 N ≤ 500)与定期 GC 策略。

## 八、译者后记

作为 AetherCode 项目 46 篇论文综述的译者之一,我把 ERL 定位为"体验学习方向的实用主义范式":它没有追求最复杂的强化学习路线,也没有堆砌最庞大的 memory 库,而是用最朴素的 reflection + selective retrieval 组合,在 Gaia2 上取得了 +7.8% 的稳健提升。这种"少即是多"的工程哲学,与 AetherCode 一贯倡导的 Tier-3 兼容性原则高度契合——每一个新模块都应该能以最小侵入的方式融入现有 17 个 Tier-3 实现,而非推倒重来。

在 46 篇论文的谱系中,ERL 与 AutoMem(粒度保留)、ExpeL(配对轨迹)、AutoGuide(反思增强)共同构成体验学习的四象限。ERL 占据"抽象 + 单次 attempt"这一在工业落地中常被低估的角落。读者若时间有限,可优先阅读本文第 4 节核心方法与第 7 节工程解读,前者厘清算法骨架,后者直接对接 AetherCode 现有模块,可在 30 分钟内形成落地方案。建议工程团队优先落地 `HeuristicExtractor` 与 `ScoredMemoryRetrieval` 两个候选模块,因为它们补齐的是 AetherCode 当前最显著的空白——"从反思到规则的最后一公里",也是 ERL 相对当前 AetherCode 体系最具增量价值的两块拼图。
