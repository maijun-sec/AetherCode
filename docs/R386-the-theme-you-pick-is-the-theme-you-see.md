# R386 —— 用户选的主题,就是用户看到的屏幕

> `/theme solarized` 打印 `theme → solarized`,然后**屏幕一动不动**。
>
> 顺着这条线查下去,发现 TUI 里有**三套从未相遇的主题系统**,
> 而"主题名"这个词表写在**四个文件**里,并且**已经开始互相矛盾**:
> 产品出厂**五套**调色板,命令层只认**三套**——
> `kanagawa` 和 `opencode` 是两套**谁也选不了**的主题。
>
> 还有一个更贵的发现:即使把发布点修对,只要发布发生在
> **App 构建 JSX 之后**,屏幕上仍然会有元素**晚一帧**才换色。
> "晚一帧"也是缺陷——它和"永远不换"是同一个用户故事。

---

## 0. 这一轮做了什么

| # | 缺陷 | 现状 | 修法 |
|---|------|------|------|
| 1.1 | `/theme NAME` 只打印,不改屏幕 | 调色板算出来就被扔掉 | `t` 的调色板角色改成活 getter |
| 1.2 | `useTheme()` 零调用点 | 发布出去的调色板没人读 | 调色板经 `t` 到达 29 个组件 |
| 1.3 | 发布点在 provider 里 | App 自己建的元素晚一帧 | App 在构建 JSX **之前**发布 |
| 2.1 | 词表写在 4 个文件、16 个字面量 | 类型系统只认 3 个名字 | 词表收进 `src/themes.ts` |
| 2.2 | `/theme kanagawa` 被拒 | 两套调色板**选不了** | `/theme` 走 `resolveThemeName` |
| 2.3 | 错误信息手写三个名字 | 少列 = 用户以为没这个功能 | 错误信息由注册表**派生** |
| 3.1 | 第二套词汇(`aethercode-themes`) | 选择写进磁盘,屏幕不变 | 删掉两个桥文件,选择器用 TUI 自己的调色板 |
| 3.2 | 选择器的选择从不写 `themeName` | 选的调色板和渲染的调色板无关 | `onSelect` / `onPreview` 都写 `themeName` |

## 1. 缺陷:调色板算出来了,然后被扔掉

### 1.1 症状

```
> /theme solarized
theme → solarized          ← 屏幕没有任何变化
```

### 1.2 三套从未相遇的系统

| 系统 | 位置 | 状态 |
|------|------|------|
| 静态 token 表 `t` | `src/theme.ts` | **29 个组件** import 它并用它渲染,**它永远不变** |
| 五套调色板 + `pickPalette()` | `src/themes.ts` | 算得出,没人用 |
| React context | `src/ThemeContext.tsx` | `useTheme()` **零调用点**,发布出去的调色板被丢弃 |

修法(`src/theme.ts:104-147`):`t` 里 22 个**调色板角色**改成 `getActivePalette()` 上的
getter,另外 20 个 token 和 38 个 icon 留在固定的底表里。

> 为什么只有 22 个角色跟着主题走?Markdown 语法色(`tokKeyword`、`heading1`…)和图标
> 是**另一层**,就像代码编辑器把"工作台主题"和"语法高亮"分开。一套调色板如果连语法色
> 一起改,每个主题还要再手挑 21 个值,没有人会认真挑。

### 1.3 为什么"晚一帧"也是缺陷

第一版修法把发布放在 `ThemeProvider` 的渲染体里。写门禁时用 Ink 真渲染了一次,
发现**还是不对**:

- App 的渲染体里有一句 `color={t.warn}` —— 这个表达式在 **App 构建 JSX 的时候**求值;
- `ThemeProvider` 的渲染体在 App 的渲染体**之后**才跑;
- 于是 App 自己建的元素读到的是**上一帧**的调色板,下一帧才补上。

React 里父组件先渲染,子组件后渲染;而 **JSX 的属性在父组件的渲染体里就已经求值了**。
所以发布点必须比 provider **更早**。

修法:发布点放在 App 渲染体的最上面(`src/tui.tsx:896`),
并且**只有这一处**发布——`useActiveTheme(state.themeName)`
(`src/ThemeContext.tsx:59`)。门禁渲染的是**同一个函数**,不是它的副本。

### 1.4 顺带修掉的"三处调用点"

- `useTheme()` 从**零调用点**变成**一个**(选择器用自己的调色板画边框和标题)。
- `THEME_LABELS` 从一张没人读的表变成选择器行里的一行说明。
- 选择器的明暗标记 `●/○` 从**手写常量**变成 `paletteIsDark()` **算出来**的
  (`src/themes.ts:316`)——手写的 `isDark` 是"颜色已经说明的事"的第二份副本,
  而副本会跟颜色打架。

## 2. 缺陷:词表写在四个文件里

### 2.1 测量(不是回忆)

改动前,`src/` 里"整个值就是主题名"的字面量:

| 文件 | 字面量数 | 是什么 |
|------|---------|--------|
| `src/state.ts` | 10 | 类型联合(两处)+ 初值 |
| `src/commands.ts` | 3 | 手写的白名单 + 手写的错误信息 |
| `src/tui.tsx` | 3 | 类型断言 |
| `src/themes.ts` | 15 | **注册表自己**(唯一合法的地方) |

产品出厂 5 套调色板,`commands.ts` 只认 3 套:

```
> /theme kanagawa
unknown theme: kanagawa. Try: default, solarized, monokai.
```

`kanagawa` 和 `opencode` 是 R166 "for OpenCode-style polish" 加进来的——
**两套出厂了、谁也选不了的主题**。

### 2.2 修法

- `src/themes.ts` 成为唯一词表:`ThemeName`、`PALETTES`、`THEME_NAMES`、`THEME_LABELS`、
  `resolveThemeName()`、`pickPalette()`。
- `state.ts` 的 `themeName` 用注册表的 `ThemeName` 类型(`src/state.ts:555`),
  初值用 `DEFAULT_THEME_NAME` 常量——因为 `"default"` 是个**普通英文单词**,
  高亮器的兜底语言、提示词格式器的颜色名都用它,写成字面量就没法管住词表。
- `commands.ts` 的 `/theme` 走 `resolveThemeName()`(`src/commands.ts:803`),
  错误信息由 `THEME_NAMES.join(", ")` **派生**——它不可能列出一个不存在的名字,
  也不可能漏掉一个存在的名字。
- 名字**大小写不敏感**:`/theme Kanagawa` 现在能用。
- 裸 `/theme` 打开选择器(和 R385 的 `/mode` 同一个形状):
  **一个能干活的裸命令应该去干活,而不是打印一行用法**。

改动后:`src/themes.ts` 之外的主题名字面量 = **0**
(剩下 3 个 `"default"` 在 `EffortPicker.tsx` / `highlight.ts` / `prompt-formatter.ts`,
是同名的普通英文单词,与主题无关)。

## 3. 缺陷:第二套词汇

`aethercode-themes` 这个包自带一套主题:
`light` / `dark` / `solarized-light` / `solarized-dark` / `high-contrast`。

它和 TUI 自己的五套调色板**没有交集**,而且是**明暗模型**——
TUI 的终端底色是固定的,浅色主题在这里根本不可读。

选择器以前由这个包的 `ThemeStore` 驱动:

- `ThemeStore.setActive(name)` 写进 `<UserHome>/.aethercode/theme.json`;
- 屏幕继续渲染 TUI 自己的颜色;
- 而且**选择结果从不写 `state.themeName`**——也就是渲染器真正读的那个字段。

于是"用户选的主题"和"屏幕上的主题"是**两件无关的事**。

修法:删掉 `aethercodeThemesBridgeCore.ts` 和 `aethercodeThemesBridgeUI.tsx`,
选择器的行改由 `THEME_NAMES` 生成(`src/tui.tsx:940`),
`onSelect` / `onPreview` 都写 `state.themeName`。

> 包本身留在 `package.json` 和磁盘上:`t457-e2e-smoke.test.mjs` 仍然加载它
> (它断言包存在、导出 `ThemeStore`、源码文件数 ≥ 10)。这是**已知的后续项**:
> TUI 的 `src/` 里已经没有任何文件 import 它了。

## 4. 门禁

`aethercode-tui/scripts/test/r386-theme-reach.test.mjs` —— **19 条断言**。

| § | 断言 | 它能挡住什么 |
|---|------|------------|
| §1 | `t` 的每个调色板角色都跟着发布的调色板走 | token 表退回冻结字面量 |
| §1 | 换调色板会改 token,但不改 Markdown 语法色 | 两层被混为一谈 |
| §1 | 名字表和调色板表双向一致 | 有名字没调色板的主题 |
| §2 | **真渲染 Ink 树,换主题后帧里的 ANSI 颜色变了** | 屏幕不变 |
| §3 | 四个特征名只写在 `themes.ts` | 词表出现第二份 |
| §3 | 参与主题的文件里一个主题名都不许写 | `"default"` 混进普通英文单词 |
| §4 | `/theme <name>` 对注册表的每个名字都路由成功 | 某个主题选不了 |
| §4 | `/theme <name>` 大小写不敏感 | 名字变成大小写敏感 |
| §4 | 未知主题的错误信息**包含注册表的每个名字** | 错误信息手写、少列 |
| §4 | 裸 `/theme` 打开选择器 | 裸命令退化成打印用法 |
| §5 | 选择器的行来自注册表、标签来自标签表、明暗是算出来的 | 选择器自己维护一份名单 |
| §5 | 选择器的**每个** handler 都写 `themeName` | 选了不生效 / 预览不是预览 |
| §5 | 注册表的说明文字真的到达了用户 | 一张没人读的表 |
| §5 | App 在构建 JSX **之前**发布 | 晚一帧 |
| §6 | `src/` 里没有任何文件 import `aethercode-themes` | 第二套词汇复活 |
| §7 | 两个主题 sentinel 在**两个渲染器**上都有归属 | 原始 token 印给用户看 |

### 4.1 §2 为什么必须真渲染

§1 证明 token 表跟着发布的调色板走。这**不等于**"屏幕变了"——
而 R386 的整个缺陷就是这两者之间的缝:调色板算出来了、发布了、没人读,屏幕停在旧颜色上。

所以 §2 用 Ink 渲染一棵真的树,切换主题,然后从**输出的帧**里读 ANSI 转义码:

```
第一帧(default):  \u001b[93mCHILD\u001b[39m          ← yellowBright
                  \u001b[36mAPP\u001b[39m            ← cyan
第二帧(solarized): \u001b[38;2;181;137;0mCHILD\u001b[39m   ← #b58900
                  \u001b[38;2;42;161;152mAPP\u001b[39m    ← #2aa198
```

两个位置都变了:**在子组件自己渲染体里读 `t` 的**,和**App 自己建的元素**。

而且它渲染的是**真的** `ThemeProvider`、**真的** token 表、**真的**发布路径
(`useActiveTheme`)——不是副本。门禁验副本,验的就只是副本。

### 5.1 电池抓到的洞:一个**在共享助手里**的老洞

最后一个用例第一次跑是 **HOLE**:把 `slash?.local === "__THEMES_PICK__"` 改成
`=== "__THEMES_PICK__X"`,门禁**照样是绿的**。

原因在 `claimedBy()` 的正则:

```
(?:case\s+['"`]__X__['"`]|===\s*['"`]__X__|\.startsWith\(\s*['"`]__X__)
```

`===` 那一支**没有要求收尾引号**,于是它匹配上了 `=== "__X__X"` 的**前缀**——
渲染器把 sentinel 改名了,门禁还认为它"认领"着。

这个助手此前被抄了两份(r362 写了一份、r385 又抄了一份,两份**逐字节相同**——
正是"副本不会漂"的错觉最容易出现的地方)。R386 把它收进
`scripts/test/claimed-by.mjs`,三处共用一份,并补上了收尾引号:

- `case "__X__":` 和 `=== "__X__"` 是**完整的字符串字面量**,必须要求收尾引号;
- `startsWith("__X__:")` 是**带参数**的 sentinel,名字本来就是字面量的**前缀**,
  所以这一支故意不收尾——两种形态不可互换。

> 顺带:r362 和 r385 各自的内联副本被删掉了。
> **一份定义写三遍,不如写一遍**;而这一遍,是被**电池**改出来的。

## 8. 教训

**Lesson 1259 —— 一条命令说它做完了,它就必须真做了。**
`/theme solarized` 打印"theme → solarized",屏幕一动不动。
"命令说成功了"和"屏幕变了"之间,隔着的正是这一轮要补的那条链路。

**Lesson 1260 —— 算出来的东西没人读,就不算做了。**
`useTheme()` 有定义、有 context、有 provider,**零调用点**。
调色板一路算到了发布点,然后被丢掉。
判据:**一个计算结果的每一个下游,都要能被指出来**;指不出来的,它就是死代码。

**Lesson 1261 —— "晚一帧"和"永远不变"是同一个用户故事。**
发布点放在 provider 里,已经比原来好很多了——但 App 自己建的元素仍然晚一帧。
JSX 的属性在**父组件的渲染体里**求值,这件事很容易忘。
判据:**发布必须发生在"任何消费者读它"之前**,而不是"渲染树的某一层里"。

**Lesson 1262 —— 词表少写一个,用户以为功能不存在。**
产品有五套调色板,命令层只认三套,于是两套**谁也选不了**——
而错误信息还理直气壮地列了三个,像那就是全部。
判据:**列表和错误信息必须从同一处派生**;手写的清单必然落后。

**Lesson 1263 —— 两套词汇比一套半对的词汇更糟。**
`aethercode-themes` 的明暗模型和 TUI 的固定深色底色根本不兼容,
而它的 `setActive()` 写进磁盘,屏幕继续渲染 TUI 自己的颜色。
用户选的是 A,看到的是 B,而 A 看起来"生效了"(文件确实变了)。
判据:**一个选择必须写到"渲染器真正读的那个字段"上**,否则它写到哪里都没用。

**Lesson 1264 —— 电池改出来的洞,往往在助手里而不是在被测代码里。**
`claimedBy()` 少了一个收尾引号,两份逐字节相同的副本都掩盖了它。
判据:**同一份定义只能有一处**;而且**当"改坏被测代码"没能让门禁变红时,
先怀疑门禁自己**。

**Lesson 1265 —— 一份定义写三遍,不如写一遍;而这一遍是被电池改出来的。**
r362 写了一份、r385 抄了一份、R386 本来要写第三份。
两份相同的副本会让人相信"它已经稳定了"。
判据:**发现第二处副本时,先把它收进共享模块,再继续**——
否则第三份出现只是时间问题。
