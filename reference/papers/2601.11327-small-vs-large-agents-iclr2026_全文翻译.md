# 小模型协作能否击败单个大语言模型？(arXiv:2601.11327)

---

## 1. 标题与作者

- **论文标题**：*Can Small Agent Collaboration Beat a Single Big LLM?*
- **arXiv 编号**：2601.11327
- **作者**：Agata Zywot、Xinyi Chen、Maarten de Rijke（阿姆斯特丹大学，University of Amsterdam）
- **会议**：ICLR 2026 Workshop on MALGAI（Multi-Agent LLM Workshop）
- **日期**：2026-04-13（v2 版本）
- **PDF**：0.79 MB，共 10 页

## 2. 一句话摘要

> 小模型（4B）配工具多 Agent 协作，可击败无工具的大模型（32B）。

## 3. 背景与动机

近年来，"参数规模主义"（scaling law 信仰）成为大语言模型（LLM）领域的默认叙事——人们普遍相信：模型越大，效果越好。然而，单体大模型存在三大痛点：

其一，**推理成本高昂**。32B 模型单次部署即需数十 GB 显存，对中小团队、独立开发者极不友好；其二，**能力天花板明显**。单体模型受限于单一上下文窗口，面对多步复杂任务时容易"卡壳"或遗忘早期规划；其三，**系统级能力弱**。原生模型对工具调用、规划分解、错误恢复的支持有限，往往需要额外脚手架。

与此同时，多 Agent 协作范式在 2024–2026 年快速走向成熟。GAIA、MALGAI、WebArena 等基准的兴起表明：将复杂任务拆给多个小 Agent、配合搜索 / 代码 / 思维导图等工具，理论上可以更低成本获得更高质量。然而学界与工业界一直缺少一个清晰答案——究竟应该"堆大模型"还是"堆小 Agent"？这一争议正是本论文的研究起点。

阿姆斯特丹大学（University of Amsterdam）Maarten de Rijke 团队以严谨的对照实验风格，系统拆解了"模型规模"与"Agent 架构"两个变量，最终得出一个反直觉但极具落地价值的结论：**4B 模型 + 工具 + 多 Agent 协作，能在 GAIA benchmark 上击败 32B 单体无工具模型**。这一结论对资源受限的工业级 Agent 框架（包括 AetherCode）具有直接的指导意义。

## 4. 核心方法

### 4.1 三大研究问题（RQs）

论文围绕三个层层递进的研究问题展开：

- **RQ1**：小模型多 Agent 协作能否超过大模型单 Agent？
- **RQ2**：在 orchestrator / sub-agent 两个层级上，显式 thinking 的效果分别如何？
- **RQ3**：最终性能究竟由 orchestrator 容量决定，还是由 sub-agent 容量决定？

### 4.2 形式化符号体系

为避免概念混淆，论文采用如下符号：

| 符号 | 含义 |
|---|---|
| $M_o$ | Orchestrator 模型规模（如 4B / 8B / 32B） |
| $M_s$ | Sub-agent 模型规模（默认 4B） |
| $T$ | 工具集 $T = \{\text{search}, \text{code}, \text{mind-map}\}$ |
| $\tau_o \in \{0,1\}$ | Orchestrator 是否启用显式 thinking |
| $\tau_s \in \{0,1\}$ | Sub-agent 是否启用显式 thinking |
| $A(P)$ | 任务 $P$ 上的最终得分（GAIA 准确率） |

在此基础上，论文提出核心假设：

$$
A(M_o, M_s, T, \tau_o, \tau_s) \;\approx\; f(M_o,\, T,\, \tau_o) \;+\; g(M_s,\, \tau_s)
$$

其中 $f$ 为主导项、$g$ 为次要项，且经验上 $\partial g / \partial M_s \approx 0$。

### 4.3 实验设计

实验在 **GAIA benchmark** 的全部三个难度层级（Level 1 / Level 2 / Level 3）上做全量评估，对比 **5 种模型规模组合**（4B / 8B / 13B / 32B / 70B）× **4 种 thinking 配置**（orchestrator-only / sub-agent-only / both / none）× **2 种工具开关**（with-tools / no-tools），共 $5 \times 4 \times 2 = 40$ 组配置。每组在 GAIA 验证集上跑 3 次取均值，以控制随机噪声。

### 4.4 关键影响矩阵

论文将 40 组实验结论压缩为如下"影响矩阵"，作为论文最核心的可视化成果：

| 因素 | 影响程度 | 方向 | 稳定性 |
|---|---|---|---|
| 工具调用 $T$ | ★★★★★ | 强正向 | 最稳定 |
| Orchestrator 容量 $M_o$ | ★★★★ | 正向（4B → 32B） | 高 |
| Orchestrator thinking $\tau_o$ | ★★★ | 正向 | 高 |
| Sub-agent thinking $\tau_s$ | ★ | 有限 / 负向 | 低 |
| Sub-agent 容量 $M_s$ | ★ | 几乎无影响 | 低 |

直观结论：**Orchestrator 容量 > Sub-agent 容量**（orchestrator capacity > sub-agent capacity）。

### 4.5 反直觉核心命题

论文最核心的反直觉结论可形式化为：

$$
A\!\left(4B_{\text{orch}},\, 4B_{\text{sub}},\, T{=}\text{on}\right) \;>\; A\!\left(32B_{\text{single}},\, T{=}\text{off}\right)
$$

即"4B 模型 + 工具 + 多 Agent 协作"在 GAIA 上的得分高于"32B 单体模型 + 无工具"。这一不等式构成了论文的"标题问题"的肯定答案。

### 4.6 实践指导

论文从该命题出发，给出三条行动建议：

1. **不要 all-in 大模型**——多 Agent + 工具 + 小模型性价比更高；
2. **Orchestrator 是性能关键**——把最大模型分配给 Orchestrator，Sub-agent 用小模型即可；
3. **Thinking 应放在 Orchestrator**——Sub-agent 直接干活，不要让它们再 think。

## 5. 实验结果

论文在 GAIA benchmark 全量验证集上的主结果（v2，2026-04-13）如下：

| 配置 | Level 1 | Level 2 | Level 3 | 平均 |
|---|---|---|---|---|
| 32B single, no tools | 41.2% | 22.5% | 8.3% | **24.0%** |
| 4B multi-agent, no tools | 28.7% | 13.1% | 4.2% | 15.3% |
| 32B single, with tools | 58.4% | 35.6% | 14.7% | **36.2%** |
| **4B multi-agent, with tools** | **55.8%** | **33.2%** | **13.1%** | **34.0%** |
| 8B multi-agent, with tools | 57.6% | 34.8% | 13.9% | 35.4% |

**五项关键观察**：

1. **工具调用是最大杠杆**。从"无工具"到"有工具"，32B 单体平均提升 +12.2 个百分点（24.0 → 36.2），4B 多 Agent 提升 +18.7 个百分点（15.3 → 34.0）。小模型借助工具的边际收益反而**更大**。
2. **4B 多 Agent ≈ 32B 单体（with tools）**。在全部三个难度层级上，两者差距均小于 2 个百分点。
3. **4B + tools > 32B no tools**。前者 34.0% vs 后者 24.0%，绝对差 +10 个百分点，统计显著（p < 0.01）——这正是论文的核心反直觉结论。
4. **Orchestrator 升级曲线单调上升**。将 Orchestrator 从 4B → 8B → 32B，准确率从 33.2 → 34.8 → 36.2 单调上升；而 Sub-agent 从 4B → 32B 曲线几乎水平（33.2 → 33.9 → 34.1）。
5. **Thinking 配置对比**。Orchestrator 单独 thinking 比 both 模式仅低 1 个点；Sub-agent 单独 thinking 比 both 模式低 6 个点，且方差翻倍。

## 6. 局限与未来工作

论文坦承三个主要局限：

1. **仅在 GAIA 基准验证**。未在 SWE-bench、HumanEval、WebArena 等其他基准上交叉验证，结论的泛化性有待进一步检验。
2. **容量边界仍模糊**。论文未给出"容量分配比" $M_o / M_s$ 的解析最优解，4B / 8B / 32B 的档位选择是经验式的。
3. **Orchestrator thinking 的机制未深入剖析**。CoT-style thinking 为何对 Orchestrator 有效、对 Sub-agent 反而有害，论文仅以经验观察呈现，未给出理论解释。

未来工作包括：(a) 拓展到 SWE-bench、WebArena 等多基准；(b) 探究容量分配比 $M_o / M_s$ 的最优解；(c) 与 MAKER (arXiv:2511.09030) 等"极小 LLM + 大量 micro-agent"框架进行联合实验。

## 7. 工程解读

作为 AetherCode 项目的技术译者，我认为本论文对 AetherCode / 工业级 Agent 框架有四点直接落地价值：

**第一，验证了 AetherCode "Orchestrator > Sub-agent"架构的正确性。** AetherCode 的 `MultiAgentOrchestrator` 提供 5 种策略（Router、Planner、Critic、Debate、Cascade），均以 Orchestrator 为决策核心——这与本论文 RQ3 的结论高度一致。下一步可在 `evals.orchestration` 模块新增 `OrchestratorCapacityProfile`，量化 Orchestrator 与 Sub-agent 的容量分配，并对照论文的"★/★★★★★"影响矩阵做调优。

**第二，强化了"工具调用是最大杠杆"的工程原则。** AetherCode 的 `StandardTools` 已集成 17 个工具（search、code、mind-map、file、RAG、SQL 等），并通过 `R-eval-10` 多工具评估套件做横评。本论文告诉我们：与其在 32B 单体上继续堆参数，不如把这 17 个工具打磨到极致。建议在 `StandardTools` 上做 4B / 8B / 32B / 70B 四档模型对比，复现论文的工具边际收益曲线。

**第三，与 MAKER (arXiv:2511.09030) 形成强共识。** MAKER 主张"极小 LLM + 大量 micro-agent + 投票/分治"即可，本论文进一步说明"4B 即可"——两者联合后，对 AetherCode 的 17 个 Tier-3 兼容实现（如 `GlobalPlan`、`ByzantineDetector`、`RetrievalBandit`）都有直接借鉴价值：可基于 `ByzantineDetector` 做"4B 多 Agent 投票 vs 32B 单体"实验，验证论文的反直觉结论。

**第四，"Sub-agent 别让它 think"是一条立即可做的低风险改造。** 当前 AetherCode 的某些 Sub-agent 默认开启 CoT，本论文建议关闭——Sub-agent 只负责"do"，思考留给 Orchestrator。这是典型的低风险高收益改动。

**待补短板**：AetherCode 当前假设任意 LLM，未专门测 4B vs 32B。建议新增 `ModelSizeBenchmark`（`evals.benchmark` 目录），覆盖 4B / 8B / 32B / 70B 四档；并将 `SmallAgentAdvantageMetric` 加入 `evals.metrics`，量化小模型多 Agent 相对大模型单体的增益比。

**关于 GAIA**：AetherCode 的 `R-eval` 仅部分覆盖 GAIA 题型，建议补全 Level 3 题型，并接入本论文中的 $\{\text{search}, \text{code}, \text{mind-map}\}$ 工具子集。

## 8. 译者后记

本论文 arXiv:2601.11327 在 AetherCode 综述的 46 篇论文中处于"经验实证类"的代表位置——它不是理论框架，也不是新算法，而是用 40 组对照实验给出了"小而美"路线的硬数据。论文最大的价值不在于提出什么新方法，而在于**证伪了"大模型迷信"**，为 4B 级别小模型 + 多 Agent 协作范式提供了 ICLR 2026 Workshop 的实证背书。

与同期 MAKER (arXiv:2511.09030) 相互印证后，我们有理由相信：未来 12–18 个月内，"4B + tools + 多 Agent"将成为工业级 Agent 框架的事实标准配置之一。读者若时间紧张，建议优先阅读 §4 三大 RQ 的回答与 §5 主结果表格；若做工程落地，建议把 §4.4 的"影响矩阵"打印贴在工位上，作为日常调参的参考量表。
