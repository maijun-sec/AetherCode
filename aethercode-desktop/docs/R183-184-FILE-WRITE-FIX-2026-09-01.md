# R183 + R184 — file_write 端到端修复 (2026-09-01)

## 1. 背景

v0.2.30 desktop 用户实测发现：发 prompt 后模型调 `file_write` 直接卡死，5 分钟都写不出一个文件。
**用户原话**："建议自己实现完，用 aethercode 实现一个简单的 java 项目，试试，到现在，都快一个月了，什么都搞不出来，调个 file_write，半天什么都写不出来"。

直接 daemon 端到端测试 (`probe-test.py`) 复现：
1. `setAutoApproveMediumHigh(true)` 返回 ok
2. `file_write` 调 `Hello.java` —— 5 分钟超时，`tool_result: isError=true "permission ask for 'file_write' timed out after 300s"`
3. 模型收到 "DO NOT retry" 消息后**还是重试**（消息 [3]）
4. 文件**始终没被写入**

端到端跑一个真实 Java Maven 项目（3 个文件）时还发现第二个 bug：
- `[2] tool_result isError=True write refused: D:\tmp\aethercode_java\pom.xml is outside the working directory`
- `file_write` 拒绝写入 session cwd 之外，但 session cwd 跟 daemon 启动 cwd 不一样

第三个 bug：
- 流式响应每个 chunk 里的 `finish_reason: ""` 空字符串，Jackson 解析 `ChatCompletionFinishReason` enum 抛 `Cannot deserialize value of type ... from String ''`
- 模型**根本没机会响应**，transcript 永远卡在 1 条 user message

## 2. 三个独立 root cause

### 2.1 R183: R130 收窄 auto-approve 导致 file_write 卡死

`aethercode-protocol/.../JsonRpcPermissionPrompter.java`：

Pre-R183：
```java
if ("high".equals(riskLevel) && methods.isAutoApproveMediumHigh()) {
    // 自动批准——但只对 high
}
```

`file_write` 的 riskLevel 是 **medium**（不是 high），所以即使桌面开了 `setAutoApproveMediumHigh(true)`，prompter 还是会把 file_write 当作需要问用户的请求，desktop 弹 consent modal（用户没看到），5min 后超时。R181 给了清晰的 "DO NOT retry" 消息但**模型还是重试了**——软建议不够。

R183 修：把自动批准扩展到 medium + high：
```java
if (("medium".equals(riskLevel) || "high".equals(riskLevel))
        && methods.isAutoApproveMediumHigh()) {
    // 关键 risk（rm -rf, sudo, mkfs, dd）由下方 critical 分支单独判，永远不会自动批准
}
```

### 2.2 R183: file_write 用错的 cwd（per-session vs JVM-launch）

`aethercode-tools/.../file/FileWriteTool.java` 和 `FileReadTool.java`：

Pre-R183：
```java
private static boolean isPathAllowed(Path p) {
    String engineCwd = System.getProperty("aethercode.cwd");
    Path cwd = (engineCwd != null && !engineCwd.isBlank())
            ? Path.of(engineCwd).toAbsolutePath().normalize()
            : Path.of("").toAbsolutePath().normalize();
    return p.startsWith(cwd);
}
```

`aethercode.cwd` 是 JVM 启动时设的全局系统属性，是 **daemon 的 --cwd**，不是 session 的 cwd。用户创建 session 在 `D:\tmp\aethercode_java`，daemon 用 `--cwd D:\tmp\aethercode_test` 启动——session cwd 跟 daemon cwd 不一样，file_write 立刻拒。

R183 修：通过 `CallContext.extra("app_state").cwd()` 拿 session 的 cwd（StreamingToolExecutor 在 `buildExtras` 里已经把 appState 放进 extras 了），fallback 才用全局系统属性。

### 2.3 R184: Spring AI 流式响应 finish_reason="" 解析失败

`aethercode-core/.../aicompat/SpringAiEnumCompat.java`（新建）：

MiniMax M3 模型（以及很多 OpenAI 兼容后端）每个流式 chunk 都会发 `finish_reason: ""` 空字符串，只在最后 chunk 发 `"stop"`。Spring AI 1.0.0 的 `OpenAiApi.ChatCompletionChunk.ChunkChoice.finishReason` 是 enum，Jackson 默认 `EnumDeserializer` 不接受空字符串 —— 抛 `Cannot deserialize value of type ... from String ''`。

R184 修：在 engine bootstrap 时通过反射拿到 `org.springframework.ai.model.ModelOptionsUtils.OBJECT_MAPPER`，注册一个自定义 enum deserializer，**只**在空字符串时返回 `null`，其他情况 delegate 给原始 deserializer（保留 case-insensitive lookup、`@JsonProperty` / `@JsonAlias` 等所有原始行为）。

```java
// R184: idempotent + best-effort — no-op if Spring AI version
// doesn't expose OBJECT_MAPPER.
SpringAiEnumCompat.patchOnce();
```

## 8. 教训 (2026-09-01)

1. **别光修不测**。R180/R181/R182 修了一堆 bug，但都没在真实场景下跑过 file_write。如果 R183 之前用 `probe-test.py` 跑过，会立刻发现 file_write 死了 5 分钟。我承诺了"端到端"就应该真跑。
2. **R130 收窄 auto-approve 是"安全过头"**。R130 把 auto-approve 从 medium+high 收到只 high，理由是用户"想 medium 也要 explicit confirm"——但用户**从来没在 desktop 上弹过 consent modal**（R183 修的另一个独立问题），结果 medium 风险（file_write）永远在等 5min 超时。教训：收窄一个开关时**先确认用户能看到 modal**，否则就是无限 timeout。
3. **per-session state vs global system property 是个长期隐患**。`aethercode.cwd` 是 JVM 启动时设的全局属性；R127 引入了 per-session cwd（`AppState.cwd()`）但工具链没跟上。R183 改两处工具（file_write + file_read）让它们优先用 per-session cwd。教训：**当一个变量有"全局"和"per-session"两个版本时，per-session 应该永远赢**。grep `System.getProperty("aethercode.cwd")` 看看还有没有别的工具踩这个坑。
4. **Spring AI + OpenAI 兼容后端的"空 finish_reason"是个跨模型隐患**。R184 用反射 + BeanDeserializerModifier 最小侵入地修了。教训：第三方库遇到非标准行为，最便宜的修复是反射 + 模块注册——不 fork 库，不替换 chat client，几行代码搞定。
5. **真实的用户 prompt 比 happy path 测试能暴露更多 bug**。"写一个 Hello.java" 通过了，"写一个 3 文件的 Maven 项目"暴露了 stream JSON deserialization 问题，"写一个排序算法项目"暴露了 file_write 卡死。教训：测试要**按真实用户场景写**，不只 happy path。
