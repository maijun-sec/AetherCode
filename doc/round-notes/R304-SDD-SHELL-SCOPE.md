# R304 — SDD Tauri shell-plugin scope for `java` + friendly scope-error UX

**Date**: 2026-09-21
**Round**: R304 (post-R303 user verification)
**Author**: Mavis (mavis)

## TL;DR

After R303 granted the `shell:allow-spawn` ACL permission, the next
failure surfaced:

```
program not allowed on the configured shell scope: java
```

Tauri 2.x shell plugin requires **two layers**:
1. **ACL permission** (`shell:allow-spawn`) — R303 already granted.
2. **Scope allow-list** (`{ "name": "java", "cmd": "java", "args": true }`) —
   pre-R304 was empty, so `java` was rejected even though `spawn` itself
   was permitted.

**Fix (2 parts)**:

1. **`src-tauri/capabilities/default.json`**: change `shell:allow-spawn`
   and `shell:allow-execute` from bare string identifiers to objects
   with an `allow` array containing the `java` entry.
2. **`src/store/index.ts`**: extend `friendlySddSpawnError` with a new
   "configured shell scope" case (between ACL denial and ENOENT java).
   Bumped the diagnostic log prefix from `R303-sdd-spawn-failed` to
   `R304-sdd-spawn-failed`.

**Verification**: 1202 desktop tests pass (up from 1200, +2 R304
source-pin). Build clean (Tauri 3m28s). exe 6.56 MB / NSIS 55.06 MB /
MSI 56.77 MB. Commit `25dd7b5` pushed to `origin/main`.

## Background

### Symptom

User installed the R303 build, restarted the desktop, triggered SDD.
The driver choice card rendered correctly (`--interactive`, the full
command line, the R299 explanation). The chat stream now showed:

```
📐 **SDD spawn failed**

slug: java-maven
jarPath: \\?\D:\...\release\R292\desktop\aethercode.jar
cwd: D:\tmp\abc_1

详细错误见下方 Raw error 折叠块。

<details><summary>Raw error (show technical details)</summary>

program not allowed on the configured shell scope: java

</details>

Diagnostic log: `%TEMP%\aethercode-desktop-daemon-info.log`
```

The R303 friendly translator correctly identified the **fallback
generic** branch (no regex matched "not allowed by ACL", "ENOENT", "jar
not found", or "NEEDS_CWD"). The raw error under the `<details>` block
told the user exactly what was wrong — but a non-Tauri user reading
"shell scope" probably doesn't know what that means either. Hence the
"详细错误见下方 Raw error 折叠块" placeholder + a real diagnostic gap.

### Root cause

Tauri 2.x shell plugin's `prepare_cmd` does two checks before spawning:

```rust
// shell-2.3.6/src/commands.rs (line 99)
fn prepare_cmd(window, program, args, options, command_scope, global_scope) -> Result {
    let scope = ShellScope {
        scopes: command_scope.allows().iter().chain(global_scope.allows()).collect(),
    };
    match scope.prepare(&program, args) {  // looks up by `name`
        Ok(cmd) => cmd,
        Err(_) => return Err(ProgramNotAllowed(PathBuf::from(program))),
    };
}
```

The `command_scope` is populated from the capability file's per-permission
scope entries. The default `shell:allow-spawn` permission (per
`tauri-plugin-shell-2.3.6/permissions/autogenerated/commands/spawn.toml`)
ships **with no scope** — meaning the allow list is empty and `java` can't
be looked up.

The `shell:allow-spawn` ACL permission grants the **right to call the
Tauri command `plugin:shell|spawn`**, but doesn't say "and `java` is
allowed". That's a separate scope object on the same permission:

```json
{
  "identifier": "shell:allow-spawn",
  "allow": [{ "name": "java", "cmd": "java", "args": true }]
}
```

The shell plugin's `scope_entry.rs::Entry` deserialises this object into
the `ShellScope`'s allow list. At spawn time, `_prepare` (scope.rs:251)
matches `command_name` (the `program` argument JS passed to
`Command.create("java", [...]).spawn()`) against `scope_entry::Entry.name`.
My desktop calls `Command.create("java", args)`, so the lookup name is
`"java"` — which means the scope entry needs `name: "java"` (matching
the JS-side name) and `cmd: "java"` (the actual executable to run).

### Why this slipped through R293-R303

The earlier rounds all failed at the **first** shell-plugin layer (ACL
denial), which R303 fixed. The second layer (scope) had been sitting
behind it, and only the R303 build ever got far enough to hit it. Same
pattern as R303's slip — pre-R303 builds never got past the ACL check.

## Fix

### Part 1: scope object on shell permissions

`src-tauri/capabilities/default.json`:

```json
"permissions": [
  "core:default",
  "core:event:default",
  "core:window:default",
  "core:webview:default",
  "dialog:default",
  "shell:default",
  {
    "identifier": "shell:allow-spawn",
    "allow": [
      {
        "name": "java",
        "cmd": "java",
        "args": true
      }
    ]
  },
  "shell:allow-stdin-write",
  "shell:allow-kill",
  {
    "identifier": "shell:allow-execute",
    "allow": [
      {
        "name": "java",
        "cmd": "java",
        "args": true
      }
    ]
  }
]
```

Key fields on each scope entry:

- `name` — the lookup key (must match what JS passes to
  `Command.create(name, args).spawn()`). For our `TauriSsdDriver` it's
  `"java"`.
- `cmd` — the actual executable to spawn (`PathBuf`-deserialisable). For
  portability we use the bare `java` name and rely on the user's PATH
  resolution. (A future round could add a Java Path setting to make
  this explicit; for now we trust `java -version` to work.)
- `args: true` — allow any argument list. `TauriSsdDriver` passes
  dynamic args (`-Xmx4g`, `-jar`, `jarPath`, `feature`, `intent`,
  `--interactive`, `--cwd`, `cwdPath`) that don't fit a fixed-list
  pattern. `true` is the safe escape hatch for this case.

`shell:allow-stdin-write` and `shell:allow-kill` don't need scope
entries because they take a `ChildId` (handle to an already-spawned
process) — the scope check is only on `spawn` / `execute`.

## Lessons

- **Lesson 634** (new): **Tauri 2.x shell-plugin security is a two-layer
  stack.** Layer 1 is the ACL permission identifier
  (`shell:allow-spawn`, `shell:allow-execute`) — grants the right to
  call the Tauri command. Layer 2 is the **scope** object on the
  permission — declares the program names that the layer-1 grant is
  for. Layer 2 default is empty; you must explicitly list
  `{ name: "<js-name>", cmd: "<executable>", args: true | [...] }`.
  Diagnostic tip: any error containing "shell scope" or
  "program not allowed" means layer 2 needs scope entries. Diagnostic
  tip 2: the scope lookup is by `name`, not `cmd` — `Command.create(name,
  args)` matches scope entries whose `name == <name>`.
- **Lesson 635** (new): **When fixing a multi-layer security stack,
  test each layer individually.** R303 fixed layer 1 (ACL) and got
  past it to layer 2 (scope) for the first time. R304 fixes layer 2.
  The R303 test only verified the capability file has the permission
  string — it didn't verify the scope object shape. R304 source-pin
  tests cover both layers explicitly, with each layer's failure mode
  expressed as a separate test case. Future rounds adding new shell
  commands should follow the same pattern.
- **Lesson 636** (new): **Friendly error messages should explain WHY
  the user's known fix won't work next time.** The R303 message
  ended with "如果已经是最新 build 还报这个错，请贴 ... log" — that
  hint paid off here because the user re-installed and hit a different
  error. R304 extends the same template to the scope case, telling
  the user that the new build's capability object has the fix.
