# R78 — Trace Recorder + `/trace` command (2026-08-09)

## Goal

Give the user a way to see **what the engine has been doing**, in
addition to *how much* (R77 metrics) and *what it said* (the
scrollback). One query may invoke several tools, each taking a
different amount of time; the user wants to know:

- Did the model call a tool at all, or answer directly?
- Which tool was slowest?
- Did any tool error out, and how long before the engine gave up?
- How much time did the query spend in the model vs. tools?

The natural answer is a small list of "spans" with a name, a
duration, and a status icon. R78 implements the simplest useful
version: a **root span per query** and a **child span per tool
invocation**, both flat (no parent linkage), capped at 256 in
memory, surfaced via a new `/trace` command.

## Pattern (R78 follows the R77 template)

R77 introduced a "backend collector + new RPC + new TUI command +
E2E" pattern. R78 generalises it:

| Layer | R77 | R78 |
|---|---|---|
| Backend class | `MetricsCollector` (counters) | `TraceRecorder` (spans) |
| Engine accessor | `engine.metrics()` | `engine.traces()` |
| RPC method | `getMetrics()` | `getTraces({limit})` |
| TUI state fields | n/a (no state) | `recentTraces[]`, `tracesInFlight`, `tracesCompleted` |
| Slash command | `/metrics` | `/trace`, `/trace <n>` |
| TUI render | side note with `padEnd` table | side note with status icon + name + duration |
| E2E | daemon query + assert counters | daemon query + assert `completed >= 1` |

Both rounds are documented as "per-process observability"
rounds; the pattern is reusable for R79 (audit log) and any
future "/<thing> shows engine state" feature.

## Backend changes

### `aethercode-core/.../trace/TraceRecorder.java` (new, 6383 bytes)

A `final` class with:

- `record Span(traceId, name, startMs, endMs, status, attrs)` —
  immutable, JSON-friendly (`toMap()`).
- `startSpan(name, attrs)` → `String traceId` (`"tr-<uuid>"`).
- `synchronized endSpan(traceId, status)` — closes the span,
  normalises status to `ok`/`error` (anything not `"error"` is
  `ok`), and pushes it onto a bounded `ConcurrentLinkedDeque`.
- `recentTraces(limit)` — descending iterator over the deque.
- `snapshot()` / `snapshot(limit)` — `{inFlight, completed, traces: [...]}`.

Thread-safety:
- `inFlight` is a `ConcurrentHashMap`.
- `endSpan` is `synchronized` so the size-guard + `addLast` +
  `pollFirst` are atomic. **The first test pass failed** with
  `expected: <true> but was: <false>` on the 8-thread × 200-iter
  concurrent test because `ConcurrentLinkedDeque.addLast` +
  `pollFirst` are individually thread-safe but the size-guard
  pair is not — under contention the deque briefly exceeded
  `CAPACITY`. Marking `endSpan` `synchronized` fixed it.

Capacity:
- `CAPACITY = 256`. Older spans fall off the tail.
- The TUI caps its in-state list at 32 (`slice(0, 32)`).
- The RPC clamps the user's `limit` to `[1, 256]`.

### `aethercode-sdk/.../AetherCodeEngine.java` (modified)

- New field: `private final TraceRecorder traces;` (per-engine,
  created in the constructor, never reset).
- New accessor: `public TraceRecorder traces() { return traces; }`.

### `aethercode-protocol/.../AetherCodeMethods.java` (modified)

- `dispatcher.register("getTraces", this::getTraces)`.
- `getTraces(Object params)` — accepts `{limit: 1..256}`,
  default 10, returns `engine.traces().snapshot(limit)`.
- `query()` worker thread now opens a root `"query"` span at
  the top, and:
  - on `ToolUseStart`: opens a `"tool.<name>"` span, keying
    by the `tu.id()` so the matching `ToolResult` can close it
    (even if events arrive out of order).
  - on `ToolResult`: closes the matching tool span with
    `isError ? "error" : "ok"`.
  - on `RunEnd`: closes the root span. Any still-open tool
    spans (defensive — shouldn't happen) are closed with
    `"error"`.
  - in `catch`: closes root + any leftover tool spans with
    `"error"`.

The hookup is inside the same `forEach` as the R77 metrics
increments — both observability layers see every event the
TUI sees, with no extra plumbing.

## TUI changes

### `state.ts` (modified)

- New `TraceSummary` interface (`traceId, name, startMs, endMs,
  status, durationMs, attrs`).
- New state fields: `recentTraces: TraceSummary[]`,
  `tracesInFlight: number`, `tracesCompleted: number`.
- New action: `setRecentTraces` (capped at 32 in reducer).

### `commands.ts` (modified)

- `SLASH_COMMANDS` adds `"trace"`.
- `case "trace"`:
  - `/trace 50` → `rpcParams: { limit: 50 }` (clamped to 256).
  - `/trace` (no arg) → `rpcParams: { limit: 10 }`.

### `tui.tsx` (modified)

- After `getTraces` RPC succeeds, dispatch `setRecentTraces`
  AND a side note with a small pretty-printed table:

  ```
  traces (3 shown, 5 total, 0 in flight)
    ✓ query                 4.58s  ok
    ✓ tool.glob           245ms  ok
    · tool.bash       running
  ```

- Status icons: `✓` for ok, `✗` for error, `·` for running.
- Duration formatter: `< 1s` → `"245ms"`, otherwise
  `"(dur / 1000).toFixed(2)s"`.
- Empty case: `(no traces yet — run a query to populate)`.

Line mode (the `ac-tui --line` path) keeps its generic
`getTraces → <json>` dump — there's no TUI component to
render in line mode, and the JSON is what E2E asserts against.

## Pitfalls (R78)

1. **ConcurrentLinkedDeque is not enough for a bounded deque.**
   The size-guard (`if (size >= CAPACITY) pollFirst()`) +
   `addLast()` pair needs to be atomic under concurrent writers.
   Marking the closing method `synchronized` is the smallest
   fix; the alternative is an `ArrayDeque` wrapped in a
   `ReentrantLock` (more code, same semantics).
2. **Empty / partial JSON inputs.** The TUI render path must
   handle `{inFlight, completed, traces}` with any field
   missing or non-numeric; line mode just dumps raw JSON
   which would crash on `JSON.parse` if the daemon ever sent
   a partial response. R78's render is defensive; line mode
   relies on the daemon never sending partials.
3. **`tool.*` prefix matters.** R78's span names start with
   `tool.` so the TUI can distinguish root queries from
   children. Future: a more conventional OTel shape
   (`{kind: "INTERNAL" | "CLIENT"}` + parent_id) — that's
   R79+ territory.
4. **Capacity vs. limit mismatch.** The TUI caps its
   in-state list at 32 but the RPC supports up to 256. R78
   is fine because the TUI dispatch re-fetches on every
   `/trace` call — the cap is a render limit, not a data
   limit. If we ever keep a "live" trace list (subscribe),
   the cap should be re-evaluated.

## What's next (R79 candidates)

- **R79: span tree** — add `parent_span_id` to `Span` so
  children nest under their query root. Render as a tree
  in the TUI (with `└─` / `├─` connectors).
- **R79: `/trace <traceId>`** — fetch a single trace's
  full span list (not just the most-recent 10).
- **R79: live trace pane** — keep a rolling list of
  in-flight spans so the user sees "tool.bash is running"
  without typing `/trace`.
- **R80+ candidates**: audit log persistence
  (`~/.aethercode/audit.jsonl`), tool-chain execution
  (DagPlan), rate limit visibility, etc.

The "engine observability" pattern (R77 metrics, R78
traces, future R79 audit) is now a clear axis for future
rounds — each one is a backend collector + RPC + TUI
command + E2E.
