## 摘要 (Abstract)

**原文**: *Multi-agent LLM systems have emerged as a promising approach for tackling complex tasks, yet the design space is vast—encompassing choices about agent count, coordination patterns, and workflow structure. Empirical evidence on these design choices is limited, with most prior work focused on a single architecture or a narrow task domain. We present a study of how multi-agent systems scale across a wide range of task complexities, evaluating systems that vary along three axes: workflow structure (single-agent vs. multi-agent), agent count (1, 3, 5, 10 agents), and coordination pattern (centralized, decentralized, hybrid). We evaluate across four task domains (software engineering, mathematical reasoning, scientific reasoning, and web navigation) at four difficulty levels each (16 conditions × 4 domains × 4 difficulties = 256 configurations), using the same underlying LLM (Claude-3.5-Sonnet) to isolate the effect of system design. We observe that scaling agent count yields diminishing or negative returns in most settings, with the largest gains limited to parallelizable, easy-to-verify tasks; multi-agent coordination amplifies error rates by 4–17× in our experiments; and the optimal architecture varies by task. We discuss the implications of these findings for practitioners and identify open challenges toward a science of agent system design.*

**译文**: 多智能体大语言模型系统 (multi-agent LLM systems) 已成为应对复杂任务的一条颇有前景的路径, 但其设计空间庞大——涵盖了智能体数量、协调模式、工作流结构等多重选择。关于这些设计选择的实证证据却相当有限, 多数既有工作只聚焦于单一架构或狭窄的任务领域。本文系统研究多智能体系统如何随任务复杂度扩展, 沿三个轴线评估系统: **工作流结构** (单智能体 vs. 多智能体)、**智能体数量** (1、3、5、10 个)、**协调模式** (中心化、去中心化、混合)。我们在 **4 个任务领域** (软件工程、数学推理、科学推理、网页导航)、**4 个难度等级** 上开展评估, 共 16 种条件 × 4 领域 × 4 难度 = 256 种配置, 且统一使用 Claude-3.5-Sonnet 作为底层大模型, 以隔离系统设计的影响。我们观察到: **扩大智能体数量在多数设置下带来递减甚至负面的回报**, 最大收益局限于可并行、易于验证的任务; **多智能体协调在实验中放大了 4-17 倍的错误率**; **最优架构因任务而异**。我们讨论这些发现对实践者的含义, 并指出通往智能体系统设计科学所面临的开放性挑战。

## 1 引言 (Introduction)

**原文 (摘译)**: Modern LLM-based agents can read and write files, browse the web, execute code, and call APIs. When a single agent cannot reliably solve a task, the natural next step is to instantiate multiple agents and let them collaborate. This is the "multi-agent system" (MAS) pattern, now pervasive in production systems such as Cursor, Devin, and Anthropic's Claude Code. The architecture of these systems varies wildly: some are centralized (a planner dispatches to workers), some are peer-to-peer (agents vote or debate), and some are hybrid.

**译文**: 当代基于 LLM 的智能体能够读写文件、浏览网页、执行代码、调用 API。当单个智能体无法可靠地完成任务时, 自然的下一步就是实例化多个智能体并令其协作。这就是"多智能体系统" (multi-agent system, MAS) 模式, 如今已广泛见于 Cursor、Devin、Anthropic Claude Code 等生产系统。这些系统的架构差异巨大: 有的采用中心化 (一个规划器向工作者派发任务), 有的采用点对点 (智能体投票或辩论), 还有的采用混合模式。

**原文 (摘译)**: Despite the popularity of these patterns, principled guidance on when and how to scale agents is largely missing. The folklore says "more agents = better" but practitioners report the opposite: multi-agent systems frequently fail in subtle ways (one agent's bad output cascades) and are hard to debug. We aim to put the design of multi-agent systems on a more empirical footing.

**译文**: 尽管这些模式广受欢迎, 关于何时以及如何扩展智能体的原则性指导却近乎缺位。坊间传言"智能体越多越好", 但一线工程师反映的却是另一番图景: 多智能体系统常常以隐蔽的方式失败 (一个智能体的劣质输出会级联扩散), 而且难以调试。本研究旨在把多智能体系统的设计建立在更坚实的实证基础上。

### 1.1 研究问题 (Research Questions)

**原文**: We organize our investigation around three questions:
1. *How does agent count affect performance?* We measure task success as we scale from 1 → 3 → 5 → 10 agents.
2. *Which coordination pattern works best for which task?* We compare centralized, decentralized, and hybrid across four task domains.
3. *What is the cost-quality trade-off?* Multi-agent systems incur 4-10× the token cost of single-agent; we quantify the break-even point.

**译文**: 我们的研究围绕三个问题展开:
1. **智能体数量如何影响性能?** 我们在 1 → 3 → 5 → 10 个智能体的规模上度量任务成功率。
2. **哪种协调模式最适合哪种任务?** 我们在 4 个任务领域上比较中心化、去中心化、混合三种模式。
3. **成本-质量权衡如何?** 多智能体系统的 token 成本是单智能体的 4-10 倍; 我们量化盈亏平衡点。

### 1.2 贡献 (Contributions)

**原文**:
- *Empirical scaling laws for agent systems* — the first systematic study varying agent count, coordination pattern, and workflow structure across 256 configurations.
- *A taxonomy of five architectural classes* — single, independent, centralized, decentralized, and hybrid — grounded in production systems.
- *Error amplification measurements* — we document 4.4× and 17.2× error rate amplification for centralized and independent coordination, respectively.
- *A practitioner's guide* — concrete recommendations on architecture choice by task type.

**译文**:
- **面向智能体系统的经验性扩展规律** — 首个在 256 种配置上系统变化智能体数量、协调模式、工作流结构的研究。
- **五大架构类别的分类法** — 单智能体、独立式、中心化、去中心化、混合 — 扎根于生产实践。
- **错误放大率度量** — 我们记录到中心化与独立式协调分别带来 4.4× 和 17.2× 的错误率放大。
- **实践者指南** — 按任务类型给出架构选择的具体建议。

## 3 五类架构 (The Five Architectures)

**原文**: We define five architectural classes that span the design space of production agent systems. The classes differ along two axes: *who decides* (centralized control vs. peer-to-peer) and *who executes* (one agent vs. many).

| 架构 | 决策权 | 执行权 | 典型代表 |
|---|---|---|---|
| **SINGLE** | 单一 | 单一 | AutoGPT, ReAct 单循环 |
| **INDEPENDENT** | 各 agent 独立 | N 个 agent 并行 | 多采样 + 投票, Self-Consistency |
| **CENTRALIZED** | 单一 planner | N 个 worker | MetaGPT, ChatDev, Magentic-One |
| **DECENTRALIZED** | N 个 peer | N 个 peer | 自由辩论, AutoGen GroupChat |
| **HYBRID** | 单一 verifier | N 个 executor | 去中心执行 + 中心校验 |

**译文**: 我们定义五大架构类别, 它们覆盖了生产智能体系统的整个设计空间。各类别沿两个轴线相互区别: **谁做决策** (中心化控制 vs. 点对点) 与 **谁做执行** (单一 agent vs. 多个 agent)。

| 架构 | 决策权 | 执行权 | 典型代表 |
|---|---|---|---|
| **SINGLE** (单智能体) | 单一 | 单一 | AutoGPT、ReAct 单循环 |
| **INDEPENDENT** (独立式) | 各 agent 独立 | N 个 agent 并行 | 多采样 + 投票、Self-Consistency |
| **CENTRALIZED** (中心化) | 单一 planner | N 个 worker | MetaGPT、ChatDev、Magentic-One |
| **DECENTRALIZED** (去中心化) | N 个 peer | N 个 peer | 自由辩论、AutoGen GroupChat |
| **HYBRID** (混合) | 单一 verifier | N 个 executor | 去中心执行 + 中心校验 |

**原文 (详细描述各架构)**:

- **SINGLE**: A single agent with a tool set, in a while loop. The agent decides what to do, executes, observes, and iterates. Failure modes: the agent gets stuck, runs out of context, or makes a single bad decision that propagates.

- **INDEPENDENT**: N agents, each with the same tools and prompt, run in parallel on the same task. They don't see each other's outputs. The orchestrator picks the best output (by self-consistency, verifier score, or LLM judge). Failure mode: agents make correlated errors (the LLM "mode-collapses" on the same wrong answer).

- **CENTRALIZED**: A planner agent decomposes the task into sub-tasks, dispatches to N worker agents, and aggregates results. Workers are typically specialized (e.g. "searcher", "coder", "tester"). Failure mode: planner's decomposition is wrong, or workers can't recover from bad sub-task definitions.

- **DECENTRALIZED**: N peer agents, each with their own specialty, pass messages to each other (round-robin, broadcast, or pub-sub). There is no planner. Failure mode: agents get into unproductive loops or contradict each other without a tie-breaker.

- **HYBRID**: N agents run in parallel (decentralized execution), but a single verifier checks each output (centralized verification). The first output that passes verification wins. Failure mode: verifier is too strict (no agent passes) or too loose (low-quality output passes).

**译文**:

- **SINGLE (单智能体)**: 单一 agent 携带工具集, 在 while 循环中运行。Agent 决定下一步动作、执行、观察、迭代。失败模式: agent 卡住、上下文耗尽、或一次糟糕决策的扩散。

- **INDEPENDENT (独立式)**: N 个 agent, 工具集与 prompt 相同, 在同一任务上并行运行。它们彼此看不到对方的输出。编排器挑选最佳输出 (按自一致性、验证器分数、或 LLM 评判)。失败模式: 智能体犯下相关错误 (LLM 在同一错误答案上"模式坍缩")。

- **CENTRALIZED (中心化)**: 一个 planner agent 把任务分解为子任务, 派发给 N 个 worker agent, 汇总结果。Worker 通常专精化 (例如"搜索者"、"编码者"、"测试者")。失败模式: planner 分解出错, 或 worker 无法从糟糕的子任务定义中恢复。

- **DECENTRALIZED (去中心化)**: N 个对等 agent, 各自专精, 彼此传递消息 (轮询、广播或发布订阅)。不存在 planner。失败模式: agent 陷入无效循环, 或在没有裁决者的情况下相互矛盾。

- **HYBRID (混合)**: N 个 agent 并行运行 (去中心执行), 但单一 verifier 校验每个输出 (中心校验)。首个通过校验的输出胜出。失败模式: 验证器过严 (无 agent 通过) 或过松 (低质量输出蒙混过关)。

## 4 关键发现 (Key Findings)

### 4.1 智能体数量的扩展规律 (Scaling Agent Count)

**原文**: We plot success rate as a function of agent count, holding the coordination pattern fixed. Three regimes emerge:
- **Diminishing returns (SWE D1, Math D1-D2)**: Going from 1 to 3 agents improves success by 12-18 percentage points. Going from 3 to 5 yields another 4-7 pp. Going from 5 to 10 yields < 1 pp. The curve flattens.
- **Negative returns (Math D3-D4, Sci D3-D4)**: Going from 1 to 3 agents *hurts* performance by 5-12 pp. More agents do not help; they add coordination overhead and disagreement cost.
- **Linear returns (Web D1-D2, parallelizable)**: Going from 1 to 10 agents yields 25-40 pp improvement, the largest in our study. The task is embarrassingly parallel.

**译文**: 我们把成功率绘制为智能体数量的函数, 固定协调模式。三种规律浮现:
- **递减回报 (SWE D1、Math D1-D2)**: 从 1 增到 3 个 agent 提升 12-18 个百分点。从 3 增到 5 再提 4-7 pp。从 5 增到 10 提升不到 1 pp。曲线趋于平缓。
- **负面回报 (Math D3-D4、Sci D3-D4)**: 从 1 增到 3 个 agent **反而**让性能下降 5-12 pp。更多 agent 帮不上忙, 反而引入协调开销与分歧成本。
- **线性回报 (Web D1-D2, 可并行任务)**: 从 1 增到 10 个 agent 提升 25-40 pp, 是本研究中的最大收益。这类任务是令人尴尬地并行的。

### 4.2 错误放大率 (Error Amplification)

**原文**: We define *error amplification* as the ratio of the multi-agent system's error rate to the single-agent error rate on the same task. For each architecture, we compute the mean amplification across all 16 (domain × difficulty) cells.

| 架构 | 错误放大率 (3 agents) | 错误放大率 (10 agents) | 主要机制 |
|---|---|---|---|
| **SINGLE** | 1.0× (基准) | 1.0× (基准) | — |
| **INDEPENDENT** | 6.2× | 17.2× | 模式坍缩: 多个 agent 犯同一错 |
| **CENTRALIZED** | 2.8× | 4.4× | Planner 分解错, worker 无法恢复 |
| **DECENTRALIZED** | 5.1× | 12.7× | 无裁决者, 群体陷入错误共识 |
| **HYBRID** | 1.6× | 2.3× | Verifier 阻断错误传播 |

**译文**: 我们把**错误放大率**定义为多智能体系统的错误率与单智能体在同一任务上的错误率之比。对每种架构, 我们在全部 16 个 (领域 × 难度) 单元上计算平均放大率:

| 架构 | 错误放大率 (3 agents) | 错误放大率 (10 agents) | 主要机制 |
|---|---|---|---|
| **SINGLE** | 1.0× (基准) | 1.0× (基准) | — |
| **INDEPENDENT** | 6.2× | **17.2×** | 模式坍缩: 多个 agent 犯同一错 |
| **CENTRALIZED** | 2.8× | **4.4×** | Planner 分解错, worker 无法恢复 |
| **DECENTRALIZED** | 5.1× | **12.7×** | 无裁决者, 群体陷入错误共识 |
| **HYBRID** | 1.6× | **2.3×** | Verifier 阻断错误传播 |

**原文 (摘译)**: The 17.2× amplification for INDEPENDENT at 10 agents is the most surprising finding. It means that 10 independent runs make 17× the mistakes of a single run, *in expectation*. The mechanism is mode-collapse: with 10 samples, you cover the LLM's output distribution more thoroughly, including its systematic error modes. If the LLM has a 5% chance of producing wrong answer X, then with 10 samples you have a 1-(0.95)^10 = 40% chance of seeing X at least once. Worse, the "best of N" selector often picks X because X looks superficially plausible.

**译文**: 独立式架构在 10 agent 时 17.2× 的放大率是最令人惊诧的发现。这意味着 10 次独立运行在期望上制造 17 倍于单次运行的错误。机制是**模式坍缩**: 采样数 10 让你更彻底地覆盖 LLM 的输出分布, 包括其系统性的错误模式。若 LLM 有 5% 概率产出错误答案 X, 那么 10 次采样你至少有 40% 概率见到 X。更糟的是, "N 选最优" 往往选中 X, 因为 X 在表面上貌似合理。

### 4.3 任务适用矩阵 (Task-Architecture Fit)

**原文**: No architecture is uniformly best. We summarize the *recommended* architecture for each (domain, difficulty) cell:

| | D1 (易) | D2 | D3 | D4 (难) |
|---|---|---|---|---|
| **SWE** | INDEPENDENT (3) | INDEPENDENT (5) | HYBRID (3) | SINGLE |
| **Math** | INDEPENDENT (3) | HYBRID (3) | SINGLE | SINGLE |
| **Sci** | INDEPENDENT (3) | HYBRID (3) | SINGLE | SINGLE |
| **Web** | INDEPENDENT (10) | INDEPENDENT (10) | HYBRID (5) | CENTRALIZED (3) |

**Pattern**: 容易且可并行任务 (SWE D1, Web D1-D2) → INDEPENDENT 多采样. 中等难度 (SWE D2, Sci D2) → HYBRID 混合校验. 高难顺序推理 (Math D3-D4, Sci D3-D4) → SINGLE 单 agent 最稳. 需要长程导航 (Web D4) → CENTRALIZED 单一规划.

**译文**: 没有一种架构在所有情形下都是最优。我们为每个 (领域, 难度) 单元推荐如下架构:

| | D1 (易) | D2 | D3 | D4 (难) |
|---|---|---|---|---|
| **SWE** | INDEPENDENT (3) | INDEPENDENT (5) | HYBRID (3) | SINGLE |
| **Math** | INDEPENDENT (3) | HYBRID (3) | SINGLE | SINGLE |
| **Sci** | INDEPENDENT (3) | HYBRID (3) | SINGLE | SINGLE |
| **Web** | INDEPENDENT (10) | INDEPENDENT (10) | HYBRID (5) | CENTRALIZED (3) |

**规律**: 容易且可并行任务 (SWE D1、Web D1-D2) → INDEPENDENT 多采样。中等难度 (SWE D2、Sci D2) → HYBRID 混合校验。高难度顺序推理 (Math D3-D4、Sci D3-D4) → SINGLE 单 agent 最稳。需要长程导航 (Web D4) → CENTRALIZED 单一规划。

### 4.4 成本-质量权衡 (Cost-Quality Tradeoff)

**原文**: Token cost scales roughly linearly with agent count. For Claude-3.5-Sonnet at $3/$15 per million input/output tokens, the per-task cost is:
- 1 agent: $0.04 (SWE) — $0.31 (Web D4)
- 3 agents: $0.12 — $0.93
- 10 agents: $0.40 — $3.10

The break-even point (when the success rate gain justifies the cost) varies by task. For Web D2, going from 1 to 10 agents improves success from 0.41 to 0.78 (+37 pp) at a 10× cost — a good trade. For Sci D4, going from 1 to 10 agents *hurts* success from 0.42 to 0.31 (-11 pp) at a 10× cost — a clear loss.

**译文**: Token 成本大致随智能体数量线性增长。Claude-3.5-Sonnet 输入/输出 $3/$15 每百万 token, 单任务成本如下:
- 1 agent: $0.04 (SWE) — $0.31 (Web D4)
- 3 agents: $0.12 — $0.93
- 10 agents: $0.40 — $3.10

盈亏平衡点 (成功率提升能覆盖成本) 因任务而异。Web D2: 1 → 10 agent 让成功率从 0.41 升到 0.78 (+37 pp), 代价是 10× 成本 — 划算。Sci D4: 1 → 10 agent 让成功率从 0.42 降到 0.31 (-11 pp), 代价 10× 成本 — 明显的亏损。

## 5 讨论 (Discussion)

**原文 (摘译)**: Our findings challenge three pieces of common wisdom. First, the assumption that "more agents = better" holds only for a narrow class of tasks (parallelizable, easy-to-verify). For most realistic tasks, agent count has diminishing or negative returns. Second, multi-agent coordination is *not* a free lunch — every architecture amplifies errors relative to a single agent, with amplification factors ranging from 1.6× (HYBRID) to 17.2× (INDEPENDENT). Third, the optimal architecture is task-dependent; blanket recommendations (e.g. "always use multi-agent") are wrong.

**译文**: 我们的发现挑战了三条常见经验法则。第一, "智能体越多越好"的假设仅对一类狭窄任务成立 (可并行、易于验证)。对多数现实任务, 智能体数量带来递减乃至负面回报。第二, 多智能体协调**不是**免费的午餐 — 每种架构相对于单智能体都会放大错误, 放大因子从 1.6× (HYBRID) 到 17.2× (INDEPENDENT) 不等。第三, 最优架构因任务而异; 笼统建议 (例如"总是用多智能体") 是错的。

### 5.1 实践者指南 (A Practitioner's Guide)

**原文**: Based on our findings, we offer the following decision procedure for choosing an agent architecture:
1. **Can the task be parallelized into independent sub-tasks?** If yes, INDEPENDENT (3-5 agents) with verification. If no, go to (2).
2. **Is the task verifiable in < 1 second?** If yes, HYBRID with cheap verifier (rule-based). If no, go to (3).
3. **Is the task long-horizon (≥ 20 steps)?** If yes, CENTRALIZED with explicit planner. If no, SINGLE.

**译文**: 基于我们的发现, 我们为选择智能体架构提出以下决策流程:
1. **任务能否被分解为独立子任务?** 若可以, 采用 INDEPENDENT (3-5 个 agent) 加验证。否则进入 (2)。
2. **任务能否在 < 1 秒内验证?** 若可以, 采用 HYBRID 加廉价验证器 (基于规则)。否则进入 (3)。
3. **任务是否长程 (≥ 20 步)?** 若可以, 采用 CENTRALIZED 加显式 planner。否则采用 SINGLE。

### 5.2 局限 (Limitations)

**原文 (摘译)**: We use a single LLM (Claude-3.5-Sonnet) to isolate the effect of system design. Stronger models may have different scaling curves. We use only 4 domains; robotics, embodied agents, and multi-modal tasks are not covered. We test up to 10 agents; production systems like AutoGen routinely run 30+ agents. Our error amplification analysis assumes verifier-independent errors; when errors are correlated (e.g. all agents use the same buggy tool), the amplification is even worse.

**译文**: 我们使用单一 LLM (Claude-3.5-Sonnet) 来隔离系统设计的影响。更强的模型可能呈现不同的扩展曲线。我们仅涉及 4 个领域; 机器人、具身智能体、多模态任务未覆盖。我们最多测到 10 个 agent; 像 AutoGen 这样的生产系统常规运行 30+ agent。我们的错误放大分析假设验证器独立; 当错误相关 (例如所有 agent 使用同一有缺陷工具) 时, 放大更严重。

### 6.1 AetherCode 已实现的 4/5 架构

- ✅ **SINGLE** — `AgentRuntime` 单 agent, V → self-correct → 单 ensemble
- ✅ **INDEPENDENT** — `IndependentStrategy` N agent 并行 (无 peer 可见)
- ✅ **CENTRALIZED** — `CentralPlanner` planner 派发 + N worker
- ⚠️ **DECENTRALIZED** — 设计文档提及, 实现暂缓
- ✅ **HYBRID** — `HybridStrategy` 去中心执行 + 中心验证

### 6.2 AetherCode 尚未实现的 paper 关键洞察

- **模式坍缩防御**: 多个 INDEPENDENT agent 共享 prompt 容易"模式坍缩"。Paper 建议 prompt 多样化 (temperature, few-shot example 改写) — AetherCode 当前 `VoteStrategy` 用相同 prompt, 应加入 `promptDiverseFactor`
- **Verifier 廉价化**: Paper 强调 HYBRID 的 verifier 必须 < 1 秒。`RuleVerifier` 满足; 但 `LlmJudgeVerifier` 走 LLM 调用太慢, 应缓存常见 verdict
- **CENTRALIZED 的 planner 必须有反馈回路**: 当前 `CentralPlanner` 一旦 dispatch 就 fire-and-forget, 缺 planner 看到 worker 错误后重分解的能力

### 6.3 论文的局限性对应 AetherCode 改进方向

- **单 LLM 局限**: AetherCode 多 LLM 路由是 R-A2A 议题, 尚未在 orchestration 层实现
- **10 agent 上限**: AetherCode `IndependentStrategy` 实测 5-10 个, 30+ agent 需 优化通信拓扑
- **错误相关性未量化**: `ByzantineDetector` 部分覆盖 (echo attack), 但工具相关错误未建模
