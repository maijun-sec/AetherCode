# R108-3: multica-protocol 兼容 (Kanban 风格)

**Date:** 2026-08-13
**Status:** SHIPPED (基础架构 + Kanban UI; 完整 multica 协议适配 deferred)
**Impact:** TaskRegistry now streams every change to all connected
clients; the desktop's right panel has a "Tasks" tab with a 5-column
Kanban board (Pending / Running / Completed / Failed / Killed) that
supports drag-drop status transitions and live updates via WS.

## 背景 (Context)

multica-ai/multica (22.7k stars) is a "managed agents" platform that
turns coding agents into teammates via a Kanban board. Each agent is
a board member, every task is a card, status transitions are visible
in real time, and comments / blockers flow through a WebSocket from
the server to every connected client.

AetherCode's existing task model (`org.aethercode.tasks.Task` +
`TaskRegistry`) already mirrors the multica concept: tasks have a
type (USER / AGENT / SUBAGENT / SYSTEM), a status lifecycle
(pending / running / completed / failed / killed), and a
parent/child tree. The R108-3 work makes this visible to the
desktop and gives the user Kanban-style affordances for managing
their own tasks.

A full multica-protocol adapter (issue body, assignee, labels, PR
linking, autopilots, runtime detection, etc.) is a multi-week
project. R108-3 ships the *infrastructure* that a multica adapter
would build on: WS push, drag-drop status transitions, the
Kanban-style data model. A future R-round can layer the multica
HTTP/REST surface on top.

The user said "如果遇到无法支持的情况优先优化底层" — R108-3
优化了底层 (TaskRegistry's WS exposure + Kanban model), and
the multica-specific compatibility is deferred to a follow-up
when the user can commit to a multica-specific scope.

## 设计 (Design)

### Engine: TaskRegistry → WS push

`AetherCodeEngine.setTaskPush(Consumer<Map<String,Object>>)` mirrors
R108-1's `setTranscriptPush`. The first call with a non-null push
installs a `TaskRegistry.onChange` listener that fans out a
`task_event` notification:

```java
{
  "action": "create" | "update",
  "task": {
    "id": "u-3a7f9b2c",
    "type": "user" | "agent" | "subagent" | "system",
    "status": "pending" | "running" | "completed" | "failed" | "killed",
    "description": "...",
    "parentTaskId": "u-..." | null,
    "createdAtMs": 1234567890,
    "endedAtMs": 0
  }
}
```

`DaemonRunner.runHttp` wires the push to
`HttpJsonRpcServer::broadcast("task_event", payload)`, the same
way R108-1 wired transcript pushes. The listener is
process-singleton (TaskRegistry.instance()), so a single
WebSocket broadcast reaches every connected client.

### RPCs: listTasks / createTask / updateTaskStatus

- `listTasks` — R108-3 returns the real TaskRegistry's live
  task list (pre-R108-3 derived tool calls from the transcript,
  which is now retired). The shape matches the taskEvent push
  payload so the same adapter handles both paths.
- `createTask({description, type, parentTaskId?})` — mint a
  new task in PENDING. Returns the new task; the daemon also
  fires a `task_event` (action=create) for free.
- `updateTaskStatus({id, status})` — transition a task. The
  TaskRegistry is idempotent for terminal states (a
  `completed` task stays `completed` even on a
  `updateStatus(pending)` call). The daemon also fires a
  `task_event` (action=update).

All three are wired in `AetherCodeMethods.registerAll` and the
`HttpJsonRpcServer` dispatch switch (the same pattern R107-G
used for `getEngineStats` / `setConcurrencyProfile`).

### Renderer: Right-panel tab + Kanban

The right panel now has a tab toggle: "Telemetry" (the existing
sections) and "Tasks" (the new Kanban). The Kanban shows five
columns (Pending / Running / Completed / Failed / Killed) and
one card per task. Cards are draggable; dropping a card on a
different column calls `updateTaskStatus`. The "+" button above
the board calls `createTask`.

The store's `task_event` subscriber keeps the board in sync
without polling — every daemon-side transition becomes a
local state update within milliseconds. The create / drag-drop
actions also do an *optimistic* local update so the user
doesn't see a flicker while the WS round-trip completes; the
`task_event` arrival later replaces the optimistic entry
(by id) rather than duplicating it.

### Status set: 'cancelled' → 'killed'

The pre-R108-3 TaskInfo had `'cancelled'` as the terminal
cancellation status; the engine's TaskStatus enum has
`'killed'`. R108-3 normalises the renderer to `'killed'` as
the canonical value. The legacy `cancelTask` action now writes
`'killed'`; the existing CSS class names
(`.task-status-cancelled`) are kept as aliases so the
pre-R108-3 `TaskList` view still renders.

## 风险 (Risks) / 已知限制 (Known limitations)

- **Optimistic update race**: the store does an optimistic
  local update on `createTask` / `updateTaskStatus`, then
  the WS push replaces the same id. If the daemon rejects
  the call (e.g. invalid status), we roll back. A
  double-click during the round-trip can land two creates;
  the duplicate task_event has the same id (UUID, server-
  generated) so the dedupe-by-id keeps the state
  consistent.
- **No multica-specific HTTP/REST surface**: R108-3 is
  the infrastructure; the actual `multica issue create` /
  `multica issue assign` / PR linking / runtime
  detection / autopilots are deferred. A future R-round
  can layer the multica REST adapter on top of the
  TaskRegistry + WS push.
- **Status mapping drift**: pre-R108-3 code wrote
  `'cancelled'`; R108-3 normalises to `'killed'`. The
  legacy CSS classes (`.task-status-cancelled`) are kept
  as aliases. A future R-round can drop them.
- **Card width is fixed (140px)**: very long descriptions
  are truncated to 80px with overflow:hidden. A future
  R-round can add an expand-on-click affordance.
