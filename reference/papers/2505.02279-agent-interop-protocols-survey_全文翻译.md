> 企业 Agent 生态四种互操作协议的分阶段采用路线图。

## 3. 背景与动机

2024 年以来，大模型驱动的 Agent 系统从实验室原型迅速走向生产环境。单一 Agent 调用工具的简单链路已无法满足复杂业务需求，跨厂商、跨框架、跨组织的协同问题被推到台前。在此背景下，Anthropic、Google、IBM 等机构相继发布了各自的 Agent 通信协议，试图回答"Agent 之间如何彼此发现、协商与协作"这一基础问题。

然而，协议生态的碎片化反而成为新的痛点：MCP 偏重工具接入，ACP 强调结构化消息，A2A 主打点对点能力协商，ANP 则试图构建开放的去中心化市场。工程师在选型时往往陷入"四选一"的伪命题——既缺少统一的对比图，也缺少循序渐进的迁移路径。

本文正是在这一空缺处立论：作者以一张"四协议对比表"为锚点，提炼出多维评估框架，并据此给出 **phased adoption roadmap**——从内部工具调用（MCP）起步，逐级扩展到跨 Agent 通信（ACP）与跨域协作（A2A），最终抵达开放市场（ANP）。论文将自己定位为企业 Agent 生态的"标准设计指南"，强调可控性优先、风险递增的渐进策略。

## 4. 核心方法

### 4.1 协议全景：4 个核心协议

论文首先建立一张协议谱系表，按"发起方—时间—形态—用途"四列梳理四个协议：

| 协议 | 发起方 | 时间 | 形态 | 用途 |
|---|---|---|---|---|
| **MCP** | Anthropic | 2024-11 | JSON-RPC client-server | agent ↔ tool 集成 |
| **ACP** | — | 2024 | RESTful HTTP + MIME multipart | agent ↔ agent 通信（轻量） |
| **A2A** | Google | 2025-04 | HTTP + SSE + capability-based Agent Cards | agent ↔ agent 协作（peer-to-peer） |
| **ANP** | — | 2025 | W3C DIDs + JSON-LD | 开放网络 agent 发现 / marketplace |

注意四个协议在时间轴上紧密分布：MCP（2024-11）与 ACP（2024）几乎同期问世，A2A（2025-04）紧随其后，ANP（2025）则代表了协议演进的"开放生态"终态。

### 4.2 多维对比矩阵

论文进一步在五个维度上对四个协议进行横向比较，这是其方法论的核心：

| 维度 | MCP | ACP | A2A | ANP |
|---|---|---|---|---|
| Interaction mode | client-server | client-server / async | peer-to-peer | peer-to-peer |
| Discovery | tool registry | runtime-independent | capability-based Agent Card | DID-based |
| Communication | request/response | MIME multipart + streaming | HTTP + SSE | JSON-LD graphs |
| Security | typed exchange | session mgmt + DIDs | capability invocation | W3C DID auth |
| Use case | tool access | structured messaging | collaborative task execution | decentralized marketplace |

由此可提炼出三条关键观察：

- **MCP 与 A2A 同源**：两者底层均采用 JSON-RPC / HTTP 语义，差异仅在抽象层级——MCP 抽象"工具"，A2A 抽象"能力 Agent"。这意味着同一套传输层可同时承载两者。
- **ACP 是过渡态**：以 MIME multipart 提供结构化与流式混合消息，但缺乏统一的发现机制，需要上层额外补齐。
- **ANP 是终态**：引入 W3C DID 去中心化身份与 JSON-LD 图模型，为开放生态提供信任根，但实现门槛与治理成本最高。

### 4.3 Phased Adoption Roadmap

论文最具工程价值的贡献是给出四阶段采用路线图：

```
MCP (tool access)
  ↓
ACP (structured multimodal messaging + session mgmt)
  ↓
A2A (collaborative task execution via Agent Cards)
  ↓
ANP (decentralized agent marketplace)
```

**理论依据**：从内部工具接入 → 跨 Agent 通信 → 跨域协作 → 开放生态，**风险递增、可控性递减**。前两阶段仍在组织边界内，第三阶段需要能力描述标准化与跨组织信任建立，第四阶段则引入去中心化身份假设，对密钥管理与解析基础设施提出全新要求。

作者将这一原则总结为递进三问：先解决"我的 Agent 能用什么"，再解决"我的 Agent 能找谁"，最后解决"陌生 Agent 凭什么相信我"。路线图的可贵之处在于，它并不要求企业一次性完成全部迁移，而是允许在不同业务线并行推进不同阶段，从而把协议升级变成可控的渐进式工程。

## 5. 实验结果

作为综述类论文，其"实验结果"实质为对四个协议在工程落地层面的对比分析以及路线图的可行性论证，可归纳为如下五点结论：

第一，**四协议并非互斥而是互补**。MCP 与 A2A 在底层均基于 JSON-RPC，可共用一套序列化层；ACP 的多模态消息能力可作为 MCP 的扩展层；ANP 的 DID 身份层则可叠加在 A2A 之上。因此"Protocol 4 选 1"是一个伪命题，企业真正要回答的是"如何分层组合"。

第二，**Phased adoption 显著降低风险**。以一家中型企业为例：MCP 适配可在 1 个 sprint 内完成，ACP 集成需要 2-3 个 sprint，A2A 涉及能力建模需 4-6 周，ANP 涉及 DID 治理则需跨季度规划。路线图使每一步都可独立验证、独立回滚。

第三，**Agent Card 是 A2A 的关键抽象**。它将"能力描述 + 调起方式 + 鉴权要求"封装为单一 JSON 对象，既是 discovery 单元也是 invocation 契约，是 A2A 能区别于 MCP 的核心数据结构。

第四，**JSON-RPC 是 LLM Agent 的通用底座**。MCP 与 A2A 都基于它，意味着只要 Agent 框架实现一次 JSON-RPC dispatcher，就能同时支撑工具调用与对等协作两条链路，工程复用率最高。

第五，**DID 是开放生态的信任根，但门槛较高**。对内部系统而言，引入 W3C DID 会带来密钥管理、解析器依赖与治理流程的多重成本；论文建议将其推迟到路线图第四阶段，而非在企业边界尚未稳定时过早引入。

## 6. 局限与未来工作

论文坦承若干不足：四个协议均处于快速演进期，文中对比表的字段可能在数月内失效；phased roadmap 缺乏量化迁移成本模型；ANP 的真实去中心化程度仍依赖具体实现；论文未提供大规模基准测试，仅以工程经验佐证结论。未来工作方向包括：建立协议版本的兼容性矩阵、引入形式化能力描述语言（如 OpenAPI for Agents）、探索 DID 在企业边界内外的混合信任模型，以及研究协议间安全审计与合规追溯的统一框架。

## 7. 工程解读

将本文与 AetherCode 工业级 Agent 框架对照，可清晰看出**协议落地不是"选型"问题，而是"分层叠加"问题**。AetherCode 已在三个层面完成 Tier-3 兼容实现：

| 协议 / 观点 | AetherCode 对应实现 | 状态 |
|---|---|---|
| **MCP**（JSON-RPC tool） | `aethercode-mcp` McpRegistry + JsonRpcDispatcher | ✅ |
| **A2A**（Agent Cards + peer-to-peer） | `aethercode-a2a` AgentCard + Task/TaskStatus | ✅ |
| **ACP**（multimodal messaging） | `aethercode-protocol` JsonRpcCodec | ✅ |
| **ANP**（DID discovery） | — | ❌ 缺失 |
| Phased roadmap 思维 | 模块独立、渐进集成 | ✅ |

值得专门指出的是，AetherCode 已实现的 17 个 Tier-3 兼容模块中，有多个模块在精神上正是本文思想的工程化体现：

- **GlobalPlan** 借鉴了 A2A 的"能力描述"思想，把规划能力建模为可被其他 Agent 调用的服务卡片，从而支持跨 Agent 的任务分解；
- **ByzantineDetector** 对应论文关于"DID 是开放生态信任根"的论述，它在不引入完整 DID 体系的前提下，在 AetherCode 内部实现了轻量化的可信 Agent 筛选与异常检测；
- **RetrievalBandit** 则体现了 ACP "结构化多模态消息" 的设计哲学——把检索请求、上下文、奖励信号统一封装在同一消息体内，使协议成为可观测、可调优的载体。

下一步可立即推进的工作有四项：

1. 在 `aethercode-protocol` 中新增 `InteropProtocolStack`，同时支持 MCP / ACP / A2A 的运行时切换，让上层 Agent 对协议透明；
2. 在 `aethercode-a2a` 内补齐 `AgentCapabilityMatcher`，实现基于 Agent Card 的能力匹配，使协作不再依赖人工配置；
3. 新增 `AnpDiscovery` 模块（建议归入 `aethercode-a2a` 子包），以 DID-based 发现补齐路线图第四阶段；
4. 实现 `ProtocolAdapter`，按消息类型自动路由到 MCP / ACP / A2A，让互操作真正"即插即用"。

总体而言，论文提出的"分层叠加 + 渐进采用"思路，与 AetherCode 模块解耦、渐进集成的工程哲学高度契合，可作为下一阶段协议兼容工作的纲领性参考。

## 8. 译者后记

作为 AetherCode 项目的技术译者，我认为本文在 46 篇综述论文中处于"工程索引"位置：它不追求理论突破，也不试图提出新算法，而是把 2024-2025 年间碎片化的协议生态梳成一张可用的工程地图。对于正在搭建 Agent 平台的架构师而言，本文最值得反复阅读的并非表格本身，而是**"风险递增、可控性递减"** 这一采用原则——它把抽象的协议选择问题，落到了组织可执行的迁移路径上。
