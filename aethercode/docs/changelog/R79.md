# R79 — Trace tree + `/trace <id>` (2026-08-09)

## Goal

R78 recorded spans as a flat list — the user could see "a query
took 4.5s, a glob took 200ms" but not the *relationship*
between them. R79 adds parent linkage and a tree view so the
user can see "this query called these tools, in this order,
with these timings". The shape is intentionally simple:
**one root span (`query`) + child spans (`tool.<name>`)**
nested underneath. The full OpenTelemetry parent / context
mechanism is overkill for this UI.

## What changed

| Layer | Before (R78) | After (R79) |
|---|---|---|
| `Span` record | `(traceId, name, startMs, endMs, status, attrs)` | + `parentSpanId: String` |
| `startSpan(name, attrs)` | root only | delegates to `startChildSpan(null, name, attrs)` (back-compat) |
| `startChildSpan(parentId, name, attrs)` | n/a | new — links the new span to a parent |
| `getTrace(traceId)` | n/a | new — BFS over `completed` returning root + all descendants |
| `getTraces` shape | spans without `parentSpanId` | each span now carries `parentSpanId` (null for roots) |
| `getTrace` RPC | n/a | new — `{traceId, inFlight, completed, spans: [...]}` |
| TUI render | flat list of recent spans | new tree render with `├─` / `└─` / `│` connectors |
| `/trace <id>` | n/a (numeric only) | new — first arg starting with `tr-` → `getTrace(id)` |

## Pattern: same as R78 (backend + TUI)

R79 follows the same recipe as R78. The only structural
difference: the new RPC + TUI command take a **traceId** instead
of a numeric **limit**, and the TUI render draws a tree
instead of a table. The per-round workflow (6 doc files +
per-round retro + R33-R82 index update) is identical.

## Backend

### `TraceRecorder.java`

- `Span` record now carries `parentSpanId`. R78 callers
  using `startSpan(name, attrs)` still work — `startSpan`
  is a thin wrapper around `startChildSpan(null, name, attrs)`
  so the back-compat path is a one-liner.
- `startChildSpan(parentSpanId, name, attrs)` is the
  explicit "I'm a child of `parentSpanId`" API. The parent
  doesn't need to be in-flight or even known — the recorder
  is best-effort and doesn't validate.
- `getTrace(traceId)` uses BFS over the completed deque:
  1. Pick the root (span whose `traceId == traceId`).
  2. Index every completed span by `traceId` in a Map.
  3. BFS: each iteration finds spans whose `parentSpanId` is
     in the current frontier; add to the result and expand
     the frontier.
  4. Return the result list (root first, then descendants
     in BFS order).

  If the root has been evicted by the bounded deque, the
  surviving descendants are still returned — the TUI renders
  them as "orphans" with a header `(root … not in the
  recorder)`. In-flight roots are NOT returned (consistent
  with the rest of the API which only sees completed spans).
- `snapshotForTrace(traceId)` is the JSON-friendly version
  of `getTrace(traceId)`. Returns
  `{traceId, inFlight, completed, spans: [...]}`.

### `AetherCodeMethods.java`

- New RPC: `getTrace({traceId: String})` →
  `engine.traces().snapshotForTrace(traceId)`.
- `query()` worker thread now opens tool spans with
  `startChildSpan(queryTraceId, "tool." + name, ...)`
  instead of `startSpan(...)`. The parent linkage is
  recorded automatically.

## TUI

### `state.ts`

- `TraceSummary` extended with `parentSpanId: string | null`.
- New state fields: `spanTree: TraceSummary[]` and
  `selectedTraceId: string | null`.
- New action: `setSpanTree` (capped at 64 spans).

### `commands.ts`

- `case "trace"`:
  - `/trace 50` → still `getTraces({limit: 50})`.
  - `/trace <id>` where `<id>` starts with `tr-` → new
    `getTrace({traceId: <id>})`. The branch order matters:
    we check the `tr-` prefix BEFORE the numeric parse,
    so `tr-1` is treated as a traceId, not as `limit: 1`.

### `tui.tsx`

- After `getTrace` RPC succeeds: dispatch `setSpanTree` AND
  pretty-print the tree inline with `├─` / `└─` / `│`
  connectors.

- The render is a small recursive function:
  ```ts
  const emit = (node, prefix, isLast) => {
    const connector = prefix === "" ? "" : (isLast ? "└─ " : "├─ ");
    lines.push(`  ${prefix}${connector}${icon} ${name}  ${durStr}  ${status}`);
    for (let i = 0; i < kids.length; i++) {
      const k = kids[i];
      const childPrefix = prefix === "" ? "  "
                          : (prefix + (isLast ? "   " : "│  "));
      emit(k, childPrefix, i === kids.length - 1);
    }
  };
  ```

- The BFS-then-emit split lets the recorder stay simple
  (just the BFS + an emit-on-find order doesn't quite
  work because a parent's first child should appear before
  any grandchild). We use two passes: BFS to collect
  `wantIds`, second pass to emit in deque order. This keeps
  the result list rooted at the requested `traceId`.

- Orphans (spans whose parent is missing from the spans
  list) are collected under the sentinel key
  `__orphans__` and rendered flat at the top of the panel
  with a `(root … not in the recorder — showing orphans)`
  header.

## Pitfalls (R79)

1. **Tree emit order ≠ deque order.** The `completed`
   deque is in end-time order (oldest endMs first). For the
   tree, the root must be FIRST and the parent's children
   must come BEFORE any grandchild. The first attempt used
   "BFS to collect ids, then second pass to emit in deque
   order" — this works for direct children but fails for
   deeper trees because the deque order doesn't match
   tree order at depth ≥ 2. The fix was to emit
   *during* the BFS: each iteration appends to the
   result list as soon as we discover a span, then advances
   the frontier. The root is added first (before the
   BFS starts), so the result is `[root, …children,
   …grandchildren, …]` in correct tree order.
2. **Wire children into EVERY node, not just the root.**
   The first pass of the tree builder only set
   `rootNode.children`; grandchild lookups failed because
   `tr-a.children` was still empty. Fix: iterate the
   `byId` map and assign each node's children from the
   `childrenOf` map. The `for ([id, node] of byId)` loop
   is the single line that fixed the grandchild test.
3. **Orphans: a span is an orphan iff its parent is
   missing from the spans list — NOT iff its
   `parentSpanId == null`.** The first implementation
   collected `parentSpanId == null` spans as "orphans"
   and rendered them with a missing-root header. But a
   real root span (parentSpanId == null) should be the
   root, not an orphan. The fix: orphans are spans whose
   `parentSpanId` is non-null but whose parent is not in
   `byId`. Orphans are collected under the sentinel
   `__orphans__` key.
4. **`/trace` arg detection order matters.** `tr-1` could
   be parsed as a numeric `limit: 1`. The fix: check the
   `tr-` prefix FIRST in `handleSlash`. If it matches,
   route to `getTrace`; else parse as a number and route
   to `getTraces`.

## What's next (R80+)

- **R80 candidate: live trace pane.** Subscribe to a
  streaming notification (`trace_event` or piggy-back on
  `stream_event`) so the user sees in-flight spans
  without typing `/trace`. Pattern: similar to R37
  sidebar's `task_state` notification + listTasks
  polling, but with push instead of pull.
- **R80 candidate: span tree persistence.** Spans
  currently live only in memory. A long-running session
  loses them on daemon restart. Persist to
  `~/.aethercode/traces.jsonl` (one span per line) so
  `/trace <id>` works after a restart.
- **R81 candidate: audit log.** Persist every
  `permission_request` and `permission_response` to
  `~/.aethercode/audit.jsonl`. `/audit tail` shows the
  last 20 entries.
- **R82 candidate: `/trace --live`.** A flag that
  re-polls `getTrace` every 1s while the user watches
  the panel. Goes away when the root is `ok` / `error`.

The "engine observability" axis now has three rounds in a
row (R77 metrics, R78 traces, R79 tree). The next axis
is "task execution": DagPlan + PlanExecutor are already
in `aethercode-sdk`; an `executeDag` RPC + `/dag` command
would be the first user-visible piece of multi-step task
execution. After that, the axis is "long-running" (caching
across restarts, checkpoint + resume, etc.).
