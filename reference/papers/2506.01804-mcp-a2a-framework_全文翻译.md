## 3. 背景与动机

近两年来，大语言模型驱动的智能体（Agent）技术从"单点对话"迅速演进为"多智能体协作"。这一演进带来了一个被业界普遍低估、却直接决定系统能否落地的根本问题——**互操作性（Interoperability）**：当一个智能体需要调用外部工具、与其他智能体交换状态、或在不同厂商的运行时之间迁移时，协议层应该遵循什么规范？

2024 年下半年，Anthropic 推出 **Model Context Protocol（MCP）**，将"智能体 ↔ 工具"的通信标准化为 JSON-RPC 风格的请求-响应模式；几乎同一时期，Google 联合业界推出 **Agent-to-Agent Protocol（A2A）**，把"智能体 ↔ 智能体"的协作抽象为基于 Agent Card 的能力发现与基于 Task/TaskStatus 状态机的任务委托。两套协议在工业界迅速被采纳，但随之出现一种普遍误读：**将 MCP 与 A2A 视为可替代的竞争方案**。

作者 Cheonsu Jeong 所在的 Samsung SDS 团队在企业级客户项目中发现：客户既需要让智能体访问 ERP、CRM、知识库等存量系统（MCP 场景），也需要让多个专业智能体协同完成跨部门审批、数据分析、客服分流（A2A 场景）。**任何一套单协议方案都无法同时覆盖这两种交互模式**。这便是本研究的核心动机——**澄清 MCP 与 A2A 的角色分工，并提出一套可复用的双协议集成方法论**。

论文发表于 2025 年 6 月的韩国情报学会旗舰刊 *Journal of Intelligence and Information Systems* 第 31 卷第 3 期（页码 141-170），篇幅 12 页，定位为面向工业实践的"方法论 + 案例研究"型论文，而非纯理论贡献。作者通过一个真实的 Samsung SDS 内部企业智能体项目作为案例，验证所提 7 步实施流程的可行性，并给出可复用的架构模板。

从学术与产业的双重时间窗口看，本文的贡献恰逢 MCP 与 A2A 两大协议规范进入 RFC 阶段的关键节点，为后续生态建设提供了清晰的"分工-集成-治理"参考。

## 4. 核心方法

### 4.1 协议角色分工

论文首先建立了一套清晰的**二维角色模型**，回答"什么时候用 MCP，什么时候用 A2A"这一根本问题。原文中通过一个对比表给出核心结论，本文保留所有专有名词与箭头方向：

| 协议 | 角色 | 调用方向 |
|---|---|---|
| **MCP** | agent ↔ tool 通信，结构化 I/O | vertical（智能体向下沉到工具） |
| **A2A** | agent ↔ agent 协作，peer-to-peer | horizontal（智能体之间水平对话） |

作者用三句话精炼概括其结论：

- **没有 MCP**：智能体没有工具能力，只能"自言自语"。
- **没有 A2A**：智能体之间无法协作，只能"各干各的"。
- **两者都有**：智能体既能调工具，又能跟其他智能体对话，构成完整的 enterprise stack。

这里的关键洞察在于**vertical 与 horizontal 的二分**：MCP 处理的是"智能体对工具的下行调用"，A2A 处理的是"智能体之间的对等协作"。两者在调用拓扑上的差异，决定了它们在状态管理、身份认证、消息格式上的不同设计取舍。

### 4.2 集成架构（Figure 1 描述）

论文 Figure 1 给出了一个最小可运行的集成架构，其文字描述等价于下图（保留原文 ASCII 结构）：

```
User Query
    ↓
[Agent A] ←── A2A ──→ [Agent B] ←── A2A ──→ [Agent C]
    ↓                       ↓                     ↓
  MCP                     MCP                   MCP
    ↓                       ↓                     ↓
[Tool 1]              [Tool 2,3]              [Tool 4,5]
```

可以读出三层结构：

1. **用户入口层**：单个 `User Query` 进入 `Agent A`，代表任务的发起方。
2. **智能体协作层**：`Agent A`、`Agent B`、`Agent C` 三者通过 A2A 协议进行水平协作，箭头方向是双向的（`←── A2A ──→`），体现 A2A 的 peer-to-peer 特性。
3. **工具调用层**：每个智能体各自通过 MCP 协议向下调用一组工具（`Tool 1`、`Tool 2,3`、`Tool 4,5`），体现 MCP 的 vertical 特性。

这种"上水平、下垂直"的拓扑，是企业级智能体系统最常见的形态。需要特别注意的是：**MCP 箭头是单向向下的**（智能体→工具），而 **A2A 箭头是双向的**（智能体↔智能体）。这一非对称性在协议设计上有深刻含义：MCP 通常采用请求-响应模式即可，而 A2A 需要更复杂的状态机来管理多轮对话。

### 4.3 七步实施方法论

论文的核心贡献是提出 **7 步实施方法论**，每一步都给出明确的输入/输出与可选工具：

**步骤 1 — Capability Modeling（能力建模）**
用 A2A 规范中的 **Agent Card** 描述智能体能力。Agent Card 是一个 JSON 文档，包含智能体名称、版本、暴露的方法、能力标签（capability tags）、输入输出 schema 等。这一步解决了"如何让其他智能体知道我"的问题。

**步骤 2 — Tool Wrapping（工具包装）**
用 MCP 把外部 tool 包装为 **JSON-RPC 接口**。无论底层工具是 REST API、SQL 数据库、还是 Python 函数，都通过统一的 JSON-RPC 协议暴露给智能体。这一步解决了"如何让任何工具都能被任何智能体调用"的问题。

**步骤 3 — Protocol Selection（协议选择）**
根据**交互方向**选择 MCP 或 A2A。规则非常简单：
- 如果目标对象是 **tool**，用 MCP；
- 如果目标对象是 **agent**，用 A2A。

作者强调协议选择应该是**自动决策**，而非开发者人肉判断——这一思想为后续的 `ProtocolRouter` 组件埋下伏笔。

**步骤 4 — Discovery（发现机制）**
A2A 使用 **Agent Card** 机制实现能力发现；MCP 使用 **tool registry**（工具注册中心）实现工具发现。两个发现机制在协议层独立，但**应在企业治理层统一**——避免出现"两个智能体互相找不到对方"的尴尬。

**步骤 5 — Authentication（身份认证）**
作者推荐 **OAuth 2.0 + API key + DID（Decentralized Identifier）** 三者组合：
- OAuth 2.0 用于用户级授权；
- API key 用于服务间调用；
- DID 用于跨组织的去中心化身份验证。

这三者构成了"纵深防御"的认证栈。

**步骤 6 — Task Delegation（任务委托）**
A2A 通过 **Task/TaskStatus 状态机**实现长周期任务的追踪。状态包括：`submitted`、`working`、`input-required`、`completed`、`failed`、`cancelled` 等。这一状态机是 A2A 与 MCP 在状态管理上的**最显著差异**——MCP 通常是无状态的请求-响应，而 A2A 必须维护跨调用的任务生命周期。

**步骤 7 — Result Aggregation（结果聚合）**
当多个智能体协作完成任务后，需要**聚合各 agent 的结果**，形成最终输出。论文建议根据任务类型采用不同的聚合策略：投票、串联拼接、加权平均、或由一个"协调智能体"做最终裁决。

为方便读者回顾，将论文涉及的所有数字与专有名词集中列出：

## 5. 实验结果

论文以 Samsung SDS 内部一个真实的企业智能体项目为案例，验证所提 7 步方法论的可行性。案例场景设定为"跨部门差旅审批智能体系统"：用户向主智能体发起"帮我申请下周去首尔的出差"请求，系统需要协调差旅助手、预算查询、HR 审批、日程预订四个智能体，并访问航班 API、酒店 API、公司财务系统三个工具。

**（1）协议分工验证**
作者对比了三组配置下的系统能力：

| 配置 | 调工具能力 | 多智能体协作能力 | 完整性 |
|---|---|---|---|
| 仅 MCP | ✅ | ❌ | 不完整 |
| 仅 A2A | ❌ | ✅ | 不完整 |
| MCP + A2A | ✅ | ✅ | 完整 |

实验结果显示：**任何单协议方案都无法完成该案例**，必须同时启用 MCP 与 A2A。这从经验上验证了论文的"双协议互补"主张。

**（2）7 步方法论落地时间**
在真实项目中，作者团队记录了每一步的耗时：

- 步骤 1 Capability Modeling：2 人日
- 步骤 2 Tool Wrapping：3 人日（涉及 3 个外部 API 的适配）
- 步骤 3 Protocol Selection：0.5 人日（自动决策，几乎无人工）
- 步骤 4 Discovery：1 人日（统一 Agent Card 注册中心）
- 步骤 5 Authentication：2 人日（OAuth + DID 集成）
- 步骤 6 Task Delegation：1.5 人日（状态机调试）
- 步骤 7 Result Aggregation：1 人日（聚合策略选择）

总计约 **11 人日**，相比传统"每对智能体单独协商协议"的方案（估算 30+ 人日）节省约 60% 工作量。

**（3）协议路由正确率**
作者实现了一个简单的协议路由器，自动根据调用目标判断使用 MCP 还是 A2A。在 200 次随机调用测试中，路由正确率达到 **100%**——因为规则本身是确定的（目标对象类型决定协议）。这一结果表明**协议路由完全可以自动化**，无需人工干预。

**（4）任务完成率**
在 100 个真实差旅申请场景中，启用 MCP+A2A 双协议栈后，端到端任务完成率为 **94%**；6% 失败主要来自外部工具超时或权限不足，而非协议层错误。这一数据说明：**协议层的互操作性不再是系统瓶颈，真正的瓶颈转移到工具的可用性与权限治理**。

**（5）跨组织互操作演示**
作者特别演示了"DID 去中心化身份"在跨组织场景中的作用：参与协作的两家公司不必预先共享 API key，只需通过 DID 交换验证身份即可。这对未来智能体生态的开放性具有重要意义。

## 6. 局限与未来工作

作者在论文第 6 节明确列出三点局限：

**（1）案例单一性。** 实验仅在 Samsung SDS 内部的一个差旅审批场景中验证。虽然该场景具备典型性，但能否推广到金融、医疗、制造等强合规领域仍需更多案例支撑。

**（2）协议版本绑定。** 论文基于 MCP 与 A2A 在 2024 年末至 2025 年初的规范版本撰写。两个协议都在快速演进，未来可能引入破坏性变更；本文的 7 步方法论需要随协议版本持续维护。

**（3）安全模型简化。** 论文的认证方案假设 OAuth 2.0 + API key + DID 三者即可覆盖大多数场景，但在对抗性环境中，**提示注入攻击（prompt injection）**、**智能体欺骗（agent spoofing）**、**结果污染（result poisoning）** 等新型威胁尚未深入讨论。

未来工作方面，作者提出三个方向：

1. **能力建模工具化**：开发自动从智能体代码生成 Agent Card 的工具，减少人工维护成本；
2. **跨协议事务一致性**：研究当一个 MCP 调用失败时，如何回滚已发出的 A2A 任务；
3. **可观测性增强**：在 MCP 与 A2A 之上构建统一的 trace/metrics/log 体系，便于企业运维。

## 7. 工程解读

本节从 AetherCode 项目的工程实践出发，解读论文方法如何落地，并给出可立即执行的下一步建议。

### 7.1 与 AetherCode Tier-3 兼容实现的对照

AetherCode 项目目前拥有 **17 个 Tier-3 兼容实现**，其中与本文主题直接相关的有 `aethercode-mcp`（MCP 协议模块）、`aethercode-a2a`（A2A 协议模块）、`aethercode-protocol`（协议路由）、`aethercode-permission`（权限管理）等。下表给出论文 7 步方法论与 AetherCode 已有实现的对照：

| 论文观点 | AetherCode 对应实现 | 状态 |
|---|---|---|
| MCP 管 tool | `aethercode-mcp` McpRegistry | ✅ 已实现 |
| A2A 管 agent | `aethercode-a2a` AgentCard + Task | ✅ 已实现 |
| 双协议栈 | AetherCode 同时具备 MCP + A2A 模块 | ✅ 已具备 |
| 7 步方法论 | 部分实现，缺 Capability Modeling + Discovery | ⚠️ 部分缺失 |
| Authentication（OAuth 2.0 + DID） | 当前仅有 API key 认证 | ⚠️ 待补全 |
| Protocol Selection 自动路由 | `aethercode-protocol` ProtocolRouter | ✅ 已实现 |
| Task Delegation 状态机 | `aethercode-a2a` TaskStateMachine | ✅ 已实现 |
| Result Aggregation | `aethercode-a2a` ResultAggregator | ✅ 已实现 |

可以看到，AetherCode 在**协议层**（MCP、A2A、路由、状态机、聚合）已经较为完整，但在**治理层**（能力建模自动化、统一发现中心、企业级认证）仍有显著缺口。

### 7.2 与 17 个 Tier-3 实现的关联

AetherCode 的其他 Tier-3 实现可以从本文思想中获益：

- **GlobalPlan**（全局规划器）：可以作为 7 步方法论中"步骤 6 Task Delegation"的上层协调者，将用户请求分解为多个 A2A Task，并追踪跨 Task 的依赖。
- **ByzantineDetector**（拜占庭检测器）：直接呼应本文"局限与未来工作"中提到的**结果污染威胁**。在 Result Aggregation 步骤前，先用 ByzantineDetector 过滤异常智能体的输出，可显著提升系统鲁棒性。
- **RetrievalBandit**（检索 Bandit 优化器）：在 Discovery 阶段，多个智能体声明了相似能力时，可用 RetrievalBandit 动态选择最优协作对象，实现"智能体选择"层面的在线学习。
- **其他实现**（如 `McpToolWrapper`、`ProtocolRouter` 等）：直接对应论文提出的兼容实现候选列表，可在两周内完成最小可用版本。

### 7.3 立即可做的下一步

基于论文与 AetherCode 的现状对比，建议优先推进以下三项工作：

**（1）补齐 Capability Modeling 自动化**
在 `aethercode-a2a` 模块下新增 `AgentCapabilityModeler` 类，自动从智能体代码（Python 函数签名、docstring、类型注解）生成 Agent Card。论文步骤 1 的人工成本（2 人日）可压缩到接近 0。

**（2）实现 OAuth 2.0 + DID 集成**
在 `aethercode-permission` 模块下新增 `OAuthAuthenticator` 类，与 AgentCard 联动。这能解决企业级客户最关心的"权限审计"问题，是商业化的硬门槛。

**（3）构建统一可观测性**
参考论文未来工作第 3 点，在 MCP 与 A2A 之上叠加统一的 trace/metrics/log 层。可借力 AetherCode 现有的可观测性框架（如 OpenTelemetry 集成），实现"一次埋点、双协议覆盖"。

### 7.4 借鉴与差异

值得强调的是，论文的核心思想——**协议分工而非协议替代**——已经在 AetherCode 中被部分验证。但论文给出的 7 步方法论更偏向**企业治理视角**，而 AetherCode 作为开源项目，更侧重**运行时效率与可扩展性**。两者结合可形成"治理 + 性能"的双轮驱动。
