## 一、核心问题

LLM-based Agent 已经在真实任务广泛使用, 但 agent 系统**性能如何随规模变化**仍然缺乏系统研究。论文引入**量化 scaling 原则**, 建立可预测模型, 捕获性能如何随 *协调方式 / 模型能力 / 系统因素 / 任务因素* 变化。

## 二、5 种标准 Agent 架构

| 架构 | 描述 | 跟 AetherCode 已有 |
|---|---|---|
| **Single-Agent** | 单 agent, 无协调 | R-orch-1 AgentRuntime 单 runtime |
| **Independent** | 多个独立 agent 并行, 无通讯 | ❌ 缺 — 需要加 |
| **Centralized** | 中央协调 + 验证 (R-orch-1 AgentRuntime.runEnsemble 是雏形) | ✅ 部分 (CritiqueStrategy 中央评分) |
| **Decentralized** | P2P 通讯, 动态调整 | ❌ 缺 — 需要加 |
| **Hybrid** | 中心验证 + 去中心执行 | ❌ 缺 — 需要加 |

## 三、关键发现 (3 大效应)

### 3.1 能力饱和 (Capability Saturation)
- **多 agent 协调**对单 agent baseline 达到 ~45% 时**收益递减甚至为负**
- beta=-0.408, p<0.001 强显著
- 含义: 不要盲目加 agent, 先看单 agent 能到哪

### 3.2 工具-协调权衡
- **tool-heavy 任务** (tool 调用多) 在多 agent 下**overhead 显著**
- 多 agent 增加 token cost 但不一定增加成功率
- 含义: tool 数 ≤ 阈值时 single-agent 更划算

### 3.3 拓扑-错误放大
- **Independent 架构**: 错误通过 unchecked 传播, **放大 17.2×**
- **Centralized 架构**: 错误被中央验证 contain, 只放大 **4.4×**
- 含义: 错误控制是 multi-agent 的关键, 必须有中央验证

## 四、量化结果 (260 configurations)

- **4× benchmark**: Finance-Agent, BrowseComp-Plus, PlanCraft, Workbench
- **3 LLM family**: Claude / GPT / Gemini
- **R² = 0.373** 全 6 benchmark, R² = 0.413 加 task-grounded 指标
- **性能范围**: +80.8% (decomposable financial reasoning) 到 **-70.0%** (sequential planning)
- **架构预测准确率**: 87% held-out configuration

## 五、对 AetherCode 的启示

| AetherCode 现状 | 2512.08296 建议 | 行动 |
|---|---|---|
| 3 strategy (Vote/Debate/Critique) | 5 architecture (Single/Ind/Cen/Dec/Hybrid) | **缺 Independent/Decentralized/Hybrid 3 个** |
| AgentRuntime.runEnsemble (centralized 雏形) | Centralized 87% 准确 | ✅ 已有 |
| 无 architecture 推荐 | Architecture 选择器 | **加 AgentArchitectureSelector** |
| 无 capability 饱和检测 | 监控单 agent 性能拐点 | 加 CapabilitySaturationDetector |
| Tool 数无限制 | tool 数 ≤ 阈值时 single 优 | 加 tool-count threshold |

## 六、关键洞见

1. **架构-任务对齐**决定协作成功 — 错的架构降低 70% 性能
2. **错误控制**比 token 优化更重要 — Centralized 把错误放大从 17.2× 降到 4.4×
3. **能力饱和**点: 单 agent 达到 ~45% 后多 agent 收益递减
4. **Centralized 适合 parallelizable 任务** (+80.8% financial reasoning)
5. **Decentralized 适合 dynamic 任务** (+9.2% web navigation)

## 七、兼容实现计划 (R-eval-13 + R-sdk-14)

### 7.1 兼容实现 1: AgentArchitectureSelector
- 输入: task 特征 (parallelizable, sequential, tool-heavy, dynamic)
- 输出: 推荐 architecture (Single/Ind/Cen/Dec/Hybrid)
- 跟 R-eval-7 + R-sdk-7 (A2A) 集成

### 7.2 兼容实现 2: 2 个新 MultiAgentOrchestrator strategy
- **IndependentStrategy**: N agent 并行, 无通讯, 各自给答案, raw 多数决
- **HybridStrategy**: Centralized verify + Decentralized execution
- 加 orchestration.multiagent 跟现有 Vote/Debate/Critique 并列

### 7.3 评估套件: 5 architecture 对比 test
- 5 architecture 跑同一 task
- 测 capability saturation (单 agent 70% 时多 agent 收益)
- 测 tool-heavy overhead
- 测 error amplification factor
