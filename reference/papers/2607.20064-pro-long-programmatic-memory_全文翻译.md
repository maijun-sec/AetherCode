## 2. 一句话摘要

**程序化记忆让代码智能体以编程方式查询完整日志,从而在长程推理任务上以四至五倍 token 节省达到专用框架同等水平。**

---

## 3. 背景与动机

近年来,大语言模型(LLM)驱动的代码智能体(code agent)在软件工程、数学解题、网页导航等任务上展现出惊人能力。然而,当任务需要跨越数小时乃至数天的长程交互时,智能体所积累的环境日志会迅速膨胀到数百 MB 甚至 GB 级别,远超任何 LLM 上下文窗口所能容纳的容量。如何处理这份"超长上下文",已成为制约智能体走向真实工业落地的核心瓶颈。

现有的两条主流路线各有明显缺陷:**激进压缩**(summarization、truncation、token-level pruning)会丢失关键细节,导致智能体在多步推理中出现幻觉或遗忘;**外部检索**(RAG、向量数据库、相似度搜索)虽然保留了原文,但召回率受限于 embedding 质量与相似度度量,在需要精确模式匹配(如正则、聚合、JOIN)的场景下表现乏力,更关键的是,检索式方案天然无法支撑跨多次会话的状态复用。

PRO-LONG 的提出者敏锐地抓住了第三个机会:**代码智能体本身就是一个强大的"上下文处理器"**。既然智能体能够读写代码,那么让它对日志进行编程式查询(grep、SQL、正则、聚合、过滤),比让 LLM 直接"吞下"所有上下文要高效得多。这一观察将近年来"代码即行动"(code-as-action)的研究范式与长期记忆(long-term memory)研究合二为一,催生了**程序化记忆**(programmatic memory)这一全新设计原语。

## 4. 核心方法

### 4.1 总体架构

PRO-LONG 的核心思想可以概括为一句话:**不动 LLM,把长上下文转化为可程序化查询的数据**。其处理流程如下所示:

```
[Long environment log]
        ↓
[Persistent log file]   ← 程序化访问
        ↓
[Code agent] 用 code 查询 log (例如 grep / SQL / 正则)
        ↓
[Filtered context]  → LLM
```

也就是说,完整的环境日志被**持久化**写入磁盘文件,而非堆积在 LLM 上下文窗口中;当智能体需要信息时,它**生成一段代码**来对日志文件进行精确查询,只把查询结果——而非原始日志——送入 LLM 的上下文。这种"日志外置 + 按需拉取"的模式天然支持跨 session 的状态复用,也天然支持高效聚合。

### 4.2 三大核心机制

**(1) 持久化日志(Persistent log)**:
所有 agent 与环境的交互(动作、观察、错误、奖励、HTTP 响应等)以追加写方式落盘,采用结构化格式(JSONL 或类似 schema)。日志文件是"真相之源",任何时刻都可以从原始事件重放整个 episode,支持回溯调试与离线分析。

**(2) 基于代码的查询(Code-based search)**:
当 LLM 需要信息时,它可以生成 Python/shell 脚本对日志文件执行 grep、awk、SQLite 查询、pandas 聚合等操作。这是 PRO-LONG 与传统 RAG 的本质区别:**RAG 是相似度的,而 PRO-LONG 是语义的精确的**。例如,智能体不再问"哪些步骤提到了超时",而是直接写 `grep "timeout" log.jsonl | wc -l`。

**(3) 受限代码子集(LogQueryLanguage)**:
为防止 LLM 生成任意代码带来的安全隐患(删除日志、调用网络、逃逸沙箱),PRO-LONG 引入了**受限查询语言**(LogQueryLanguage),将 LLM 可生成的代码限制在一个白名单子集内——只允许只读的文件操作、过滤、聚合、统计。这既保留了表达的灵活性,又杜绝了越权操作。

### 4.3 与现有方案的关键对比

| 维度 | 上下文压缩 | 向量检索 RAG | PRO-LONG 程序化记忆 |
|---|---|---|---|
| 信息保真度 | 低(有损) | 中(模糊匹配) | **高**(精确查询) |
| Token 消耗 | 中 | 中 | **低**(只取结果) |
| 跨 session 复用 | 难 | 中 | **易**(落盘文件) |
| 表达力 | 弱 | 中(语义级) | **强**(任意代码) |
| 安全风险 | 低 | 低 | **中**(需沙箱) |
| 实现复杂度 | 中 | 高 | **低**(仅需文件系统) |

### 4.4 关键设计原则

- **不动 LLM**:不修改模型权重,不引入额外训练,纯推理时框架;
- **代码即接口**:智能体与日志的交互统一通过代码,统一可观测、可审计;
- **持久化为先**:日志落盘是一等公民,内存缓存只是优化;
- **查询受限**:白名单子集确保 LLM 不会写"危险代码"破坏日志或越权。

## 5. 实验结果

论文在 ARC-AGI-3 公开游戏集上对 PRO-LONG 进行了系统评估。ARC-AGI-3 是由 François Chollet 团队推出的抽象推理基准,考察智能体在未知游戏规则下的长程探索、记忆与归纳能力,被认为是当前最能体现"长程推理"水平的试金石。

### 5.1 核心指标

在与 baseline code agent(无持久化日志、纯上下文窗口处理)的对比中,PRO-LONG 在 ARC-AGI-3 公开游戏集上**平均提升 +18.0 个百分点**(pp),这一差距在长 episode 游戏上尤为显著——传统方案在上下文溢出后即陷入"循环遗忘",而 PRO-LONG 凭借持久日志保持稳定增长。

在专用 harness(为该基准专门优化、动用大量上下文工程的系统)对比下,PRO-LONG 取得 **76.1% pass@1**(一次通过率),达到 SOTA 水平,而其 token 消耗仅为对方的 **1/4.2 至 1/5.8**,即节省 **4.2-5.8 倍 token**。这是论文最具冲击力的结果:**在不牺牲准确率的前提下,数量级地降低成本**。

### 5.2 极端场景:Fable 5 游戏

Fable 5 是 ARC-AGI-3 中难度最高的游戏之一,需要数百步探索才能归纳出隐藏规则。PRO-LONG 在该任务上达到 **97.4% best@2**(两次尝试内最佳通过率),总成本仅 **$1,750**。这一数字虽然不低,但相比专用 harness 在同等任务上动辄数万美元的开销,已是数量级的优化。

### 5.3 实验结论归纳

| 评测维度 | 关键数字 |
|---|---|
| 相对 base code agent | **+18.0 pp** |
| pass@1(ARC-AGI-3) | **76.1%**(SOTA 持平) |
| Token 节省倍数 | **4.2-5.8×** |
| Fable 5 best@2 | **97.4%** |
| Fable 5 总成本 | **$1,750** |

这些数字共同验证了 PRO-LONG 的核心论断:**代码智能体 + 持久化日志 + 程序化查询,可以用远低于传统方案的资源,达到甚至超越专用 SOTA 框架的水平。**

## 6. 局限与未来工作

尽管成果亮眼,PRO-LONG 仍有若干明确局限。首先,**受限代码子集的设计需要人工维护**,且与具体日志格式紧耦合——当日志 schema 演化时,白名单需要同步更新,这增加了工程负担。其次,**沙箱执行 LLM 生成代码带来额外的延迟**(每次查询需启动 Python 进程),在高频率小查询场景下反而可能慢于直接读上下文。再次,**PRO-LONG 主要面向单 agent 场景**,对多 agent 协作中的日志所有权、一致性、并发访问等问题尚未充分讨论。

未来工作可沿以下方向展开:① 自动学习受限查询子集,使其随日志 schema 共同演化;② 引入流式/增量查询机制,降低冷启动延迟;③ 将程序化记忆扩展到多 agent 共享记忆,研究分布式日志的一致性协议;④ 与向量检索**混合使用**——代码查询负责精确过滤、向量检索负责模糊召回,形成互补。

## 7. 工程解读:在 AetherCode 中的落地路径

### 7.1 与 AetherCode 现有 Tier-3 实现的对照

AetherCode 作为工业级 Agent 编排框架,已沉淀 17 个 Tier-3 兼容实现,包括 **GlobalPlan**(全局规划器)、**ByzantineDetector**(拜占庭容错检测)、**RetrievalBandit**(检索臂老虎机)等。下表给出 PRO-LONG 与 AetherCode 现有模块的映射关系:

| 论文观点 | AetherCode 对应模块 | 实现状态 |
|---|---|---|
| Persistent log(持久日志) | `RuntimeTrace`(运行时轨迹) | ✅ **部分实现**,当前仅 in-memory,**需补持久化** |
| Code-based search(代码查询) | ⚠️ 无直接对应 | ❌ **缺位**,是最具借鉴价值的洞见 |
| 4-5× token 节省 | `R-perf-1`(`ActionCache` 等动作缓存族) | ✅ **已落地** |
| ARC-AGI-3 benchmark | ⚠️ 无 | ❌ **缺位**,可作为长程评估基线 |
| 受限查询白名单 | `SandboxPolicy`(沙箱策略) | ✅ **已有**,可直接复用 |

### 7.2 可立即借鉴的三大思想

**思想一:代码查询替代向量检索**——这是 PRO-LONG 给 AetherCode 最直接的启示。当前 `RetrievalBandit` 主要依赖 embedding 相似度,在需要精确过滤(如"过去 10 步内所有包含 HTTP 500 的事件")时召回率不佳。引入 **`CodeSearchBridge`**(代码搜索桥接器),允许 LLM 在工具调用中生成 Python 片段查询 `RuntimeTrace`,可以与现有向量检索形成"精确+模糊"的双路召回。这与 `ByzantineDetector` 的多路校验思想天然契合——拜占庭检测本身就要求精确规则匹配,代码查询比相似度匹配更可靠。

**思想二:持久化轨迹优于内存缓存**——`RuntimeTrace` 当前仅在内存中维护,这限制了跨 session 复用与崩溃恢复。借鉴 PRO-LONG,将轨迹以 JSONL 格式落盘,既支持冷启动恢复,也为 `GlobalPlan` 的全局规划提供"完整历史"——规划器可以查询任意时间窗的事件,而非仅最近 N 步。这与 `GlobalPlan` 现有的"滑窗规划"形成互补。

**思想三:受限查询语言作为安全屏障**——`SandboxPolicy` 已在 AetherCode 中承担代码执行沙箱职责,PRO-LONG 的 **LogQueryLanguage** 思想可以直接复用为白名单扩展。新增 `LogQueryLanguage` 模块(位置:`orchestration.context`),将可执行操作限制在只读文件 + 过滤 + 聚合上,既保护日志完整性,又便于审计。

### 7.3 候选实现清单

| 类名 | 用途 | 建议文件位置 |
|---|---|---|
| `ProgrammaticMemory` | 把 log 存为可代码查询的结构 | `orchestration.memory` |
| `CodeSearchBridge` | LLM 写 code 查 log,替代 similarity search | `orchestration.context` |
| `LogQueryLanguage` | 限制 LLM 写的 code 子集(避免越界) | `orchestration.context` |

### 7.4 下一步行动建议

短期(1-2 周):在 `RuntimeTrace` 上补 JSONL 落盘,加 `tail`/`grep` 工具暴露给 agent;在 `RetrievalBandit` 内增加"代码召回"通道作为精确路。

中期(1 个月):落地 `CodeSearchBridge` 与 `LogQueryLanguage`,接入 `SandboxPolicy`;在 ARC-AGI-3 公开子集上跑 baseline,目标验证 4-5× token 节省是否在 AetherCode 框架内同样成立。

长期:借鉴 `ByzantineDetector` 的多 agent 思想,把程序化记忆扩展到多 agent 共享场景,研究并发日志的版本控制与冲突解决。

## 8. 译者后记

作为本系列 46 篇论文综述中的一篇,PRO-LONG 在定位上属于**"方法论级创新"**而非"benchmark 级刷榜"。它没有提出新模型、没有堆叠新数据,而是重新审视了一个被忽视的原语——**代码智能体本身就是上下文处理器**——并把这一观察工程化为可落地的系统。这种"小切口、深挖掘"的研究风格,与 AetherCode 所倡导的"框架即产品"哲学高度一致。

从技术影响力看,PRO-LONG 的程序化记忆很可能成为 RAG 之后的下一代长上下文范式;从工程实用性看,**4.2-5.8× token 节省 + SOTA 持平准确率**的双重组合,在 LLM 推理成本仍居高不下的当下,具有直接的经济价值。建议读者重点关注:**§4 的受限查询语言设计**(沙箱与表达力的平衡)与 **§5 的 ARC-AGI-3 评测**(长程推理的标尺),前者可立即在 AetherCode 的 `SandboxPolicy` 中复用,后者则可作为 AetherCode 自身 Tier-3 实现的评估基准。

如果你只读一段,请记住:**让 LLM 写代码查日志,而不是把所有日志塞进 LLM 的上下文——这是 PRO-LONG 给整个 Agent 领域最简洁也最深刻的礼物。**
