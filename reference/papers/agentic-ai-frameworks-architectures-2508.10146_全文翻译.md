## 三、背景与动机

大语言模型（LLM）的崛起正深刻重塑人工智能系统的形态。在传统范式中，AI 系统多为"输入—模型—输出"的封闭管道；而 LLM 凭借其在自然语言理解、世界知识压缩与链式推理方面的能力，催生了一种全新的范式——**智能体化 AI**（Agentic AI）。在该范式下，智能体（Agent）不再是被动响应输入的工具，而是具备**上下文感知、目标导向的自主性、动态推理能力以及多智能体协作能力**的"自主协作实体"。它们能够感知环境、规划行动序列、调用外部工具、记忆历史经验，并与其他智能体协同完成复杂任务。

围绕这一范式，工业界与学术界在过去两年间涌现出一大批智能体化 AI 框架。其中最具代表性的包括 Microsoft 出品的 **AutoGen**、角色驱动协作的 **CrewAI**、基于图状态机的 **LangGraph**、模拟软件工程团队的 **MetaGPT**、企业级编排框架 **Semantic Kernel**、声明式推理的 **Agno**，以及 Google 推出的 **Agent Development Kit（ADK）**。这些框架在抽象层次、编排范式、记忆机制、护栏强度等方面各有特色，但也呈现出显著的"碎片化"特征——开发者很难在不同框架之间迁移，跨框架互操作几乎是一片空白。

正是在这样的产业与学术双重背景下，Derouiche 等人撰写了这篇综述论文。文章明确指出：现有文献对这些框架的**架构设计、技术组件、记忆与护栏机制差异**缺乏系统性对比，这不仅阻碍了学术研究者的深入探索，也使工程师在选型时面临"信息不对称"的困境。为此，作者围绕四个研究问题（RQ1–RQ4）展开系统性论述：

- **RQ1**：智能智能体如何从传统 AI 智能体演化为 LLM 驱动的现代智能体？
- **RQ2**：有哪些主流智能体化 AI 框架？它们如何实现核心智能体概念与多智能体系统范式？
- **RQ3**：这些框架在通信、记忆、编排、模块化、护栏方面如何对比？
- **RQ4**：现代框架在多大程度上已准备好集成到服务计算生态中？

上述四个问题构成本文的研究骨架，覆盖了从概念演化、协议设计、框架横评到服务计算对齐的完整链条。

## 四、核心方法

### 4.1 智能体的概念演化

智能体并非新生事物。在传统 AI 领域，**BDI 范式**（Belief-Desire-Intention）长期占据主导地位：智能体持有对环境的信念（Belief），具有目标导向的愿望（Desire），并通过意图（Intention）驱动行动。传统 BDI 智能体依赖固定规则、有限自主性，多用于多智能体系统（MAS）中的协商与博弈场景。

LLM 的出现彻底打破了这一格局。现代智能体以 LLM 为"推理引擎"，将**规划、记忆、对话与工具使用**统一编排到一个迭代循环中。论文梳理了代表性范式：**ReAct**（Reasoning + Acting）通过"思考—行动—观察"循环实现推理与执行的交替；**PRACT** 强调过程级自适应；**RAISE** 关注多智能体协同推理；**Reflexion** 则通过自我反思强化长期表现。

基于此，作者给出一个新的现代智能体定义：

> "具备推理与通信能力的自主协作实体，能动态解释结构化上下文、编排工具，并通过记忆与跨分布式系统的交互来调适行为。"

这一定义突出了三个关键要素：**自主性**（无需人为逐步指令）、**通信能力**（可与其他智能体或服务交互）、**适应性**（能根据上下文调适行为）。它与传统 BDI 智能体最大的区别在于，推理过程不再是预编码的规则，而是由 LLM 在运行时动态生成。

### 4.2 智能体通信协议

智能体之间如何"说话"？这是智能体化 AI 走向大规模工程化的核心瓶颈之一。论文梳理了五大新兴协议族系：

**（1）MCP（Model Context Protocol）**——由 Anthropic 提出的 JSON-RPC 客户端-服务器模型，专注于**结构化工具调用**。MCP 通过标准化的请求/响应模式，使 LLM 能够一致地调用外部工具、数据源与服务。

**（2）A2A（Agent-to-Agent）**——Google 推出的智能体间通信协议，核心概念包括 **Agent Card**（智能体能力声明卡片）、**Task Object**（任务对象）与 **Artifact**（产物对象）。A2A 强调"任务可被识别、状态可被追踪、产物可被传输"。

**（3）ANP（Agent Network Protocol）**——采用 **DID**（Decentralized Identifier，去中心化标识符）与 **JSON-LD**（JSON for Linked Data）作为语义层，目标是支持**跨组织的去中心化智能体网络**。ANP 试图将 Web 语义网技术引入智能体通信。

**（4）ACP（Agent Communication Protocol）**——IBM 推出的 RESTful + 结构化 JSON 协议，延续了传统服务计算的设计哲学，易于与企业现有系统集成。

**（5）Agora**——一个**元协调层**（meta-coordination layer），创新性地引入**协议文档（Protocol Document, PD）**概念，允许系统根据 PD 动态选择最合适的底层协议。

**关键洞察**：JSON-LD 与 PD 等语义机制为动态发现与组合提供了可能，但**碎片化仍然存在**——HTTP 在传输层占据主导地位，不同协议的语义异质性限制了无缝集成。作者特别指出，目前仍缺少类似 WSDL for agents 的"标准化服务契约"规范，这是未来标准化工作的重点方向。

下表概括五大协议的核心特征：

| 协议 | 提出方 | 传输/语义层 | 核心抽象 | 主要场景 |
|---|---|---|---|---|
| **MCP** | Anthropic | JSON-RPC | 工具调用 | LLM 工具集成 |
| **A2A** | Google | HTTP + JSON | Agent Card / Task / Artifact | 智能体任务协作 |
| **ANP** | 社区 | DID + JSON-LD | 语义标识符 | 跨组织去中心化 |
| **ACP** | IBM | RESTful + JSON | REST 资源 | 企业集成 |
| **Agora** | 学术 | 元层 + PD | 协议文档 | 协议动态选择 |

### 4.3 智能体化 AI 框架对比

论文对七大主流框架进行了系统性横评，从**架构特色**、**记忆实现**、**护栏支持**三个维度展开。

#### 4.3.1 架构特色

| 框架 | 特色定位 | 出品方 |
|---|---|---|
| **AutoGen** | 结构化多智能体对话 | Microsoft |
| **CrewAI** | 角色驱动的团队式协作 | 开源社区 |
| **LangGraph** | 基于图的有状态工作流 | LangChain 团队 |
| **MetaGPT** | 模拟软件工程团队的产品生命周期 | 开源社区 |
| **Semantic Kernel** | 企业级编排 + 技能规划器 | Microsoft |
| **Agno** | 声明式 + 透明推理 | 开源社区 |
| **Google ADK** | 云原生分布式编排 | Google |

跨框架共享的核心组件可归纳为四元组：**LLM 推理引擎** + **工具调用** + **记忆系统** + **护栏**。这一共识性架构反映了行业对"什么是智能体"的基本理解正在趋于一致。

#### 4.3.2 记忆实现

记忆机制的设计差异是各框架最显著的分野之一：

- **LangGraph**：将记忆建模为**图节点的状态（State）**，天然支持有状态工作流；
- **OpenAI SDK**：采用**会话缓冲（Conversation Buffer）**，简单直接但缺乏长程压缩；
- **CrewAI**：引入**角色记忆**，每个角色维护独立的记忆空间；
- **AutoGen**：依赖**共享对话上下文（Group Chat Manager）**，所有智能体可见同一上下文；
- **LlamaIndex**：通过**嵌入检索（RAG）**实现记忆，记忆即检索；
- **MetaGPT**：使用**角色行为快照**记录每个角色的输出与决策。

这些实现反映出不同的设计哲学：有状态 vs. 无状态、共享 vs. 隔离、显式 vs. 隐式。

#### 4.3.3 护栏支持

护栏（Guardrail）是指对智能体行为的约束与安全检查机制。论文统计的护栏支持程度如下：

- **原生最强**：AutoGen、LangGraph、Agno、OpenAI SDK
- **部分支持**：CrewAI、MetaGPT、Semantic Kernel、Google ADK
- **完全缺失**：SmolAgents

这一差异直接影响框架在企业级生产环境的可用性——缺乏原生护栏意味着开发者必须自行实现安全检查。

### 4.4 服务计算视角

论文最具理论深度的工作是将这些框架对齐到**面向服务架构（SOA）**的经典原则。SOA 的三个核心能力——**动态发现、动态发布、动态组合**——恰好对应智能体化 AI 走向大规模工程化的三大需求。

论文 **表 IV** 给出了对齐评估：

| 框架 | 动态发现 | 动态发布 | 动态组合 | 综合评级 |
|---|---|---|---|---|
| **Semantic Kernel** | ★★★ | ★★★ | ★★★ | 最强 |
| **Google ADK** | ★★★ | ★★★ | ★★★ | 最强 |
| **LangGraph** | ★★ | ★★ | ★★★ | 可扩展性强 |
| **CrewAI** | ★ | ★★ | ★★ | 需外部注册表 |
| **AutoGen** | ★★ | ★★ | ★ | 需外部注册表 |
| **Agno** | ★ | ★★ | ★★ | 需外部注册表 |
| **MetaGPT** | ★ | ★ | ★ | 需外部注册表 |

（★ 为 1 分，★★★ 为 3 分；评级来自论文原文的定性评估。）

进一步地，作者考察了 W3C 传统规范在现代框架中的采用情况（论文 **表 V**）：

| W3C 规范 | AutoGen | CrewAI | LangGraph | MetaGPT | Semantic Kernel |
|---|---|---|---|---|---|
| **WSDL**（服务描述） | ✗ | ✗ | ✗ | ✗ | 部分 |
| **BPEL**（业务流程编排） | ✗ | ✗ | 部分 | ✗ | 部分 |
| **WS-Policy**（策略） | ✗ | ✗ | ✗ | ✗ | ✓ |
| **WS-Security**（安全） | ✗ | ✗ | ✗ | ✗ | 部分 |
| **WS-Coordination**（协调） | ✗ | ✗ | ✗ | ✗ | ✗ |
| **WS-Agreement**（协议） | ✗ | ✗ | ✗ | ✗ | ✗ |

结果显示：传统 W3C 规范在智能体化 AI 框架中的采用仍然十分有限，Semantic Kernel 是走得最远的一个。**标准化互操作的"最后一公里"仍未完成。**

## 五、实验结果

由于本文是一篇**综述性论文**（survey），其"实验结果"章节以**横向对比与定性评估**为主，而非定量基准测试。作者通过系统化的文献梳理与框架文档分析，得出以下关键结论：

**结论一：架构范式收敛但实现路径分化**。七大框架在高层抽象上趋同（都包含 LLM 推理、工具调用、记忆、护栏四大组件），但在具体实现路径上呈现显著差异。例如，记忆机制在 LangGraph 中表现为图节点状态，在 LlamaIndex 中表现为嵌入检索，二者的工程取舍截然不同。

**结论二：通信协议呈现"碎片化但有共识"**。五大协议各自针对不同场景（MCP 偏工具、A2A 偏任务、ANP 偏语义、ACP 偏 REST、Agora 偏元层），但**JSON-LD 与 PD 等语义机制的引入**显示出业界对"动态可解释性"的共识。HTTP 仍占传输主导，但语义层尚未统一。

**结论三：服务计算对齐度差异显著**。Semantic Kernel 与 Google ADK 在 SOA 三大能力（发现、发布、组合）上的得分最高，这与二者强调"企业级"与"云原生"的定位相符。LangGraph 凭借状态机抽象提供可扩展性，被作者单独列为"最具工程潜力"的框架之一。CrewAI、AutoGen、Agno、MetaGPT 则仍依赖外部服务注册表，未实现原生 SOA 对齐。

**结论四：护栏与安全的成熟度参差不齐**。原生护栏最强的是 AutoGen、LangGraph、Agno 与 OpenAI SDK；SmolAgents 完全缺失原生护栏，需开发者自行构建。这一发现对生产环境选型具有直接指导意义。

**结论五：W3C 传统规范采用率极低**。除 Semantic Kernel 部分引入外，绝大多数框架未采用 WSDL、BPEL、WS-Policy 等传统服务计算规范。这反映出智能体化 AI 框架倾向于"另起炉灶"而非复用成熟标准，但也意味着**标准化工作的巨大空间**。

上述结论为研究者和工程师提供了清晰的选型与研究方向。

## 六、局限与未来工作

作者在论文第 V、VI 节中坦率地指出了领域当前的四大局限：

1. **架构刚性**：现有框架普遍采用静态角色分配（如 planner、executor、coder），智能体一旦启动便难以根据任务上下文动态调整角色，限制了系统的适应性。

2. **缺乏运行时发现**：智能体间的交互必须在编译期或启动期静态定义，无法支持运行时涌现的协同行为。这与生物界"分布式涌现"现象形成鲜明对比。

3. **代码安全风险**：智能体生成代码并执行的能力带来文件系统访问、shell 命令执行等高风险操作，护栏机制尚不完善。

4. **互操作性差距**：CrewAI 的任务模型无法被 AutoGen 直接解释；SmolAgent 不能调用 LangGraph 的工作流。这种"框架孤岛"现象严重阻碍了生态发展。

基于上述局限，作者提出三个未来方向：

- **建立标准化基准**：开发可复现、可比较的基准测试套件，支持客观比较。
- **开发通用智能体通信协议**：在 MCP、A2A、ANP 等现有协议基础上，推动跨框架互操作。
- **引入 MAS 范式**：将协商、协调、自组织等成熟的多智能体系统范式引入现有框架，提升动态适应能力。

## 七、工程解读

将这篇综述的洞见映射到 **AetherCode** 项目的工业级 Agent 框架设计与落地，我们可以看到若干直接可借鉴的思想与具体的下一步行动。

**借鉴点一：四元组核心架构与 17 个 Tier-3 兼容实现的对应关系**。综述指出跨框架共享的核心组件为 **LLM 推理引擎 + 工具调用 + 记忆系统 + 护栏**。AetherCode 的 17 个 Tier-3 兼容实现已经在很大程度上覆盖了这四元组：

- **GlobalPlan** 实现了综述所述的"基于图的有状态工作流"思想，与 LangGraph 的状态机抽象异曲同工；
- **ByzantineDetector** 提供了 AutoGen、LangGraph 级别的护栏机制，对应综述强调的"原生最强护栏"；
- **RetrievalBandit** 则采用了 LlamaIndex 式的"记忆即检索"范式，将嵌入检索作为长程记忆的载体。

这种设计哲学与综述提出的"四元组共识"高度契合，说明 AetherCode 在架构层面已经走在行业前沿。

**借鉴点二：通信协议的标准化与 A2A/MCP 接入**。综述将 MCP 与 A2A 视为未来标准化的核心方向。建议 AetherCode 在下一版本中：

- 立即可做：在 GlobalPlan 与外部智能体之间引入 **MCP 客户端适配器**，支持通过 JSON-RPC 调用任意 MCP 兼容工具；
- 短期可做：在 17 个 Tier-3 实现的元数据层引入 **Agent Card** 规范（A2A 风格），使每个实现都能被外部发现与调度；
- 中期可做：探索 **ANP 风格的 DID 标识符**作为智能体的去中心化身份，与 AetherCode 的跨进程互操作需求天然匹配。

**借鉴点三：服务计算对齐与跨进程互操作**。综述 §IV-D 提出将智能体化 AI 框架对齐 SOA 原则，这是 AetherCode 跨进程互操作模块的直接理论基础。具体而言：

- AetherCode 已经实现的服务注册表可视为"动态发布"的雏形；
- 建议引入"服务契约"概念，作为综述所称的"WSDL for agents"的最小可行实现；
- W3C 规范采用方面，可考虑在 BPEL 兼容的工作流描述上做有限探索，以支持与遗留企业系统的集成。

**借鉴点四：MAS 范式与涌现协同**。综述指出"缺乏运行时发现"是当前框架的核心局限。AetherCode 的下一代路线图（如 R236+ 后续）可借鉴：

- AutoGen 的 Group Chat Manager 模式实现"共享对话上下文"；
- CrewAI 的角色记忆机制实现"角色独立记忆空间"；
- MetaGPT 的角色行为快照实现"决策可追溯"。

**下一步具体建议**：

1. 在 GlobalPlan 中实现 **Protocol Document（PD）抽象**，参考 Agora 的元协调层思想；
2. 在 ByzantineDetector 中实现 **Agent Card 解析器**，使其支持 A2A 协议；
3. 在 RetrievalBandit 中引入 **角色隔离记忆**机制，借鉴 CrewAI 设计；
4. 启动 **AgenticBench-Aether** 标准化基准项目，呼应综述对"可复现基准"的呼吁。

总体而言，这篇综述对 AetherCode 的工程实践具有**强指导价值**——它既验证了现有设计方向的正确性，也指明了下一阶段的演进路径。

## 八、译者后记

作为 AetherCode 项目的资深技术译者，我认为 *Agentic AI Frameworks: Architectures, Protocols, and Design Challenges* 是 2025 年度智能体化 AI 领域**最值得精读的综述之一**。它篇幅短小（仅 8 页），却以极高的信息密度完成了从概念演化、协议设计、框架横评到服务计算对齐的完整论证，展现出作者团队深厚的系统综合能力。

在 46 篇论文综述的定位中，本文处于**"地图绘制者"**的角色——它不创造新方法，而是为整个领域绘制一张清晰的"技术地形图"。对于刚进入智能体化 AI 方向的研究者，本文是不可替代的入门读物；对于资深从业者，本文提供的"四大局限"与"三大方向"则是判断未来三到五年技术演进的关键坐标。

对读者的阅读建议：

1. **首次阅读**建议先看 §II（智能体演化）与 §IV（框架横评），建立整体认知；
2. **深入研究**建议精读 §III（通信协议），尤其关注 MCP 与 A2A 的对比；
3. **工程实践**建议重点参考 §IV-D（服务计算视角），对照自身系统进行差距分析；
4. **跨项目协作**建议将本文与 AetherCode 的 17 个 Tier-3 实现并列阅读，体会"理论综述"与"工程实践"的相互印证。

最后值得一提的是，本文作者在"协议碎片化"与"标准化差距"上的洞察，对所有正在建设智能体平台的团队都是一记警钟：**在追逐新框架、新协议的同时，更应关注底层标准化工作**。这既是本文的学术价值，也是其工程价值。
