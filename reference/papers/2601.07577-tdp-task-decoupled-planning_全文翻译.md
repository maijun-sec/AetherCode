## 二、背景与动机

在大模型驱动的智能体（LLM Agent）研究范式中，"长程任务"（long-horizon task）始终是一道横亘在工程落地面前的鸿沟。所谓长程任务，是指那些需要跨越数十甚至上百步决策、调用多种工具、并在异构环境中连续执行才能完成的复合型目标，例如"调研某行业并撰写竞品分析报告""在沙箱中部署一套微服务并完成端到端压测""基于仓库代码自动修复一组关联 issue"等。这类任务的共同特征是：步骤多、依赖深、信息容量大。

传统智能体框架在面对长程任务时普遍采用"单一上下文持续累积"的策略：随着执行步数 $t$ 递增，拼接进 Prompt 的历史信息 $C_t = \bigcup_{i=1}^{t} (a_i, o_i)$ 也线性膨胀。这种"纠缠式上下文"（entangled context）会引发两个棘手问题：

1. **信息干扰（information interference）**：当多个子任务的信息被混编在同一段上下文中，模型容易将本应隔离的语义片段相互混淆，导致推理漂移。
2. **错误涟漪（error ripple）**：早期子任务中产生的幻觉或误判，会作为"事实"被后续步骤无差别地引用，进而引发链式失败。

为缓解上述问题，学术界曾提出两条主流路线：其一是 **ReAct** 类逐步式推理（step-wise reasoning），在每一步 $(think, act)$ 中显式记录，但缺乏全局视野，决策短视；其二是 **One-shot Planning**，先一次性生成完整计划再执行，视野虽全却极度脆弱——环境稍有变动，全局计划即告失效。

TDP 论文敏锐地指出：上述两条路线均未触及问题本质——**上下文的耦合结构本身**。即便采用 ReAct 的逐步机制，只要不同子任务共享同一段上下文，干扰与涟漪就无法消除。为此，作者主张以"任务解耦"为第一性原理：把长程任务拆解为有向无环图（DAG）形式的子任务，并为每个子任务建立严格隔离的上下文边界，从根源上切断干扰与涟漪的传播路径。

## 三、核心方法

TDP（Task-Decoupled Planning）的整体架构由三大模块与一项关键机制构成：监督器（**Supervisor**）、规划器（**Planner**）、执行器（**Executor**），以及子任务完成后的 **Self-Revision（自修订）** 机制。

### 3.1 总体形式化

给定全局任务 $\mathcal{T}$，TDP 首先将其分解为一个 DAG：

$$
\mathcal{T} \longrightarrow G = (V, E)
$$

其中节点集 $V = \{v_1, v_2, \dots, v_n\}$ 表示 $n$ 个子任务，有向边集 $E \subseteq V \times V$ 表示子任务之间的前置依赖关系，即若 $(v_j, v_i) \in E$，则 $v_j$ 为 $v_i$ 的前置节点。每个节点 $v_i$ 拥有**独立的上下文缓冲区** $\mathcal{C}_i$，与兄弟子任务（sibling sub-tasks）的上下文互不可见。

### 3.2 三大模块职责

| 模块 | 作用 | 关键约束 |
|---|---|---|
| **Supervisor** | 全局任务分解 → DAG，监控整体进度 | 拥有全局视图，但不直接干预单子任务执行 |
| **Planner** | 为当前子任务 $v_i$ 生成高层计划 | 仅可见 $v_i$ 的 spec + 前置节点 $\{v_j \mid (v_j, v_i) \in E\}$ 的**结果摘要**，**绝不传递全局 history** |
| **Executor** | 在子任务内部执行具体 action，必要时触发 local replan | 上下文严格限于 $\mathcal{C}_i$ |

**最关键的设计原则**在于 Planner 的上下文隔离——它不继承任何兄弟子任务的中间状态。这一约束与函数式编程中的"参数作用域"（parameter scoping）思想高度同构：只传递当前计算真正需要的数据，其余一概屏蔽。

### 3.3 Self-Revision（自修订）机制

当子任务 $v_i$ 执行完毕，TDP 并不立即推进到下一节点，而是触发 **Self-Revision 钩子**，检查 $v_i$ 的执行结果是否违背全局假设 $\mathcal{A}$。若违背，则视违背程度执行以下三类修订之一：

| 违背类型 | 修订动作 |
|---|---|
| 结构性违背（新增需求出现） | 在 DAG 中**插入新节点** $v_{n+1}$，并更新拓扑序 |
| 范围性违背（某节点目标已失效） | **删除过时节点** $v_k$ 及其下游链 |
| 参数性违背（细节偏差） | **细化待执行节点的 spec**：$\text{spec}(v_j) \leftarrow \text{Refine}(\text{spec}(v_j), \Delta)$ |

Self-Revision 的精妙之处在于：它以**局部修订**取代了传统的全局重规划（global replan），从而在保持全局可行性（feasibility）的同时，避免了昂贵的全局上下文重建开销。

### 3.4 Token 消耗模型

设全局共有 $n$ 个子任务，每个子任务平均消耗 $T_i$ 个 Token。若采用"纠缠式上下文"，第 $i$ 步的总 Token 消耗可近似为：

$$
T_{\text{entangled}}^{(i)} \approx T_i + \sum_{j<i} T_j
$$

而 TDP 下，由于 Planner 仅看前置结果摘要（设摘要大小为常数 $c \ll T_j$），单节点消耗近似为：

$$
T_{\text{TDP}}^{(i)} \approx T_i + |E_i| \cdot c
$$

其中 $|E_i|$ 为节点 $v_i$ 的入度。在典型的稀疏 DAG（$|E_i|$ 很小）下，整体 Token 消耗可下降一个数量级。论文实测报告显示，在标准长程基准上，TDP 相比纠缠式基线实现了 **82% 的 Token 消耗削减**。

## 四、实验结果

论文在多类长程智能体基准上对 TDP 进行了系统评估，主要结论可归纳为以下三点：

**1. 任务成功率显著提升。** 在包含数十步复合操作的复杂任务集合中，TDP 相较 ReAct 类逐步基线的端到端成功率提升明显，相较 One-shot Planning 基线的提升幅度更大（在最困难的若干子集上提升超过 20 个百分点）。这一结果验证了"DAG 解耦 + 局部规划"相较于"单一上下文持续累积"的结构性优势。

**2. Token 消耗下降 82%。** 在保持任务完成质量不下降甚至略有提升的前提下，TDP 的整体 Token 消耗相比纠缠式上下文基线下降约 **82%**。这是本文最具工程价值的数字——它直接对应着推理成本（API 调用费用、推理时延、显存占用）的同比例下降，对于需要规模化部署的工业级 Agent 系统而言，意味着数量级的成本压缩。

**3. 错误涟漪被显著抑制。** 通过对失败案例的归因分析，论文显示：在纠缠式基线下，约 35% 的失败可追溯到上游子任务的早期错误被下游无差别引用；而 TDP 由于上下文隔离 + Self-Revision 双重机制，将该比例压缩到 5% 以下。这一指标在生产环境中意味着更低的级联故障率与更高的鲁棒性。

此外，论文还报告了 Self-Revision 机制对全局重规划次数的削减效果——平均每条任务轨迹中触发 global replan 的次数从基线的 1.7 次降至 0.3 次，进一步印证了"局部修订优于全局重写"的设计哲学。

## 五、局限与未来工作

论文作者坦率指出了若干尚待解决的边界条件与开放问题：

**第一，DAG 静态性假设。** TDP 的核心建立在"全局任务可被预先分解为 DAG"这一假设之上。然而在真实工业场景中，任务拓扑往往需要根据环境反馈动态涌现（例如用户中途改变需求）。论文将"动态 DAG 重构"列为未来重要方向。

**第二，Self-Revision 的代价函数。** 当前 Self-Revision 采用规则化的三类修订动作，缺乏对修订代价的显式建模。当修订粒度过细时，可能陷入"过度修订"循环——每完成一个子任务都触发修订，反而抵消了 Token 节省收益。

**第三，跨子任务的信息复用边界。** 完全隔离的上下文虽消除了干扰，但也牺牲了某些场景下跨子任务信息复用的潜在收益。如何在"严格隔离"与"受控复用"之间寻找最优平衡点，仍是一个开放课题。

**第四，评估基准的局限。** 论文实验主要集中在结构化较强的合成基准上，对真实开放环境（如真实 IDE 操作、真实 SaaS API 调用）的泛化能力尚需进一步验证。

## 六、工程解读（AetherCode 视角）

作为 AetherCode 项目的译者，我在通读 TDP 后最直接的感受是：**这篇论文几乎是为 AetherCode 的 Tier-3 体系量身定做的工程蓝图**。AetherCode 现已沉淀的 17 个 Tier-3 兼容实现中，至少有四个模块与 TDP 的核心组件一一对应。

### 6.1 已有覆盖的对应关系

| TDP 论文观点 | AetherCode 对应实现 | 当前状态 |
|---|---|---|
| Supervisor（全局分解 → DAG） | `CentralPlanner`（R-paper-batch4） | ✅ 已实现 |
| Planner（per sub-task 隔离规划） | `GlobalPlan`（R-paper-batch3） | ✅ 已实现 |
| Scoped context（per-task memory） | `Blackboard` 共享层 + per-task memory 隔离 | ✅ 已实现 |
| DAG sub-tasks 表达 | `DagPlan` | ✅ 已实现 |

这意味着 TDP 的"四大支柱"中有四个已被 AetherCode 的现有架构覆盖，剩下的关键缺口是 **Self-Revision 机制**——AetherCode 目前尚未提供显式的子任务后修订钩子。

### 6.2 立即可落地的下一步

基于上述对照分析，建议 AetherCode 在近期引入以下四个新的 Tier-3 兼容类：

| 类名 | 用途 | 推荐文件位置 |
|---|---|---|
| `ScopedContext` | 严格隔离 per sub-task context，强制 Planner 不可见兄弟子任务历史 | `orchestration.planner` |
| `TaskDecoupledPlanner` | 整合 Supervisor + Planner + Executor 三模块，对外暴露统一接口 | `orchestration.planner` |
| `SelfRevisionHook` | 子任务完成后触发检查：是否违反全局假设，必要时增删改 DAG 节点 | `orchestration.planner` |
| `DAGContextPruner` | 自动剪掉与当前节点无关的子任务上下文，防止边界泄漏 | `orchestration.planner` |

### 6.3 与 GoalAct 的协同

TDP 的 Supervisor 与 AetherCode 现有 **GoalAct** 体系中的 Global Plan 高度互补：Supervisor 负责"DAG 拓扑如何演化"，GoalAct 负责"每个节点内的目标如何被具象化为动作序列"。二者组合可形成"两层规划"架构——上层是结构性的拓扑演化，下层是节点内的行为展开。

### 6.4 工程哲学层面的共鸣

TDP 的"上下文作用域隔离"思想与函数式编程中的 parameter scoping、操作系统中的进程地址空间隔离、微服务架构中的租户隔离一脉相承——**只传递当前计算真正需要的数据，其余一概屏蔽**。这一原则在 AetherCode 的后续演进中应被提升为一条核心架构原则：每一个 Planner、每一个 Agent、每一个 Tool 都应明确声明其上下文依赖边界，而非默认继承全量全局状态。
