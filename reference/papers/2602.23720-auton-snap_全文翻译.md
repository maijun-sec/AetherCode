## 摘要 (Abstract)

**原文**: *The proliferation of agentic AI frameworks (LangChain, AutoGen, CrewAI, etc.) has created an "Integration Paradox": each new framework adds value but also adds integration cost. We propose Auton, a unified agentic AI framework that decouples cognitive specification (the "what") from runtime execution (the "how"). Auton comprises (1) a Cognitive Blueprint — a declarative spec of the agent's goal, tools, and decision rules; (2) a Runtime Engine that executes the blueprint deterministically; (3) a 3-Level Self-Evolution mechanism that adapts the blueprint based on feedback. We deploy Auton at Snap Inc. to handle 12 production use cases (recommendation, moderation, customer service, etc.) and show 3-10× improvement over hand-engineered agents in throughput, with no accuracy regression.*

**译文**: 智能体 AI 框架 (LangChain、AutoGen、CrewAI 等) 的激增造成了"集成悖论": 每个新框架增加价值, 但也增加集成成本。我们提出 **Auton**, 一个解耦认知规范 ("什么") 与运行时执行 ("如何") 的统一智能体 AI 框架。Auton 包含 (1) **认知蓝图** — agent 目标、工具、决策规则的声明式规范; (2) **运行时引擎** — 确定性执行蓝图; (3) **3 层自我演化** 机制 — 基于反馈适配蓝图。我们在 Snap Inc. 部署 Auton 处理 12 个生产用例 (推荐、审核、客服等), 吞吐量比手工 agent 提升 3-10 倍, 无准确率下降。

## 1 集成悖论 (Integration Paradox)

**原文 (摘译)**: 当 agent 框架数量增长 (AutoGen, LangChain, CrewAI, MetaGPT, Aider, Devin, ...), 集成成本指数增长。每个新框架有不同的 API、不同的 state 管理、不同的 prompt 模板。开发者必须 N×M 学习曲线: N 个 agent 类型, M 个集成点。

Auton 的解法: 引入中间层 "Cognitive Blueprint", 把 agent 的认知 (目标、工具、决策) 与框架实现 (LangChain 或 AutoGen) 解耦。一个 Blueprint 可在多个 Runtime Engine 上跑。

**译文**: 当 agent 框架数量增长 (AutoGen、LangChain、CrewAI、MetaGPT、Aider、Devin、...), 集成成本指数增长。每个新框架有不同的 API、不同的 state 管理、不同的 prompt 模板。开发者必须 N×M 学习曲线: N 个 agent 类型, M 个集成点。

## 2 4 大支柱 (4 Pillars)

### 2.1 Pillar 1: Cognitive Blueprint (声明式规范)

**原文 (摘译)**: A Blueprint is a YAML/JSON file with 4 sections:
- **Goal**: the agent's mission, success criteria, constraints.
- **Tools**: list of available tools with input/output schemas.
- **Decision Rules**: a finite state machine or decision tree for what to do at each state.
- **Memory Schema**: what to remember between calls.

Example:
```yaml
goal: "answer user questions about Snap products"
tools:
  - name: search_kb
    input: { query: string }
    output: { hits: array }
rules:
  - on: user_query
    do: search_kb(query=user_query)
  - on: kb_results_non_empty
    do: llm_summarize(kb_results, user_query)
  - on: kb_results_empty
    do: ask_clarification(user_query)
memory: { last_5_queries: array }
```

**译文**: 一个 Blueprint 是含 4 段的 YAML/JSON 文件:
- **目标**: agent 使命、成功标准、约束。
- **工具**: 可用工具列表与输入/输出 schema。
- **决策规则**: 有限状态机或决策树, 描述每状态做什么。
- **记忆 Schema**: 调用间保留什么。

**译文 (例子)**:
```yaml
goal: "回答用户关于 Snap 产品的提问"
tools:
  - name: search_kb
    input: { query: string }
    output: { hits: array }
rules:
  - on: user_query
    do: search_kb(query=user_query)
  - on: kb_results_non_empty
    do: llm_summarize(kb_results, user_query)
  - on: kb_results_empty
    do: ask_clarification(user_query)
memory: { last_5_queries: array }
```

### 2.2 Pillar 2: Runtime Engine (确定性执行)

**原文 (摘译)**: The Runtime Engine interprets the Blueprint and executes it. It maintains state, calls tools, and dispatches to the LLM at the points marked in the rules. The runtime is deterministic except for the LLM calls; this makes the agent testable and reproducible.

**译文**: 运行时引擎解释 Blueprint 并执行。它维护状态, 调用工具, 在规则标记的点派发到 LLM。除 LLM 调用外, 运行时是确定性的; 这让 agent 可测试、可复现。

### 2.3 Pillar 3: 3-Level Self-Evolution

**原文**: The Blueprint can be updated by 3 mechanisms:
1. **In-context updates**: Add new rules or examples to the prompt (cheap, fast).
2. **Meta-prompt updates**: Rewrite the LLM's system prompt to incorporate new patterns (medium cost).
3. **RL fine-tuning**: Fine-tune the underlying LLM on the agent's successful trajectories (expensive, long-term).

**译文**: Blueprint 可通过 3 种机制更新:
1. **上下文更新**: 加新规则或例子到 prompt (便宜、快)。
2. **元 prompt 更新**: 重写 LLM 的 system prompt 纳入新模式 (中等开销)。
3. **RL 微调**: 在 agent 成功 trajectory 上微调底层 LLM (贵、长期)。

### 2.4 Pillar 4: Constraint Manifold (确定性治理)

**原文 (摘译)**: The Constraint Manifold is a set of declarative constraints on the agent's behavior: "this agent must never call tool X with parameter Y", "this agent must always return a JSON object with schema Z". Constraints are checked at runtime, before the action is executed. Violations are blocked + logged.

**译文**: 约束流形 (Constraint Manifold) 是对 agent 行为的声明式约束集: "此 agent 绝不以参数 Y 调用工具 X", "此 agent 始终返回 schema Z 的 JSON 对象"。约束在运行时、动作执行前检查。违规则阻断 + 记录。

## 4 工程解读: 跟 AetherCode 的对应关系

| Paper 观点 | AetherCode 实现 |
|---|---|
| 4 段 Blueprint (Goal/Tools/Rules/Memory) | `AgentCard` 部分覆盖 (capability 描述); 缺 Rules FSM |
| Runtime Engine 确定性 | AetherCode 的 `AetherCodeEngine.query()` 已经是 deterministic-where-possible |
| 3-Level Self-Evolution | 仅 in-context (system prompt) 覆盖; 缺 meta-prompt + RL 微调 |
| Constraint Manifold | `CommandAllowlist` 部分覆盖; 缺 schema 验证 |
| Cognitive Blueprint 跨 Runtime 跑 | 部分: 同一 Blueprint 可在 TUI / CLI / IDEA 跑 (AetherCode 多端) |

### 关键工程启示

- **声明式 vs 命令式**: 论文力推声明式 Blueprint, 跟 AetherCode 当前"代码即配置"风格不同。可考虑加 YAML/JSON spec
- **跨框架互操作**: Auton 的"一个 Blueprint 多个 Runtime" 跟 AetherCode 的 A2A 协议思想一致
- **生产部署的"3-10× 提升"是工程价值证明**: 蓝图模式确实比直接写 LangChain 代码高效

### 后续可做

- `Blueprint.java` 类 (YAML schema)
- `BlueprintRuntime.java` (执行 Blueprint, 调度 LLM + 工具)
- `ConstraintManifold.java` (声明式约束, runtime 检查)
- 把现有 `AgentCard` 升级为 Blueprint

## 5 译者后记

> Auton 的核心洞察, 在于"集成悖论" — 当 agent 框架数量爆炸, 集成成本是真正的瓶颈。Blueprint 作为中间层, 把"认知"与"实现"解耦, 是经典的"中间层"工程哲学应用。
>
> AetherCode 本身就有"中间层"基因: `AetherCodeMethods` 是 RPC 抽象, `AetherCodeEngine` 是 runtime 抽象。Auton 给我们的启示是: 把"中间层"做得更标准化 (YAML Blueprint), 让用户能用声明式而非命令式定义 agent。
