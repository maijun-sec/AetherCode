## 摘要 (Abstract)

**原文**: *LLM-based agents have demonstrated strong capabilities in executing multi-step tasks, but they typically rely on a flat action space and rigid plan-then-execute paradigm. This limits their adaptability: when a step fails, the agent has no good way to re-plan without re-prompting the entire context. We propose GoalAct, a hierarchical goal-oriented planning framework. GoalAct represents plans as sequences of typed skills (SEARCHING, CODING, WRITING, REASONING, RESEARCH, FINISH), where each skill has its own action space and execution model. The plan is continuously regenerated by a policy π(query, tools, history) → next_plan, allowing real-time re-planning after each step. We evaluate GoalAct on 6 long-horizon benchmarks (HotpotQA, HumanEval, ALFWorld, AppWorld, SWE-Bench, WebArena) and show 8-22% absolute improvement over ReAct and Plan-and-Act baselines, with 30-50% fewer LLM calls.*

**译文**: 基于 LLM 的智能体已展示出执行多步任务的强大能力, 但它们通常依赖扁平的行动空间和僵化的"先规划后执行"范式。这限制了它们的适应性: 当一步失败时, 智能体没有好方法重新规划, 只能重提示整个上下文。我们提出 **GoalAct**, 一个层级化目标导向的规划框架。GoalAct 把规划表示为类型化技能 (SEARCHING、CODING、WRITING、REASONING、RESEARCH、FINISH) 的序列, 每种技能有自己的行动空间与执行模型。规划由策略 π(query, tools, history) → next_plan 持续再生成, 允许在每一步后实时重新规划。我们在 6 个长程 benchmark (HotpotQA、HumanEval、ALFWorld、AppWorld、SWE-Bench、WebArena) 上评估 GoalAct, 展示比 ReAct 与 Plan-and-Act 基线提升 8-22 个绝对百分点, 同时 LLM 调用数减少 30-50%。

## 1 引言 (Introduction)

**原文 (摘译)**: 现有 LLM agent 框架 (ReAct, Plan-and-Act, AutoGPT) 把任务规划为一串文本动作 ("search for X", "click button Y"), 共享同一个 action space。这种扁平化设计有两个问题:
1. **粒度不匹配**: "search for X" 这一步可能需要 5-10 次工具调用; "click button Y" 可能需要 1 次; 把它们当成同质的 action, 调度效率低下。
2. **重规划难**: 当第 3 步失败时, 整条链都要重做, 因为没有"跳到第 3 步重新规划"的机制。

GoalAct 的解决方案: 把 action 抽象为 **skill**, 每个 skill 有自己的子动作空间。规划是 skill 序列, 而不是原始动作序列。每步执行后, 智能体可以重新规划剩余步骤, 失败时跳过/重试而不必从头开始。

**译文**: 现有 LLM agent 框架 (ReAct、Plan-and-Act、AutoGPT) 把任务规划为一串文本动作 ("搜索 X"、"点击按钮 Y"), 共享同一个 action space。这种扁平化设计有两个问题:
1. **粒度不匹配**: "搜索 X" 这一步可能需要 5-10 次工具调用; "点击按钮 Y" 可能需要 1 次; 把它们当成同质的 action, 调度效率低下。
2. **重规划难**: 当第 3 步失败时, 整条链都要重做, 因为没有"跳到第 3 步重新规划"的机制。

GoalAct 的解决方案: 把 action 抽象为 **skill**, 每个 skill 有自己的子动作空间。规划是 skill 序列, 而不是原始动作序列。每步执行后, 智能体可以重新规划剩余步骤, 失败时跳过/重试而不必从头开始。

## 2 技能分类法 (Skill Taxonomy)

**原文**: We identify 6 high-level skills that cover the action space of typical long-horizon tasks:

| Skill | 子动作 | 典型 LLM 调用 | 例子 |
|---|---|---|---|
| **SEARCHING** | search(query), read(url), summarize(text) | 0-2 次/步 | 搜索网络、读文档 |
| **CODING** | write_code(spec), run_code(code), fix_error(err) | 0-5 次/步 | 写脚本、调试 |
| **WRITING** | draft(outline), edit(draft, feedback) | 1-3 次/步 | 写报告、邮件 |
| **REASONING** | deduce(premise, rule), verify(conclusion) | 0-2 次/步 | 逻辑推理、证明 |
| **RESEARCH** | investigate(topic), synthesize(findings) | 2-5 次/步 | 综述研究 |
| **FINISH** | (none, terminal) | 0 次/步 | 任务完成 |

**译文**: 我们识别 6 类高层技能, 覆盖典型长程任务的行动空间:

| Skill | 子动作 | 典型 LLM 调用 | 例子 |
|---|---|---|---|
| **SEARCHING** (搜索) | search(query), read(url), summarize(text) | 0-2 次/步 | 搜索网络、读文档 |
| **CODING** (编码) | write_code(spec), run_code(code), fix_error(err) | 0-5 次/步 | 写脚本、调试 |
| **WRITING** (写作) | draft(outline), edit(draft, feedback) | 1-3 次/步 | 写报告、邮件 |
| **REASONING** (推理) | deduce(premise, rule), verify(conclusion) | 0-2 次/步 | 逻辑推理、证明 |
| **RESEARCH** (研究) | investigate(topic), synthesize(findings) | 2-5 次/步 | 综述研究 |
| **FINISH** (完成) | (无, 终止) | 0 次/步 | 任务完成 |

**原文 (摘译)**: Each skill's LLM-call budget is bounded. SEARCHING and FINISH use 0-2 calls, CODING uses up to 5 (since debug loops are common), RESEARCH uses 2-5 (synthesis takes effort). The skill annotation lets the runtime know when to stop a skill and either re-plan or fail.

**译文**: 每个 skill 的 LLM 调用预算有界。SEARCHING 与 FINISH 用 0-2 次, CODING 最多 5 次 (调试循环常见), RESEARCH 用 2-5 次 (综合需要功夫)。Skill 标注让运行时知道何时停止一个 skill 然后重新规划或失败。

## 3 层级化规划 (Hierarchical Planning)

### 3.1 规划表示 (Plan Representation)

**原文 (摘译)**: A plan is a sequence of `Step` records, where each step is a (description, skill) pair. The last step is always FINISH.

```
Step 1: [SEARCHING] "Find the user's last 5 transactions"
Step 2: [REASONING] "Check if any are over $1000"
Step 3: [WRITING] "Compose an email summary"
Step 4: [FINISH] "Send email and log"
```

**译文**: 规划是一个 `Step` 记录的序列, 每个步骤是 (描述, 技能) 对。最后一步总是 FINISH。

```
步骤 1: [SEARCHING] "查找用户最近 5 笔交易"
步骤 2: [REASONING] "检查是否有超过 $1000 的"
步骤 3: [WRITING] "撰写邮件总结"
步骤 4: [FINISH] "发送邮件并记录"
```

### 3.2 持续再规划 (Continuous Re-Planning)

**原文**: After each step executes, the policy π(query, tools, history) generates a new plan for the remaining work. This is a Markov decision process: the state is (query, tools, history_so_far), the action is the next plan.

**Algorithm 3.1 (GoalAct main loop)**:

```python
def goal_act(query, tools):
    plan = llm_plan(query, tools=tools, history=[])  # initial plan
    history = []
    for step in plan.steps:
        result = execute_skill(step, tools)
        history.append((step, result))
        if step.skill == FINISH:
            return result
        # re-plan based on what's happened
        remaining = [s for s in plan.steps if s not in history]
        plan = llm_plan(query, tools, history, remaining=remaining)
    return history[-1].result
```

**译文**: 在每一步执行后, 策略 π(query, tools, history) 为剩余工作生成新规划。这是个马尔可夫决策过程: 状态是 (query, tools, history_so_far), 动作是下一规划。

**算法 3.1 (GoalAct 主循环)**:

```python
def goal_act(query, tools):
    plan = llm_plan(query, tools=tools, history=[])  # 初始规划
    history = []
    for step in plan.steps:
        result = execute_skill(step, tools)
        history.append((step, result))
        if step.skill == FINISH:
            return result
        # 根据已发生的事重新规划
        remaining = [s for s in plan.steps if s not in history]
        plan = llm_plan(query, tools, history, remaining=remaining)
    return history[-1].result
```

### 3.3 重新规划的成本 (Re-Planning Cost)

**原文 (摘译)**: Re-planning after every step is expensive (an LLM call per step). We adopt two optimizations:
1. **Skip re-plan if step succeeded and no new information**: if the step's result is as expected, don't re-plan; continue to next step.
2. **Partial re-plan**: instead of regenerating the entire plan, only re-plan the *remaining* steps (those not yet executed). This is cheaper because the LLM only sees `remaining` + `history`, not the full plan.

These optimizations reduce re-planning calls by 60-80% in practice.

**译文**: 每步后重新规划开销大 (每步一次 LLM 调用)。我们采用两个优化:
1. **若步骤成功且无新信息则跳过再规划**: 若步骤的结果如预期, 不再规划, 继续下一步。
2. **部分再规划**: 不重新生成整个规划, 只重新规划**剩余**步骤 (尚未执行的部分)。这更便宜, 因为 LLM 只看到 `remaining` + `history`, 而非完整规划。

这些优化在实践中让再规划调用减少 60-80%。

## 4 各 Skill 的执行细节 (Per-Skill Execution)

### 4.1 SEARCHING Skill

**原文**: The SEARCHING skill takes a query and returns relevant text. Implementation:

```python
def execute_searching(step, tools):
    query = step.description
    results = tools.search(query)  # web search
    summaries = []
    for r in results[:5]:  # top-5
        text = tools.read(r.url)  # read URL
        summary = llm_summarize(text, query)
        summaries.append(summary)
    return {"results": summaries, "count": len(summaries)}
```

### 4.2 CODING Skill

**原文 (摘译)**: The CODING skill writes code, runs it, and may iterate on errors. The debug loop is the most expensive part:

```python
def execute_coding(step, tools, max_iters=5):
    spec = step.description
    code = llm_generate_code(spec)
    for i in range(max_iters):
        result = tools.run_code(code)
        if result.success:
            return {"code": code, "output": result.output}
        # debug
        code = llm_fix_error(code, result.error)
    return {"code": code, "error": "max iters reached"}
```

**译文**: CODING skill 写代码、运行、可能迭代错误。调试循环是最贵的部分:

```python
def execute_coding(step, tools, max_iters=5):
```

### 4.3 FINISH Skill

**原文**: The FINISH skill is special: it has no sub-actions. It marks the end of the plan. The runtime checks that the result is "complete" (some user-defined notion of done-ness) before returning.

**译文**: FINISH skill 是特殊的: 它没有子动作。它标记规划的结束。运行时在返回前检查结果是"完整" (某种用户定义的完成感)。

**原文**: GoalAct uses 30-50% fewer LLM calls than baselines, despite achieving higher accuracy. The savings come from:
- **Skill-typed actions**: SEARCHING converges in 1-2 LLM calls; Plan-and-Act often calls 5+ "search"-like actions.

**译文**: GoalAct 相比基线 LLM 调用少 30-50%, 同时准确率更高。节省来自:
- **类型化动作**: SEARCHING 1-2 次 LLM 调用收敛; Plan-and-Act 经常调用 5+ 次"搜索"类动作。
- **部分再规划**: 只再规划剩余步骤, 不重做整个。
- **无冗余"思考"**: 每个 skill 有自己的 LLM prompt 模板; 无通用"先想再做"的开销。

## 6 讨论 (Discussion)

### 6.1 与 ReAct 的根本区别

**原文 (摘译)**: ReAct interleaves "Thought" and "Action" in a single loop. The agent decides what to do next based on the previous Thought + Observation. This is reactive, not deliberative. GoalAct's plan is a *deliberation* ahead of time: the LLM commits to a skill sequence, executes it, and re-plans only when needed. This trades upfront cost (planning) for downstream savings (fewer re-decisions).

**译文**: ReAct 在单循环中交错"思考"与"动作"。智能体基于前次思考 + 观察决定下一步。这是反应式, 不是慎思式。GoalAct 的规划是**事先慎思**: LLM 承诺一个 skill 序列, 执行它, 仅在需要时再规划。这用前期成本 (规划) 换取下游节省 (更少的重决策)。

### 6.2 何时重规划

**原文 (摘译)**: We adopt a simple heuristic: re-plan if the step's result contains an error or unexpected output, otherwise continue. This works 80% of the time. For the remaining 20%, we may miss re-planning opportunities (e.g. when a "successful" step actually gives wrong info). Future work could use a critic model to decide when to re-plan.

**译文**: 我们采用一个简单启发式: 若步骤结果包含错误或意外输出, 则重规划, 否则继续。这在 80% 情况下有效。剩下 20%, 我们可能错过重规划机会 (例如"成功"的步骤实际给出错误信息)。未来工作可以用评论模型决定何时重规划。

### 6.3 局限性 (Limitations)

**原文 (摘译)**: GoalAct assumes the LLM can produce a sensible initial plan. For very open-ended tasks (e.g. "design a new product"), the initial plan may be useless and the re-planning loop never converges. We address this by capping the number of re-plans at 10; if no progress, we return the best partial result. The skill taxonomy is also fixed; new tasks may need new skills.

**译文**: GoalAct 假设 LLM 能产出合理的初始规划。对非常开放的任务 (例如"设计新产品"), 初始规划可能无用, 重规划循环永远不收敛。我们通过把重规划次数上限设为 10 来应对; 若无进展, 返回最佳部分结果。技能分类法也是固定的; 新任务可能需要新技能。

### 7.1 AetherCode 已实现 vs 论文待补

- ✅ **6 类 skill** — 完整 enum
- ✅ **末步 FINISH 不变量** — `of()` 校验
- ✅ **update() / advance()** — re-planning API
- ✅ **HierarchicalExecutor** — skill 路由
- ⚠️ **持续再规划的实际策略** — `update()` API 在, 但 LLM 驱动的 `π(query, tools, history) → next_plan` 还没接入
- ⚠️ **每个 skill 的 LLM call 预算** — 论文说 SEARCHING 0-2, CODING 0-5; AetherCode 还没设
- ⚠️ **Re-plan 跳过启发式** — 论文 §6.2 的"step 结果无错则不重规划"未实现
- ⚠️ **Re-plan 上限 10** — 未实现, 当前 `update()` 无限制

### 7.2 论文的精妙设计

- **Skill 是接口而非子动作**: 论文把 skill 当作可替换的策略 (`searching: step -> result`), 让 runtime 不必关心"怎么搜", 只关心"搜什么"
- **末步 FINISH 必为终态**: 不变量让 runtime 不必检查"是不是结束了", 直接看 step.skill == FINISH
- **部分再规划**: 不重做整个规划, 只 re-plan 剩余。LLM 的 input 长度下降, 调用成本降低

### 7.3 给 AetherCode 的改进建议

- **接 LLM 驱动的 `replan()`**: `GlobalPlan.update()` 当前只接受完整 steps, 应加 `replanFromHistory(query, tools, history)` 调用 LLM
- **加 skill budget 限制**: `HierarchicalExecutor.execute()` 加 max-llm-calls 参数, 论文给的具体值
- **跳过再规划启发式**: 加 `if (lastResult.isExpected()) skipReplan()` 优化
- **Step.result 包含 status 字段**: 让 runtime 知道"成功但信息可能错"vs"明确错误"

## 8 译者后记 (Translator's Afterword)

> GoalAct 的洞察, 在于把"规划"和"执行"清晰解耦, 但又通过 skill 这个中间抽象让两者紧密相连。这与软件工程里的"接口-实现"模式异曲同工: skill 是接口, 具体 LLM 提示与工具调用是实现, runtime 只需与接口打交道。

> 与 ReAct 的"边想边做"相比, GoalAct 的"先规划再做"看起来"慢" (要等规划), 实际上"快" (因为重规划少, 一次规划对多步都管用)。这是经典的"前期投资换后期回报"在 agent 设计中的体现。

> AetherCode 的 `GlobalPlan` + `HierarchicalExecutor` 是 GoalAct 思想的工程化骨架。论文 §6.3 提到的"open-ended 任务初始规划可能无用", 在 AetherCode 实际部署中也很常见 (例如 `query` 含糊不清时) — 后续应加 LLM-driven replan() 让骨架活起来。

**— Mavis, 译于 2026-09-13**
