## 摘要

大语言模型（LLM）的兴起开启了人工智能领域的一次范式转变——**智能体化 AI**（Agentic AI），其中智能智能体（intelligent agents）展现出目标导向的自主性、上下文推理能力以及动态的多智能体协作能力。本文对主流的智能体化 AI 框架进行系统性综述与对比分析，包括 **CrewAI、LangGraph、AutoGen、Semantic Kernel、Agno、Google ADK 和 MetaGPT**，评估它们在架构设计原则、通信机制、记忆管理、安全护栏（guardrails）以及与面向服务计算范式对齐程度方面的表现。此外，我们识别了该领域的关键局限性与新兴趋势。为应对智能体通信问题，我们对 **Contract Net Protocol (CNP)、Agent-to-Agent (A2A)、Agent Network Protocol (ANP) 和 Agora** 等协议进行深入分析。我们的成果不仅为智能体化 AI 系统建立了基础分类法，还提出了可扩展性、鲁棒性与互操作性等未来研究方向。本文是面向致力于推动下一代自主 AI 系统的研究者与从业者的综合性参考文献。

## I. 引言

大语言模型（LLM）的快速进步开启了智能智能体（intelligent agents）的新纪元，即所谓的**智能体化 AI**——这些自主系统能够推理、通信与协作，以完成复杂的、长时程（long-horizon）的任务。这一范式转变有别于传统 AI 与多智能体系统（MAS）[1]，引入了不仅具备上下文感知、还能由基于 LLM 的认知驱动的目标导向行为智能体。

智能体化 AI 正被越来越多地部署于软件工程 [2]、科学发现、商业自动化与人机协作等领域。为支撑其能力，一个不断壮大的智能体化 AI 框架生态系统（如 CrewAI、LangGraph）应运而生。这些框架为构建、编排与部署智能智能体提供架构基础与工具支持。尽管智能体化 AI 范式发展迅速，但对各框架在设计哲学、技术组件与实际能力上的差异，仍缺乏系统性理解。现有相关文献稀缺且往往只关注孤立特性。例如，[3] 中的作者在金融服务情境下提供了综合综述。

本文旨在通过提供对主流框架（CrewAI、LangGraph、AutoGen、Semantic Kernel、MetaGPT）的综合对比分析来弥补这一空白。我们的研究基于对各主要智能体化 AI 框架架构特征的探究，凸显其设计模式与运行组件。同时关注这些系统所采用的通信协议（如 ACP、ANP、A2A、Agora）。此外，本文研究不同框架在**记忆集成**与**护栏执行**等关键方面的处理方式。最后反思了这些系统当前面临的局限性与挑战，并识别智能体化 AI 未来发展的有前景方向。为此，我们探讨以下研究问题：

- **RQ1**：智能智能体如何从传统 AI 智能体演化为现代 LLM 驱动的智能体？
- **RQ2**：有哪些可用于开发智能体化 AI 系统的框架？这些框架如何实现核心智能体概念、MAS 范式（协商、协作、组织）与通信？
- **RQ3**：这些框架在通信、记忆、编排、模块化与护栏方面如何对比？智能体通信协议方面有哪些最新进展？
- **RQ4**：现代智能体化 AI 框架在多大程度上已准备好集成到服务计算生态中？

本文其余部分组织如下：**第 II 节**讨论智能智能体与通信协议的基础。**第 III 节**详细考察通信协议。**第 IV 节**从记忆、护栏与服务计算角度分析智能体化 AI 框架。**第 V 节**概述当前局限性与开放研究方向。**第 VI 节**总结全文。

## II. 智能智能体

人工智能中"智能体"（agent）的概念在过去数十年间于 AI 的基础范式——主要是多智能体系统（MAS）与专家系统——中经历了重大演变 [4]。传统上，智能体被定义为能够通过传感器感知环境、通过效应器对环境施加作用以达成指定目标的自主实体。该经典定义强调自主性、反应性、主动性与社交能力，这也是早期 MAS 研究的核心原则 [1]。然而，随着大语言模型（LLM）与基于 Transformer 架构的兴起，现代智能体展现出更具动态性、上下文感知的行为。它们不再局限于预定义环境，而是在流动且往往以人为中心的上下文中运行。这些智能体不仅能推理与行动，还能与外部数据源交互、编排工具并与其他智能体实时（常常是异步地）协作。

当代智能体架构，包括 ReAct [5]、PRACT [6]、RAISE [7] 与 Reflexion [8]，均以 LLM 作为推理引擎为核心，通过迭代循环统一编排规划、记忆、对话与工具使用。例如，ReAct 架构在迭代循环中结合了推理（思维链）与行动（工具使用）。

我们认为，现代智能体与经典智能体（例如信念-愿望-意图（BDI）智能体）的根本差异在于利用 LLM 与先进技术作为通用的推理引擎与动态工具组合。**表 I** 给出了传统 AI 智能体与现代 AI 智能体的对比。

**表 I：传统 AI 智能体 vs. 现代 AI 智能体**

| 方面 | 传统 AI 智能体 | 现代智能体化 AI 系统（基于 LLM 的智能体） |
|---|---|---|
| **定义** | 具有固定感知/动作循环的自主实体；受限于静态规则或模型 | 使用 LLM 的自主推理系统，具动态行为、工具编排与上下文感知 |
| **自主性** | 自主性有限；常常依赖人类输入或预定义指令 | 高度自主；能独立执行复杂且长期的任务 |
| **目标管理** | 聚焦于单一、静态目标或固定任务规划 | 能自适应地管理多个演化的、嵌套的目标 |
| **架构** | 基于规则或 BDI（信念-愿望-意图）模型；单体设计 | 以 LLM 为中心的模块化架构，组件包括记忆、工具、上下文注入与角色 |
| **适应性** | 适用于受控、可预测的环境；泛化性差 | 为开放、动态、不可预测的环境设计 |
| **决策** | 确定性或基于规则的逻辑；符号推理 | 上下文敏感的概率性推理，具自适应规划与自我反思 |
| **学习机制** | 基于规则或监督学习，更新有限 | 自监督与强化学习；可持续微调 |
| **上下文处理** | 静态或手工编码的状态与规则 | 通过智能体协议（如 MCP、A2A）的动态上下文注入与运行时感知 |
| **通信** | 通过 ACL 或 KQML 的消息传递 | 实时、事件驱动的协作；自然语言接口 |
| **工具使用** | 工具与动作有限或预定义 | 基于上下文的动态工具调用、链式执行与 API 调用 |
| **记忆** | 可选，常常硬编码或任务特定 | 集成记忆系统，支持长短期信息保留 |

考虑到这一广泛演进，现在有必要重新思考乃至重新定义何为智能体。**现代智能体**可被更佳地定义为：

> "一个具备推理与通信能力的自主协作实体，能够动态地解释结构化上下文、编排工具，并通过记忆与跨分布式系统的交互来调适自身行为。"

## III. 智能体通信协议

LLM 驱动的自主智能体的兴起，凸显了在互操作性、安全性与可扩展性方面的关键挑战——其根源主要是碎片化的框架与临时性集成 [9][10]。健壮的智能体通信协议对于实现**对等发现、上下文共享与协调行动**至关重要，它们构成模块化且鲁棒的多智能体系统的支柱。这些协议相对于传统交互模型具有明显优势。

智能体通信协议从 1980–1990 年代的早期语义标准（如 FIPA ACL），演进到 2000–2010 年代的基于 Web 的系统（如 SOAP/WSDL），最终演变为今天由 LLM 驱动的协议（如 ACP、ANP）以及前瞻性的神经-符号或量子安全架构。尽管其具有变革性潜力，清晰且被普遍接受的标准仍处于萌芽状态，这造成了阻碍多智能体生态可扩展性与可组合性的鸿沟 [11][12]。新兴协议（如 MCP、A2A、Agora）旨在通过轻量的 JSON-RPC 模式（用于上下文交换、言语行为（performative）消息传递与发现）来弥合这一鸿沟。

从根本上说，当代通信协议共享一个统一原则："**消除对手动集成、定制中间件或深度特定协议专长的需求**，通过标准化的智能框架实现智能体之间、AI 与网络之间以及多智能体系统之间的无缝交互。" 其中最早的协议之一——**模型上下文协议（Model Context Protocol, MCP）¹**——最初为通过 JSON-RPC 的结构化工具调用与安全模式验证而设计。尽管 MCP 遵循客户端-服务器模型，但当需要严格层级角色时，它也能支持智能体间委托。后来，Google 的 **Agent2Agent Protocol (A2A) [13]** 引入更具智能体导向的架构，支持记忆管理、目标协调、任务调用与能力发现等功能。A2A 通过 **Agent Card、Task Object、Artifact**（标准化输出）等构件将通信形式化。为支持去中心化身份与语义互操作，**智能体网络协议（Agent Network Protocol, ANP）[14]** 结合了去中心化标识符（DID）与 JSON-LD 语义，围绕一个生命周期（创建、运行、更新、终止）组织通信 [15]。它既支持显式定义的协议，也支持使用 LLM 的自然语言协商。

基于类似原则，最初在 IBM 发起的**智能体通信协议（Agent Communication Protocol, ACP）²** 允许智能体通过 RESTful API 进行通信，使用结构化的 JSON 消息对动作、目标与意图进行编码。其设计是传输无关的，并与 Web3 环境兼容，使其适合可扩展的跨组织通信。在更高级的抽象层，**Agora³** [16] 充当元协调层，整合包括 MCP、ANP 与 ACP 在内的多种协议。它引入了**协议文档（Protocol Documents, PDs）**——机器可读的规范——以指导智能体在选择或构建通信协议时作出决策。**表 II** 给出了所研究协议的全面对比，依据包括发现、消息传递、分层等标准。

**关键发现**

现代智能体协议（MCP、ACP、A2A、ANP、Agora）反映了向面向服务互操作性的转变，其中 JSON-LD/PD 语义支持动态发现与组合。然而碎片化仍然存在：HTTP 在传输层占主导，但语义异质性（自定义言语行为 vs. 目标导向/PD 消息）限制了无缝集成。像 AutoGen 这样的框架跨域桥接，但标准化的服务契约（类比 WSDL for agents）仍处于萌芽阶段，阻碍了大规模 agent-as-a-service 的采用。

**表 II：现代智能体化 AI 协议对比**

| 特性 | MCP | ACP | A2A | ANP | Agora |
|---|---|---|---|---|---|
| **消息格式** | JSON-RPC | JSON-LD | JSON-RPC / HTTP / SSE | JSON-LD + NLP | PD + 自然语言 |
| **语义** | 自定义言语行为 | 目标导向消息（如 goal、action） | 自定义言语行为 | PD | PD |
| **发现** | 手动 | 智能体元数据（agent.yml）与注册表 | Agent Card | 以 JSON-LD 形式描述智能体 | 交换自然语言 PD |
| **框架** | LangChain、OpenAgents、Agno | AutoGen、LangGraph、CrewAI | AutoGen、CrewAI、LangGraph | AGORA、CrewAI、Semantic Kernel Agent | — |
| **传输层** | HTTP、Stdio、SSE | HTTP | HTTP，可选 SSE | HTTP with JSON-LD | HTTP with PD |
| **用例** | LLM-工具集成 | 跨智能体协作 | 企业智能体编排 | 去中心化智能体市场 | 多智能体环境 |

## IV. 智能体化 AI 框架

### A. 综合概览

智能体化 AI 框架为开发智能体（其展现自主性、上下文感知与目标导向行为）的系统提供了基础架构。这些由 LLM 驱动的智能体动态地解读任务、编排工具使用并适应实时环境。在本节中，我们通过基于共享原则与使用模式对主要智能体框架进行分类，合成主要智能体框架，凸显其设计选择如何塑造智能体行为与协作（见**图 1**）。

![图 1：智能体化 AI 设计分类法](images/agentic-ai-frameworks-architectures-2508.10146/p004_i01.png)

一些框架聚焦于结构化编排与多智能体工作流。**AutoGen [17]** 由 Microsoft 开发，支持丰富的多智能体对话，配备共享工具与模块化的 LLM 后端，为编码与自动化等领域的协作工作流提供基础。类似地，**CrewAI [18]** 推动智能体间的基于角色的协作，强调基于团队的协同问题求解中的协调与委托。**Listing 1** 展示了一个 CrewAI 智能体的示例。

```
Listing 1: 简单的 CrewAI 智能体

agent = Agent(
    role="Research Assistant",
    goal="Summarize recent AI news",
    backstory="An AI expert who keeps track of the latest in research.",
    llm=OpenAI(temperature=0.5),
    tools=[],
    memory=True
)
```

另一个框架 **MetaGPT [19]** 遵循可类比的理念，通过让每个智能体承担专门角色（如项目经理或开发者）来在产品生命周期流水线中执行结构化任务，从而模拟真实世界的软件工程团队。**SmolAgents** 与 **PydanticAI⁴** 提供了轻量且透明的智能体组合方案。SmolAgents 强调简洁性与模块化，以低开销支持提示链式调用与工具使用。PydanticAI 使用 Pydantic 库定义智能体模式，增强可复现性与安全性，尤其便于调试与部署。

在编排抽象与开发易用性方面，**OpenAI Agents SDK** 提供了一个高级接口，封装了工具使用、记忆与指令遵循行为。其他框架则倾向基于图（graph-based）或声明式（declarative）的编排。**LangGraph [20]** 引入新颖的基于图的模型来为 LLM 智能体排序任务。通过支持可组合的流与有状态操作，它为研究与分析场景下可追踪且可扩展的智能体设计提供了可能。沿着类似思路，**Semantic Kernel [21]** 提供企业级编排，对规划、记忆与技能执行提供细粒度控制，使其能在结构化推理场景下与外部系统集成。**Agno** 则倡导一种声明式且透明的方法来定义智能体目标、工具与推理逻辑，使其成为需要可解释性与控制力的自动化工作流的有力候选者。

最后，像 **LlamaIndex** 与 **Google ADK** 这样的框架推动了以数据为中心与分布式智能体生态的边界。LlamaIndex 让智能体具备查询结构化与非结构化数据的能力，适用于知识密集型应用。Google ADK 仍处于实验性阶段、面向可扩展性而设计，支持多智能体工作流的编排，使其适合自适应 AI 助理与企业自动化。

为提炼通用且可复用的智能体模型，识别共同的架构模式，**图 2** 中的提议类图描绘了一个统一的类模型。

![图 2：智能体化 AI 框架的统一类模型](images/agentic-ai-frameworks-architectures-2508.10146/p004_i02.png)

**关键发现**

在实践中，各框架共享核心组件：**LLM** 通过基于提示的交互（由上下文学习增强——少样本、单样本、思维链提示）实现高级推理，使智能体能在最少监督下执行复杂认知任务；**工具**（外部动作）；**记忆**；以及**护栏**——确保智能体输出与动作的安全性、可靠性与有效性。

### B. 智能体化 AI 框架中的记忆

记忆是智能体化 AI 的基础，使上下文感知、自适应行为成为可能 [22]。其机制支持跨交互的保留、检索与推理，促进多轮对话、偏好适配与知识迁移。记忆主要可分为：(1) **短期记忆**——使智能体维持即时对话或任务上下文；(2) **长期记忆**——与之相对，跨会话捕获持久化数据，如用户偏好、任务历史或学到的知识，智能体可在以后重访。一些框架还实现长期记忆的专门形式，如**语义记忆 [23]**——存储并复用过去的推理路径或决策；**程序性记忆**——回忆曾用过的特定任务流或策略；以及**情景记忆 [24]**——对特定过往交互或经验的文本快照进行编码，使智能体能随时间展现更细致且个性化的行为 [25]。

在所综述的框架中，记忆依据目标用例与设计哲学以多种方式实现。例如，LangGraph 将记忆集成至其基于图的结构中，在节点内与跨节点保留状态，从而让智能体在保留上下文的前提下遵循结构化工作流。OpenAI 的 SDK 通过对话会话支持记忆，显式地维护任务特定状态，简化开发者的实现。CrewAI 为每个智能体配备个体记忆，在角色特定协调与委托中起核心作用。AutoGen 支持智能体间结构化对话，其中记忆可在角色间传递、持久化或修改 [17]。Google ADK 为动态协作与任务交接维护共享记忆。与之形成对比，Agno 采用更具声明性的记忆方法以增强透明性与可检查性。**表 III** 基于各框架的官方文档与观察到的实现模式，给出了记忆支持的对比概览。

**表 III：智能体化 AI 框架中的记忆支持**

| 框架 | 记忆方法 | 短期 | 长期 | 语义 | 程序性 | 情景 |
|------|---------|:----:|:----:|:----:|:------:|:----:|
| LangGraph | 有状态的图节点在智能体转换间保留上下文。 | ✓ | – | – | – | – |
| OpenAI SDK | 基于会话的记忆抽象（如 ConversationBufferMemory）。 | ✓ | – | – | – | – |
| SmolAgents | 记忆是可选的，需手动注入。 | – | – | – | – | – |
| CrewAI | 智能体级记忆用于对话与协调，含实体/上下文记忆。 | ✓ | ✓ | ✓ | – | ✓ |
| AutoGen | 在结构化对话间维护共享记忆上下文。 | ✓ | ✓ | – | – | ✓ |

### C. 智能体化 AI 框架中的护栏

护栏通过验证输出、执行安全策略与维护工作流完整性，确保 AI 智能体的安全且可预测的行为。在当前框架中，AutoGen、LangGraph、Agno 与 OpenAI SDK 提供了最强的原生支持。AutoGen 包含验证器与重试逻辑；LangGraph 通过节点验证支持高级流级检查；Agno 提供早期阶段的信任层；OpenAI SDK 支持基于模式验证与开发者定义的安全防护。其他如 CrewAI、MetaGPT 与 Google ADK 提供部分支持，而 LlamaIndex 与 Semantic Kernel 仅在特定阶段进行验证。SmolAgents 完全缺乏护栏，优先考虑开发者对安全性的掌控。总体而言，尽管护栏能力正在涌现，但大多数框架仍需外部逻辑或手动设置才能实现强有力的执行。这凸显了在智能体化 AI 开发中对标准化、模块化安全层的需要。

### D. 智能体化 AI 框架的应用

CrewAI 与 LangGraph 这样的智能体化 AI 框架已被应用于多个领域，通过协调专门的 LLM 智能体。在金融领域，它们支持风险管理、异常检测与战略制定等任务 [26][27]，CrewAI 通过对历史数据的推理支持知情决策。LangGraph 已被用于智能交通中的模块化交通管理 [28]；CrewAI 也被用于旅游业的自动化旅行规划，使智能体能够协作分析城市并规划行程 [29]。

尽管有这些努力，智能体化 AI 框架的更广泛采用仍面临挑战。关键障碍包括架构透明度与标准化的缺失，因为大多数方案缺乏可重用、可互操作的设计——而这在面向服务系统中是常见特性。主流框架（如 AutoGen、AutoGPT）在领域特定场景（如金融、医疗）中仍未被充分利用。此外，多智能体协调协议往往不充分，可扩展性受限，迫切需要用于协作的标准化 API（见**第 IV-E 节**）。

### E. 服务计算视角下的智能体化 AI

本节回答 **RQ4**：智能体化 AI 框架在多大程度上已准备好集成到服务计算生态中？我们通过分析关键面向服务的能力（如动态发现、组合与编排）对照现代服务架构需求，在**表 IV** 中评估它们的成熟度。

Semantic Kernel 与 Google ADK 通过技能规划器与云集成分别为服务组合提供强力支持。但这两个框架都没有原生内嵌完整的服务计算原语。它们的就绪程度依赖于与外部注册表与编排层的集成。LangGraph 凭借其状态机抽象，同样提供健壮的组合模式与可扩展性钩子用于发现。LangGraph 提供确定性的、容错的编排，可通过简单的目录适配器支持发现，使其成为一个有力的备选方案。相比之下，CrewAI、AutoGen、Agno 与 MetaGPT 擅长多智能体规划或代码生成，但需要辅助服务注册表（如 OpenAPI 网关或服务网格）才能参与完全动态的服务生态。引入这些注册表将把这些框架从任务中心的智能体平台提升为全面的服务计算解决方案。

为支持面向服务的智能体化 AI，当前框架已开始集成 W3C 标准（如 WSDL、WS-Policy、BPEL），但采用率仍有限（见**表 V**）。CrewAI 与 OpenAI SDK 中的 JSON-Schema 函数注册模仿了 WSDL，AutoGen 反映了 BPEL 风格的编排但缺乏声明式语法。WS-Policy 与 WS-Security 原则通过运行时设置和 JWT 出现在 Agno 与 SmolAgents 中，但缺乏正式策略或安全令牌格式。协调逻辑与类似 SLA 的行为存在于 MetaGPT 与 CrewAI 等框架中，但没有 WS-Coordination 或 WS-Agreement 的正式构件。总体而言，受 W3C 启发的特性正在涌现，但标准化的、可互操作的采用仍然缺失。

## V. 局限性与挑战

尽管进展迅速，当前智能体化 AI 框架仍存在若干关键局限。这些局限涵盖架构刚性、动态协作约束、安全风险与互操作性缺失。

**架构刚性**：大多数框架强制智能体承担静态角色（如规划者、执行者、编码员），这在动态或演进的任务中限制了适应性。例如在 MetaGPT 或 CrewAI 中，一旦智能体被分配了预定义角色，便难以在执行过程中改变行为。

**缺乏运行时发现**：许多系统中的智能体无法在运行时动态发现或与对等智能体协作。相反，所有智能体交互必须静态定义，这限制了可扩展性与涌现协同。作为解决方案，我们可以实现智能体或技能注册表——一个中央目录——智能体可在其中发布与查询能力。这允许新智能体加入系统并动态地形成协作。

**代码安全**：在 MetaGPT 与 AutoGen 中常见的生成代码执行带来严重安全风险。生成的 Python 代码可能包含文件系统访问、shell 命令或不安全的导入。为确保安全执行，可采用具有严格能力限制的沙箱环境（如 Docker 容器）。或者，可以将执行限制在预先批准的、无副作用或无外部依赖的纯函数。

**互操作性差距**：各框架在各自的孤岛中运行，使用互不兼容的智能体、任务、工具与记忆抽象。例如，CrewAI 的任务模型不能被 AutoGen 智能体直接解释，SmolAgent 规划者也无法在大量翻译工作的情况下调用 LangGraph 工作流。这种碎片化阻碍了代码复用、工具可移植性与系统无缝集成。一个有前景的架构方案是采用 SOA 原则，将 AI 智能体包装为服务以通过 RESTful API 暴露其能力。这能实现基本的跨框架交互——例如，让 LangGraph 规划者远程调用 CrewAI 编码员。然而 REST 缺乏对复杂智能体交互的表达力。为应对这一问题，一个新兴方向是使用受 FIPA-ACL 或现代标准（如 AutoGen 的消息层）启发的通信协议。在未来的框架中，结合 RESTful 暴露与协议级消息传递，可实现完全可互操作的协作型智能体生态。

## VI. 结论

本文综述并分析了主要的智能体化 AI 框架（如 CrewAI、LangGraph、AutoGen、MetaGPT），聚焦于架构、记忆、通信、护栏与服务计算支持等方面。尽管这些框架都旨在支持 LLM 驱动的应用，它们的设计优先级各异：一些强调模块化与记忆（如 Semantic Kernel），而另一些聚焦于协作（如 AutoGen、ADK）或基于角色的协调（如 CrewAI）。通信协议仍在演化，ACP 与 Agora 等新范式表明对更健壮的智能体间与人机对话模型的需求。

尽管进展迅速，当前的智能体化 AI 框架仍面临若干关键局限，阻碍其泛化性、可组合性以及对服务计算的支持。为进一步推动该领域，关键方向包括建立标准化的基准以实现客观比较与可复现性，以及开发通用智能体通信协议以增强跨框架互操作性与可扩展性。另一个有前景的方向是将多智能体系统（MAS）范式——如协商、协调与自组织——纳入现有框架。
